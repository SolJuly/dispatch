# 升级与新增工作流：坑与正确流程（固化版）

> 2026-11-12 定稿。这份文档不是"经验总结"，是**执行清单** ——
> 每一次新增工作流、每一次升级镜像，照着走完，坑就不再复现。
>
> 配套工具三个：`tools/upgrade_audit.py`（镜像升级离线审计）、
> `tools/wfctl.py`（工作流变更唯一入口）、`tools/p20/graph_check.py`（图契约检查）。
> 文档里每条坑都标注了**哪条命令能在花钱之前拦住它**。拦不住的会明说。

## 0. 先记住一件事

**所有的坑都只在"钱已经花出去"之后才显现。** 这不是概率问题，是结构问题：

```
本地写配置  →  建机（¥2.15/h 开始计费）  →  setup  →  提交  →  才发现错
                    ↑
              错误的代价从这一刻起就在累计
```

所以流程设计的目标不是"少犯错"，而是**把发现错误的时机往前推**：

| 时机 | 手段 | 单次代价 | 能拦住什么 |
|---|---|---|---|
| 写配置时 | `wf_lint` 19 条规则 | ¥0 | 绑定错、正负反、类型不符、重复绑定 |
| 提交前 | `graph_check` | ¥0 | 缺必填输入、连线类型不匹配、动态参数子键缺失 |
| 建机前 | `asset_preflight` | ¥0 | 缺节点、缺权重、值不在候选列表 |
| 升级前 | `upgrade_audit` | ¥0 | 换镜像会不会把现有工作流搞死 |
| **只有这里开始花钱** | 真机 | ¥0.13–3.8 | 张量形状、显存、推理 NaN、出片质量 |
| 跑完后 | `wfctl verify` | ¥0 | 把"没有证据的 verified"写进 compat.json |

**下面 6 张表里，凡是"本轮能拦"写着 ¥0 的，都意味着那次事故今天不会再花一遍钱。**

## 1. 新增工作流：七个步骤

```
拿图 → wfctl new（自动反推 + 门禁 + 导入）→ 人审四处 → 预演 → 真机 → 转正 → 上线
```

```bash
# ① ② 一条命令
python3 -m tools.wfctl new --key my_wf --name "显示名" --kind video \
    --graph /path/to/my_wf.api.json --model <模型key> --template i2v

# ③ 人审（机器判不了，见 §1.2）
# ④ 预演 ¥0
python3 -m tools.p2.asset_preflight --workflow my_wf

# ⑤ 真机（花钱）
python3 -m tools.p20.p20ctl new --workflow my_wf --allow-experimental --run

# ⑥ 转正（唯一能写 verified 的入口）
python3 -m tools.wfctl verify --key my_wf --job-id <job_id>

# ⑦ 上线
./deploy.sh
```

终端里随时可看：`python3 -m tools.wfctl guide`

### 1.1 六个必须记住的形态

| 模板 | 形态 | 什么时候用 |
|---|---|---|
| `t2i` | text → image | 只要提示词 |
| `i2i` | image + text → image | 改风格 / 加细节 |
| `t2v` | text → video | 只给提示词出片 |
| `i2v` | image + text → video | 首帧推运动（最常用） |
| `flf2v` | image + image_2 + text | 首尾帧插值 |
| `v2v` | video + image + text | 动作迁移 / 整片重绘 |
| `upscale` | image → image | 超分放大 |
| `inpaint` | image (+mask) → image | 擦除 / 局部修复 |

不给 `--template` 时按图的输入形态自动推荐：
有视频输入 → `v2v`；两张图 → `flf2v`；一张图 → `i2v`；都没 → `t2v`。

### 1.2 人审四处（这是唯一不能自动化的部分）

**a) 正负提示词方向**

把 `prompt` 和 `neg_prompt` 的默认值各念一遍。

> 2026-11-11 实测：**5 张卡犯这个错，其中 4 张已经是 verified**。
> 「真机跑通过」完全不代表参数绑对了 —— 正负填反只会让成片变糊，作业照样 PASS。

工具只标 `confidence=medium`，因为连图连通性追出来的结论也不能当真。
`WF005/006/017/018` 四条规则能拦**明显的**（默认值相同、含负向词、绑到同一条输入），
拦不住"绑到了一个合法的但错误的编码器"。

**b) 参数是否重复**

同一个节点同一条输入只能有一个参数管。渲染顺序是字典序，后者覆盖前者。

> 2026-11-11：`scail2_int8` 同时有 `prompt` / `prompt_2` / `prompt_3`，
> 其中 `prompt` 和 `prompt_3` 都绑 `1404.text`。用户改 `prompt`，
> `prompt_3` 的旧值随后又盖回去 —— 改了等于没改，且完全不报错。

`WF019` 能拦这一条。

**c) 模型卡覆盖**

`registry/models/<key>.json` 的 `files` 要覆盖卡里 `model.slots` 的每个角色。

> `wfctl new` 会在落盘前就拦住（不用等 `p20ctl import` 抛异常）：
> ```
> ✗ 模型卡 ltx_2_3_22b_dev_fp8 覆盖不了图里推出来的槽位。
>   图要的槽位 : ['ckpt', 'text_encoder']
>   模型卡有   : ['ckpt', 'lora', 'lora_2', 'upscale']
>   缺         : ['text_encoder']
> ```

**d) `frames` / `length` 绑到哪个节点**

必须绑到**决定 latent 长度**的节点（`EmptyXxxLatentVideo.length`、
`WanVaceToVideo.length`）。

> 2026-11-11 踩过：`scail2` 图里 4 个 `ImageFromBatch.length=1`，
> 照它写 frames 默认 1，用户不改就出 1 帧废片。
> 绑到 `ImageFromBatch.length` 是**裁切**，不是总帧数。

## 2. 新增工作流的坑（按危害排序）

### 坑 1：图不是 API 格式

ComfyUI 里有两个 Save：普通 Save 存的是 UI 格式（`{"nodes": [...]}`），
只有 **Save (API Format)** 存的是提交格式。

```
判据：顶层是 {"节点id": {"class_type": ..., "inputs": {...}}}
```

| | |
|---|---|
| 本轮能拦 | ✅ ¥0。`wfctl new` 直接报"图不是 ComfyUI API 格式" |
| 不能拦 | 无 |

### 坑 2：API 格式丢掉了没有默认值的必填输入

导出成 API 格式时会丢一批输入。有默认值的服务端会补；**没有默认值的会让 `/prompt` 直接 400**。

> 2026-11-10：`pack_image_qwen_image_edit_2511_int8` 一次缺 5 个输入
> （prompt ×2、reference_latents_method ×2、SaveImageAdvanced 的 format 子字段），
> 每条要花 ¥0.10 建机才能发现一次。

| | |
|---|---|
| 本轮能拦 | ✅ ¥0。`python3 -m tools.p20.graph_check` |
| 判据 | 分三段：`has_default`（服务端补，不算缺）/ `dynamic`（运行时生成，标"需实测"）/ `missing`（真缺） |
| 陷阱 | 第一版把 `COMFY_AUTOGROW_V3` 算成"缺"，8 条工作流报 53 个问题，大部分误报。**照那个清单修会把能跑的工作流改坏** |

自动补图里漏写的字段：

```bash
python3 -m tools.p20.graph_fill --dry-run    # 先演练
python3 -m tools.p20.graph_fill --apply      # 真写回（自动备份 .bak）
```

`graph_fill` **刻意不补**：模型名、文件名、提示词、连线型输入。
补错这些不报错，只会静默出错片。

### 坑 3：动态参数的子键

两种动态类型，写法**不同**，混了就是 400：

| 类型 | 需要的键 |
|---|---|
| `COMFY_DYNAMICCOMBO_V3` | 主键**和**子键都要 |
| `COMFY_AUTOGROW_V3` | 只用子键 |

> 2026-11-11：`TextGenerateLTX2Prompt.sampling_mode` 是 DYNAMICCOMBO，
> 图里写了 `"sampling_mode": "on"` 却没写它需要的
> `top_k/top_p/temperature/repetition_penalty/seed/min_p`，
> 提交时被拒 6 个 `required_input_missing`。
> 而 `graph_check` 当时判"通过"—— 因为它只查"有没有以 `sampling_mode.` 开头的键"，
> 而这个节点用的是**平铺**写法。
>
> 更关键的是：`on` 要 6 个、`off` 一个都不要。所以必须**按图里实际选的那个 key** 展开。

| | |
|---|---|
| 本轮能拦 | ✅ ¥0。`graph_check` 的三条独立规则（缺主键 / 缺子参数 / 都没有 → dynamic） |

### 坑 4：连线类型不匹配

字段齐全、`graph_check` 全绿，真机才报 `return_type_mismatch`。

> 2026-11-11：`ref_videos.ref_video_0` 要 `IMAGE`，我接了 `LoadVideo` 的输出 `VIDEO`。
> 一次 ¥0.09 建机费换一条错误信息。

| | |
|---|---|
| 本轮能拦 | ✅ ¥0。`graph_check` 取源节点 `output[out_idx]` 的类型与目标声明比对 |
| 陷阱 | 类型比较**不能按字符串直接比**：目标可能是联合（`FLOAT,INT,BOOLEAN`）或通配（`*`）。第一版直接比，一趟扫出 33 处"错误"，全是假的 |
| 另一个陷阱 | `COMFY_AUTOGROW_V3` / `DYNAMICCOMBO_V3` 要**下钻到 template** 取真实类型，顶层类型一律放行会漏检 |

### 坑 5：权重文件名暴露成自由文本

> 2026-11-11：`sdxl_t2i_lora.lora` 是 `string` 类型，UI 渲染成文本框 ——
> 用户打错一个字就是 `use_missing_models`，而报错发生在提交那一刻。

| | |
|---|---|
| 本轮能拦 | ⚠ `WF007` 只报 WARN，不拦（因为有些场景确实需要自由文本） |
| 正确做法 | 改成 `enum`，`values` 来自真机候选 |

### 坑 6：标了 verified 却没有证据

`registry/compat.json` 是**唯一事实来源**，`registry.db` 只是派生索引。
手改 `compat.json` 把 `experimental` 写成 `verified`，结果是"没有可追溯性"。

| | |
|---|---|
| 本轮能拦 | ✅ **结构上只有一条路**：`wfctl verify` 是唯一能写 `verified` 的入口 |
| 硬条件 | 作业 `DONE` + `manifest.verdict == PASS` + 作业 meta 与卡一致 + 过门禁 |
| 质量分 | D 会拦下来，确要转正加 `--allow-low-quality`，但先看 `issues` |

### 坑 7：改了配置忘了重导入

`registry.db` 在 `.gitignore` 里，**改完 JSON 不跑 import，UI 还是旧的**。

| | |
|---|---|
| 本轮能拦 | ✅ `wfctl update` 自动跑 validate + import，不要求你记得顺序 |
| 教训 | 「能自动做的不要让人记」是这套工具的设计原则 |

### 坑 8：名字里写死状态词

> 2026-11-11：4 条已 verified 的卡名字里还挂着「尚未开发」，
> 用户以为不能用，实际上能用。

`WF008` 拦这一条。

## 4. 镜像升级：正确流程

```bash
# ① 拿到目标版本的 object_info 快照（唯一需要开机的步骤，约 ¥0.5）
#    起一台目标镜像的空实例，curl /object_info 存下来
curl -s http://127.0.0.1:8188/object_info > oi-target.json

# ② 离线审计（¥0，不建机）
python3 -m tools.upgrade_audit audit --target oi-target.json

# ③ 看影响面，决定是否继续
python3 -m tools.upgrade_audit diff --base A.json --target B.json --verbose

# ④ 真机推理冒烟（图 / 视频 / 放大各一条，约 ¥2–3）
# ⑤ 全量回归：把 54 条工作流按 batch 跑一遍
```

### 4.1 `upgrade_audit` 的四档判据

| 档 | 含义 | 会死吗 |
|---|---|---|
| `LOST` | 节点类在新镜像里没了 | **会**。用到它的工作流必死 |
| `OUTPUT` | 输出变短 / 顺序变了 | **会**。索引越界的连线必死 |
| `INPUT` | 必填输入新增（无默认值）或类型改变 | **会**。图里没写该字段的必死 |
| `ADDED` | 只多了可选输入、多了节点、**输出纯追加** | 不会 |

**四档必须分开统计。** 混成一个数字就等于没说：
"变了 765 处"听起来严重，其中 107 处是新增节点（无害）。

### 4.2 输出「纯追加」是安全的 —— 这条差点被判死

> 2026-11-12：`upgrade_audit` 第一版把输出 `[STRING] → [STRING, STRING]`
> 判成 `OUTPUT` 破坏性变更，报了 5 处、6 条工作流受影响。
> 而真相是：那 6 条在真机上**全部跑通**（全部只用 idx 0）。

判据必须分三种：

```
ob 比 oa 短                  → 真的坏（索引越界）
ob[:len(oa)] == oa 且更长    → 纯追加，无害
数量相同但顺序/类型不同      → 危险（idx 指向了另一个类型）
```

**这类误报的代价比漏报更难发现** —— 它让你因为假警报放弃一次本来可用的升级。

### 4.3 真实数据（三次升级的审计结论）

| 升级 | 基线节点 | 目标节点 | 破坏性 | 受影响工作流 |
|---|---|---|---|---|
| v4 → v4+核心0.43.0 | 1757 | 1818 | **0** | **0/54** |
| v4 → 裸 0.45.0 | 1757 | 1094 | **765**（全 LOST） | 4/54（其余 45 条共用节点安全） |
| v4 → 0.45.0 + 侧载自定义节点 | — | 目标含全部节点包 | 预期接近 0 | 待测 |

**裸 0.45.0 的 765 个 LOST 全部是自定义节点包**（Impact-Pack / KJNodes /
FaceParsing / SeedVR2 / TTPlanet …）—— 平台镜像只带 ComfyUI 核心，
不带我们的 13 个节点包。所以「换底座」必须连同节点包一起搬。

## 5. 镜像升级的坑

### 坑 1：不要升 0.43.0 —— 它有 `memfd_create` bug

```
comfy/anonymous_file.py 用了 os.memfd_create
而 miniconda Python 3.10.15 没有这个函数（hasattr = False）
→ 所有走 int8 模型加载的路径直接崩
0.44.0 才改用 ctypes 调 libc
```

> 2026-11-12 实测：`SaveImageAdvanced` 报
> `execute() missing 1 required positional argument: 'format'`，
> 手工补 `memfd_create` 后仍失败 —— 说明还有第二个问题叠在上面。
> **结论：要升就升 0.44+，不要 0.43.0。**

| | |

## 6. 镜像体积与费用（口径纠正过两次）

存储费  ¥0.236/GB/月，每天 01:10 结算

## 7. OOM 自动升卡（2026-11-12 新增）

显存不足不再原地失败，而是换更大的卡重跑。**三道闸缺一不可**：

| 闸 | 判据 | 默认 |
|---|---|---|
| ① 判定闸 | 只有日志里**确诊**显存不足才升卡 | 进程崩了但没 OOM 字样 → 不升 |
| ② 次数闸 | 最多升 2 次（24G → 48G → 80G） | 96G 还 OOM 说明问题不在显存 |
| ③ 预算闸 | **已花 + 将花** < `budget.max_cost` | 只算单次会漏掉前面烧掉的钱 |

### 7.1 显存阶梯（2026-11-12 实测）

| 卡型 | 显存 | ¥/h | 库存 | 可作升卡目标 |
|---|---|---|---|---|
| `4090` | 24G ✓ | 2.15 | 54 | 起点 |
| `4090_48G` | 48G ✓ | 3.80 | 2 | ✅ |
| `5090` | 32G | 3.99 | 0 | ✅（常无货） |
| `A100` | 80G | 10.75 | 1 | ✅ |
| `A800` | 80G | 7.36 | 0 | ✅（常无货） |
| `H20` | 96G | 7.50 | 2 | ✅ |
| `V100S` | 32G | 1.41 | 1 | ❌ **Volta sm_70，无 int8 tensor core** |
| `P40` | 24G | 0.40 | 0 | ❌ Pascal sm_61 |
| `3090` | 24G | 1.19 | 0 | 不比 4090 大 |
| `3080Ti` | 12G | 0.74 | 0 | 更小 |
| `2080` | 11G | 0.42 | 0 | 更小 |

**V100S 和 P40 显存够但被排除**：我们的权重是 int8/fp8 量化的
（`comfy-aimdo` / `comfy-kitchen` 的解码内核），这些内核要 tensor core。
升到这两张卡的后果不是"慢一点"，而是**换一种方式失败**，然后再花一轮钱。

### 7.2 只升不降

`next_targets()` 只返回显存**严格更大**的卡。降级等于把已经证伪的配置再跑一遍。

`instance.oom_escalation.floor_vram` 是**跨进程生效**的下限：只要它在，
`--resume` / `--restart` / 正常重跑都不会再选回小卡。
要回到小卡必须 `--reset-escalation`（人工声明"这次 OOM 是参数写错了"）。

### 7.3 升卡时旧实例必须真销毁

不能走「长任务空转窗口」也不能走「借来的槽位不销毁」——那台机器**已经证明
跑不了这个作业**。`step_release` 的 `force_release` 分支在所有"保留"判断
**之前**生效，且直接 `terminate`。

## 9. 已知边界（工具兜不住，必须真机）

| 类别 | 为什么兜不住 | 最近一次实例 |
|---|---|---|
| 张量形状不匹配 | 本地没有求解器 | `fasth3_ominiref_r2v`：`tensor a (24) must match b (768)` |
| 显存够不够 | 取决于卡型和图的实际峰值 | 静态算不准，只能靠 OOM 后升卡 |
| 推理会不会 NaN | 同上 | — |
| 权重版本对不对 | 文件名对得上 ≠ 版本兼容 | — |
| 正负提示词方向（隐蔽的那种） | 只能靠人念一遍 | 5 张卡犯过，4 张当时是 verified |
| 成片好不好看 | 质量分只抓崩坏，不评审美 | `quality.py` 七项技术判据 |
| `memfd_create` 类运行时 bug | `object_info` 里看不出来 | 0.43.0 的 int8 全崩 |
| 平台侧意外关机 | 平台行为 | 2026-11-12 两次 |

## 10. 这份文档怎么维护

**新增一条坑时，问三个问题：**

1. **能不能变成一条门禁规则？** 能就加进 `wf_lint`（现在是 19 条）。
   不能变成规则的，"人审"那一节要写清楚。
2. **能不能在 `graph_check` / `asset_preflight` / `upgrade_audit` 里查到？**
   能就加判据，并配一条测试锁住它。
3. **如果都拦不住，代价是多少？** 写进 §9 的已知边界，别让它看起来像能自动兜住。

**改判据时必须同时改测试。** 这个仓库的测试不是覆盖率工具，
是「上一次踩坑的结论」的存储 —— `test_upgrade_audit.py` 里
`test_v4_to_core43_has_no_breaking_change` 那条断言，就是
"输出纯追加是安全的"这个结论的化身。它红了，说明判据被改回去了。
