# PPIO GPU 服务下线风险核查

> 日期：2026-11-13 21:40 · 分支 `feat/l5-ppio`
> 触发：YG 指出「这个平台的 GPU 服务好像快下线了」
> 结论先说：**证据指向「GPU 云服务这条线在前端被标记为即将下线」，但那块标签没有
> 对应的官方公告、没有 EOL 日期、后端 API 仍在正常返回数据。风险等级：高，但不是「已经不能用了」。**
> 需要 YG 决策：继续压在 PPIO 上，还是转回别的平台。

## 一、原始证据（我当时扫到却没在意的）

第一次抓 `ppio.com/pricing` 时页面上就有这行字，我把它当成普通导航文案跳过了：

```
模型 API 服务 | Agent 沙箱 | GPU 服务 即将下线 | 企业私有化部署
```

YG 提醒后重查，**这个徽章出现在三处**，都挂在「GPU 云服务 / GPU 服务」本身：

| 位置 | 原文 |
|---|---|
| `/pricing` 页 tab | `GPU 服务` + `<span class="bg-[var(--red-4)] ... text-[11px]">即将下线</span>` |
| 全站 header 一级导航 | `data-testid="header-menu-gpu_service"` → `GPU 云服务` + 同款红底徽章 |
| 移动端菜单 | `GPU 云服务` + 同款红底徽章 |

对照同一导航里其它一级项：

```
model_service    → 模型服务          （无徽章）
agent_service    → Agent 云服务      （无徽章）
gpu_service      → GPU 云服务 即将下线 ← 只有它带红底徽章
```

徽章用的是 `--red-4`（告警红），样式类是复用的 badge 组件 —— 说明这是产品侧
**主动、成体系**打的标，不是渲染事故。

## 二、相互矛盾的证据（这是判断难点）

### 支持「要下线」的

1. **前端三处红底徽章**，挂在产品线一级入口上
2. **产品目录在萎缩**：API 只返回 9 个 SKU，覆盖 3 种卡（H100 / L40S / 4090）
3. **落地页宣传与实际目录脱节**：落地页主推「H200 强势登陆」「H20 SXM 96GB ¥6.80/卡时」，
   但 `products` 接口里 **H200 和 H20 一个都没有**
4. 最新上新是 **2026-05-13**（L40S.22c125g），此后半年没有新 SKU

### 反对「正在下线」的

1. **34 条官方公告里没有一条 GPU 下线公告** —— 全是 LLM/多模态模型下线。
   与 GPU 相关的三条是：价格调整（2026-03-16）、自动迁移入口迁移、访问认证安全策略升级
2. **后端 API 完全正常**：`products` / `balance` / `images`（1852 条）/ `instances` 全部 200，
   价格字段结构完整，`billing_methods` 还标着 `postpaid, spot, prepaid`
3. **文档是活的**：`gpu-instance-overview.md` / `product-specifications.md` /
   `gpu-instance-pricing.md` 的 `Last-Modified` 都是 **2026-11-13 当天**（就是今天）
4. **官方 skills 仓库仍在维护 GPU 指南**：`PPIO/ppio-skills` → `ppio-docs/references/gpu-guide.md`
   把「GPU 实例 vs Serverless GPU」写得完整，没有 deprecation 提示
5. **落地页整页都在卖 GPU**，H200 写「年末特惠，火热抢购」—— 不像要收摊

## 三、我的判断

**最可能的解释：GPU 云服务（容器实例这条线）被标记为「即将下线」，正在往
Serverless / Endpoint 方向收敛，但具体时间表没公布。**

理由：徽章是产品侧成体系打的（三处、告警红、复用组件），不可能是误渲染；
而「没有公告 + 文档今天还在更新 + API 正常」说明**还没进入执行阶段**，
或者公告只发在控制台站内信 / 只对已付费用户可见（我们余额 0，可能收不到）。

**次可能：** PPIO 在做产品线重命名/合并（`/gpu-instance` 已 301 到 `/ai-computing/gpu-instance`），
徽章是「这个入口要挪走」的临时标记。但「即将下线」这个措辞对「挪入口」来说过重。

**排除：** 不是「已经停服」—— 后端全通，价格和镜像都能读。

## 四、这件事对已完成的工作意味着什么

### 代码本身没有白做

`ppio.py` 852 行、82 项测试、5 个真响应 fixture。它验证的是**契约可实现性**：

- `price()` 能从产品接口拿到真值（¥2.31 / ¥3.96 / ¥23.76 全部实测对上第三方监测）
- `stock()` 能读到 `available` / `inventory_state` / `deployable`
- `can_pull_oci = True` 真的成立（镜像地址在 `tags[].full_image_name`）
- 130GB 免费系统盘、Spot 5 折、按秒计费 —— 全部真机确认

**这套东西是「Provider 契约能覆盖到什么程度」的实证**，即便换平台，
`_money` 的教训（不要信响应里的 `precision`）、`_match` 的三档匹配、
`create`/`start` 分开的重试语义、`ssh_endpoint` 不缓存 —— 全部可复用。

### 但如果真下线，接它是白花的

- 200 行适配器 + 82 项测试 + 一轮真机调研
- 已经花的时间不会回来
- **更要紧的是：如果按它设计「失败停机保留 + 唤醒」，半年后平台没了，这套设计要重做**

## 五、决策建议

### 方案 A：先问 PPIO 要明确答复（0 成本，建议先做）

在控制台提工单 / 问客服，问三句话：

1. `GPU 云服务` 上的「即将下线」徽章指什么？是否有最终服务日期？
2. 现有实例和数据会被如何处理？有无迁移方案？
3. OpenAPI v2（`/gpus/v2/*`）是否也会一起下线？

**这是我们自己查不到的**：站内信和工单只对付费账号开放，余额 0 看不到。
充 ¥10 就能问（比继续猜便宜）。

### 方案 B：转回 AutoDL，PPIO 留作已验证的参考实现

- AutoDL 分支 `feat/l5-autodl` 还在，调研笔记完整，缺的是 price/stock/OCI
- 代价：`price()` 抛 UNSUPPORTED，`run.py` 预算闸门要退化成静态表
- 好处：AutoDL 是国内最大 C 端算力平台，短期没有下线风险

### 方案 C：找第三家（回到选型报告的表）

`reports/l5/国内GPU平台选型-20261113.md` 里的排名要按「生命期风险」重新加权：

| 平台 | 能力 | 生命期风险 | 重新评估 |
|---|---|---|---|
| PPIO | 8/10 | ⚠️ **高**（即将下线徽章） | **降级** |
| AutoDL | 5/10 | 低（国内最大 C 端） | **升为首选** |
| 恒源云 | 5.5/10 | 低（老牌） | 备选（要企业认证） |
| 智星云 | 4/10 | 中（API 最全但没 stop） | 备选 |
| 共绩算力 | 不可自动化 | 低 | 等它开放云主机 API |
| 蓝耘 / 算家云 / 算力自由 | 无 API | — | 不可选 |

### 我的倾向

**先按方案 A 问一句（¥10 换一个确定答复），同时按方案 C 把 AutoDL 重新提为首选。**

理由：接一家「前端标着即将下线、但没有任何时间表」的平台，等于把 P3（加权评分调度）
和「失败停机保留」都建在一个不知道还剩多久的地基上。而能力可以补，地基不能。

**不建议**现在就把 PPIO 代码删掉 —— 它是唯一一家把 price/stock/OCI 四项跑通的实证，
留着当参照，写第三家时可以照它对照「哪些能力是真的可得的」。

## 六、我漏掉了什么（复盘）

第一轮调研我抓了 `/pricing` 页面（`pr_ae4d3.html` 等），`即将下线` 就在返回的 HTML 里，
但我当时：
1. 只把该页当「价格数据源」用，没读导航文案
2. 在选型报告里给 PPIO 打了 8/10 —— **只评了能力，没评生命期**
3. 写了「PPIO 是唯一四项全给的平台」这个结论，却没问「这家还能活多久」

**这是选型方法论上的缺口，不是数据缺口**：能力矩阵里应该有一列「生命期风险」，
和「停机是否收费」同级。已写进本文档第五节表里。
