## 一、问题 2 + 问题 3 是同一个根因链（最重要发现）

### 实测证据

```bash
# /pub/ 直连 nginx → 401（要 basic auth）
$ curl -sk -o /dev/null -w '%{http_code}' https://<host>/pub/jobs/<id>/xxx.mp4
401

# 走 fileserver 代理 → 200
$ curl -s -o /dev/null -w '%{http_code}' http://127.0.0.1:8081/<token>/pub/jobs/<id>/xxx.mp4
200

# 但带 Range 请求 → 仍然 200 + 全量 1.37MB（不支持分段）
$ curl -s -o /dev/null -w '%{http_code} %{size_download}' -H 'Range: bytes=0-1023' <同上>
200 1378480
```

### 三个叠加的故障

| # | 问题 | 后果 |
|---|---|---|
| **A** | nginx `/pub/` 挂着 `auth_basic`，前端拿不到凭据 | 前端直连 `/pub/` 必然 401 |
| **B** | fileserver 的 `_pub_file` **把整个文件读进内存再发**（`p.read_bytes()`） | 1.4MB 视频要等全部读完才开始播 |
| **C** | **完全不支持 HTTP Range** | 视频**不能边下边播、不能拖动进度条**，必须下完才能播 |

**这就是你说的「加载期间等待时间过长，又或者视频根本加载不出来」。**

> 注意：`/files/<token>/pub/` 走的是 fileserver 代理，所以能出 200 —— 但 B 和 C 仍然存在。这就是为什么「有时能看（等很久）、有时看不了（超时）」。

### 问题 2 的独立根因

前端 **5 秒轮询**一次 `/api/p2/instances`，但后端这个接口的数据来自：

```
.compshare/watch.log    ← cron 每 5 分钟采样一次
```

**5 秒轮询一个 5 分钟才更新一次的数据源** → 界面永远慢半拍。这不是前端的问题，是**数据源本身就是滞后的**。

而且 `tools/p2/instances.py` 的注释写得很清楚：

> 数据源（全部本地文件 / 表，**不调云 API**，零费用、可离线）

设计上是省钱的，代价就是**不实时**。

### 问题 2 · 实例状态界面无法实时反映

**根因**：数据源滞后（见第一节）

| 层级 | 周期 |
|---|---|
| 前端轮询 | 5 秒 |
| `watch.log` 采样 | **5 分钟**（cron） |
| `status2.json` 刷新 | 10 分钟（cron） |

**另外**：`/api/p2/instances` 只读本地文件，**不查云 API**，所以：
- 你在控制台开机，界面要等下一次 cron 采样才知道
- 实例被平台回收，界面也是几分钟后才反应

**这不是 bug，是设计取舍**（零 API 调用=零费用）。但体验确实差。

## 七、一个技术判断

在动手前必须说清楚：**问题 2 和问题 3 是「设计取舍」造成的，不是纯 bug**。

| 设计 | 好处 | 代价 |
|---|---|---|
| 实例状态只读本地文件 | 零 API 调用、零费用、可离线 | 5 分钟滞后 |
| 视频全量读内存发送 | 代码简单、无依赖 | 大文件慢、不能拖 |
| 前端 5 视图 | 开发快 | 交互弱 |

**修它们要付代价**：
- 实时状态 = 每次点刷新打一次云 API（几分钱/次，可接受）
- Range 支持 = `fileserver` 要改成流式读文件（纯代码，无成本）
- 视图扩充 = 前端工时

我的建议是：**前两个都改（成本低收益高），第三个排后面**。
