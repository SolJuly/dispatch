## 2. 架构（按计划 §5.2）

```
batchctl submit → queue.db(item 入队, 同参数活跃态去重)
batchctl run    → scheduler 循环:
    ① 回收子进程（poll） ② reset_stale ③ 预算/配额检查 ④ claim ⑤ spawn run.py --batch
run.py --batch  → 作业级锁 + 九步闭环（状态机/G1/G2 全不变）
```

**关键决策**：一实例一 job，worker = `run.py --batch` 子进程（subprocess 隔离，最稳）；队列状态活在 `queue.db`，job 的 15 态完全不动。

## 4. 过程中修掉的 4 个真 bug（都是跑起来才暴露的）

| # | Bug | 后果 | 修复 |
|---|---|---|---|
| 1 | `tools/p2/queue.py` 与**标准库 queue 同名** | 脚本目录在 `sys.path[0]` 遮蔽标准库，CS 依赖报 `LifoQueue` 缺失 | 改名 `jobqueue.py` |
| 2 | `run.py` 建机硬编码 `cpu=16, memory_gb=96` | 4090（16C/64G）被平台拒：`cpu memory ratio not in 2:1` | 加 `GPU_SPEC` 表按卡型取 (cpu, mem) |
| 3 | 批量模式失败后仍**保留实例** 15 分钟 | 无人值守 → 空转烧钱（实测 ¥0.07） | scheduler spawn 时加 `--no-keep` |
| 4 | 失败终态恒为 `FAILED`，看不出可重试原因 | 重试逻辑失效（provision 失败不重排） | 从 `events.jsonl` 回溯 `FAILED_*` 判断是否重排 |

**第 4 条的实测价值**：第一次并发（12:33 那轮）两个 job 都因 bug#2 建机失败，scheduler 正确地**没有**无限重排（因为没有可重试态可识别 → 记为 failed），暴露了逻辑缺口后已修。

## 5. 一个「看起来是误报、其实是真错」的样本

第二轮并发里 B 作业 `FAILED_VERIFY`，freeze 门禁报 `ratio=1.0 / longest=2.92s`（整片冻结）。排查发现：**我为省 token 把 prompt 截断到第一句，删掉了「坐下→放下手机→起身→镜头右摇」的全部动作描述**，LTXV 忠实地产出了一个静止画面。

- 结论：**门禁没误报**，是输入退化导致产物退化。
- 修复：spec 用完整 prompt → 第三轮两片全 PASS。
- 这条正好给 D3「严格门禁」做了反向验证：它抓住的是真问题。
