## 2. 数据模型（`reports/p2/queue.db`，SQLite WAL）

`item` 关键列：

| 列 | 用途 |
|---|---|
| `job_id` **PRIMARY KEY** | P0-1 幂等的物理保证 |
| `params_hash` + 活跃态唯一索引 | 同参数防双花 |
| `state` | queued/claimed/running/done/failed/terminal_failed/cancelled/skipped/reclaimed |
| `instance_id` | 建机后登记；watchdog 据此找孤儿 |
| `heartbeat_at` / `lease_until` | P0-2 心跳与租约 |
| `attempts` / `max_attempts` / `next_retry_at` / `backoff_s` | P1-4 退避重试 |
| `exit_code` / `gpu_minutes` / `cost` | P0-3 审计字段 |

`audit_log`：`ts, job_id, instance_id, from_state, to_state, exit_code, gpu_minutes, detail`
—— 每次状态变更都原子写一条（submit/claim/running/done/failed/requeue/reclaim）。

## 3. 时序

```
submit ──► queued ──claim──► claimed ──► running ──► done
  │           ▲                 │           │
  │           │ requeue(退避)    │ 心跳 15s   │ finish(exit_code/gpu)
  │           └─────────────────┴───────────┘
  │                 ▲
  │  心跳断 >60s ────┘（mark_timeout → failed → requeue/terminal_failed）
  └─ 同 job_id/同参数活跃 → 直接拒（P0-1）
```

## 4. 逐项设计

### P0-1 幂等
- 物理层：`job_id PRIMARY KEY` + `ux_item_params_active`（活跃态唯一）。
- 应用层：`submit()` 先查 `job_id`，同 ID 且 queued/claimed/running → **显式拒绝**并给出原因；再查 `params_hash` 活跃态。
- 效果：重复下发在入队阶段就被拦住，**不会建第二台实例**。

### P0-2 心跳与超时
- **Worker 侧**：`run.py --batch` 启动 daemon 线程，每 `HEARTBEAT_S=15`s 调 `jobqueue.heartbeat(job_id)`，更新 `heartbeat_at` + 续租约。
- **调度器侧**：每 `SCAN_S=30`s 调 `reset_stale(TIMEOUT_S=60)`；`heartbeat_at` 超 60s → 先 `mark_timeout` 置 FAILED，再按 P1-4 退避重排。
- 说明：Worker 在 GPU 实例上跑，**连不到本机 DB**，所以「心跳」由本地 `run.py` 进程代发（等价于 worker 的守护协程）；这一点在报告里写明，避免误解为 Redis。

### P0-3 审计日志
- `audit_log` 表 + `_audit()` 在每次状态变更的同事务内写入。
- 字段覆盖你要求的：任务 ID、实例 ID、状态变更时间戳、exit_code、GPU 时长（分钟）。
- 查询：`python3 tools/p2/batchctl.py audit --job <jid>` / `--limit 50`。

### P1-4 有限重试
- 退避阶梯 `(1, 5, 30)` 秒，`claim()` 只领 `next_retry_at <= now` 的项。
- 最大 3 次（`max_attempts=3`）；超限 → `terminal_failed`，`batchctl list` 可见，`watchdog` 负责后续回收。
- 与 P0-2 衔接：心跳超时 → failed → requeue（占用一次 attempt）。

### P1-5 Watchdog 闭环
- `scheduler.reclaim_orphans()` / `batchctl watchdog`：
  1. 扫 `item.instance_id` 非空、状态非 running 的项；
  2. 实例仍存活 → SSH `pkill -f '[m]ain.py --listen'`（方括号技巧）+ `pkill -f '[c]omfyui'`；
  3. `terminate(uid)` 释放 GPU；
  4. failed/terminal_failed → `reclaimed`；queued（待重试）→ 只清 instance_id，保留重试。
- 适合 cron：`python3 tools/p2/batchctl.py watchdog`（加 `--dry-run` 只报告不动手）。

### P2-6 输出校验增强（已有基础）
- `verify.py` 已用 ffprobe 做 decode/geometry/frames/size/black/freeze/params 七项，**覆盖并超过**「时长+分辨率」要求。
- 未做：在实例内预筛（需把 media 镜像接进 run.py），当前校验在本地做，不影响正确性，只多花一次回传。

### P2-7 检查点
- 按你的要求**不推进**。设计上如果要接：ComfyUI 分段 + 段间落盘 + `RESUMING` 复用，属于大改，单列版本。

## 6. 边界与已知限制

- 心跳是「本地 worker 代发」，不是实例内 Redis（实例无外网，连不到 DB）。真·实例内心跳需要公网 DB，不在本轮。
- `terminal_failed` 只在「超 3 次」时出现，不会自动再试；需要人工 `batchctl` 处理或改 spec 重提。
- Watchdog 的 SSH kill 依赖实例 sshd 可达；不可达时只做 terminate（记录在审计）。
- 旧 `queue.db`（schema v1）与新 schema 不兼容，**删库即可重建**（job 事实在 `job.json`，不丢产物）。
