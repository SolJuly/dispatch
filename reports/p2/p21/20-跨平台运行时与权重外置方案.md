# 跨平台运行时 + 权重外置：技术方案

> 目标：运行时（ComfyUI + 节点 + 依赖）做成可移植的 OCI 镜像，权重放对象存储，作业引擎不绑死在任何一家 GPU 平台。
> 约束：现有 P1 作业引擎、P2 注册表、38 条模板、21 条 verified 工作流都要能继续跑；画质不能退化。
> 结论先说：**质量可以做到不变（同一份权重 + 同一套镜像）；速度会多出 1–5 分钟的冷启动/搬权重开销，推理本身不变**。

---

## 1. 现状与问题

| 项 | 现状 | 问题 |
|---|---|---|
| 运行时 | CompShare 自制镜像 `p2-comfy-media-v3`（210GB 全盘快照） | 平台私有格式，换平台带不走 |
| 权重 | 平台只读 `/model`（40T 共享库）+ 镜像内软链 | 换平台后路径/文件全变，要重新找 |
| 作业引擎 | `run.py` 直接调 CompShare API | 绑死 `compshare.cs` |
| 结果 | 21 条 verified，画质/成本有据 | 迁移后要重新验证 |

换平台时，真正要重做的是三样：**运行时、权重、调度适配**。三者解耦之后，平台就只是“一台能跑容器的 GPU”。

---

## 2. 目标架构

```
                    ┌─────────────────────────────┐
                    │  P1 作业引擎（不变）          │
                    │  job.json → run.py → 状态机   │
                    └──────────────┬──────────────┘
                                   │ Provider 接口
        ┌──────────────────────────┼──────────────────────────┐
        │                          │                          │
  CompShareProvider          AliyunProvider             RunPodProvider
  （现有，VM+私有镜像）        （ECS/ACK，OCI）            （Pod，OCI）
        │                          │                          │
        └──────────────┬───────────┴──────────────┬───────────┘
                       │                          │
              ┌────────▼────────┐        ┌────────▼─────────┐
              │ 运行时镜像 OCI   │        │ 权重对象存储 S3   │
              │ comfyui-p21:v3  │        │ oss://p21-weights │
              │ ~20–25GB        │        │ 按 provider 分桶  │
              └─────────────────┘        └──────────────────┘
                       │                          │
                       └────────► bootstrap.py ◄──┘
                                  拉权重 → 软链 → 起 ComfyUI → 健康检查
```

三层各自独立版本化：

1. **镜像**：只放代码/依赖，tag = 内容摘要（`comfyui-p21@sha256:…`）。
2. **权重**：S3 对象 + `weights.json` 清单（key → sha256/size/license/source）。
3. **作业**：`job.json` 只引用 model key，由 registry 解析到“镜像 digest + 权重清单”。

## 3. 分层设计

### 3.1 运行时镜像（OCI）

已有的 `docker/Dockerfile` 就是这一层：

- base：`python:3.10-slim-bookworm`（可换 `nvidia/cuda` base）；
- torch 2.10.0+cu130、ComfyUI `3c80da7f`、10 个节点 commit、198 个 pip 包锁定；
- **不放权重**；
- 启动脚本 `start-comfyui.sh` 前台跑 `main.py --listen 0.0.0.0:8188`。

构建放 CI（或一台有 docker 的构建机），推私有 ACR，按 digest 引用。预计压缩后 8–12GB，解压 20–25GB。

> CompShare 不能拉 OCI（API 只认 `CompShareImageId`），所以 CompShare 侧保留“用同一套 Dockerfile 步骤在实例上复现 → save”的路径；其他平台直接用 OCI。

### 3.2 权重仓库（S3 兼容对象存储）

**为什么用 S3 而不是 NAS/CFS**：S3 是所有平台都有的共同接口（阿里云 OSS、UCloud US3、MinIO、AWS），NAS/FUSE 在租用平台上经常没有权限挂载。

目录按 ComfyUI 习惯排：

```
s3://p21-weights/
  diffusion_models/{qwen_image_edit_2509_fp8,seedvr2_ema_3b_fp8,ltx-2.5-22b-int8,...}
  vae/{qwen_std_vae,seedvr2_ema_vae_fp16,...}
  text_encoders/{qwen25vl7b_std,...}
  loras/...
  weights.json          # 清单：key/路径/sha256/size/license/source_url
```

`weights.json` 是唯一事实来源，模型配置只写逻辑名：

```json
{"qwen_image_edit_2509": {"unet": {"key": "diffusion_models/qwen_image_edit_2509_fp8_e4m3fn.safetensors",
  "sha256": "...", "size": 20430698424, "license": "Apache-2.0"}}}
```

**交付方式二选一**：

| 方式 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A. 挂载 | rclone mount / ossfs 挂到 `/weights`，软链进 models | 不复制、秒级可用 | FUSE 依赖内核权限；随机读慢；safetensors mmap 可能不稳 |
| B. 拷贝（推荐） | bootstrap 时 `rclone copy` 到本地盘 | 本地盘速度、mmap 正常、无 FUSE 依赖 | 每个作业多搬 2–20GB |

推荐 **B 为主、A 为可选**；热模型（SeedVR2 3B、Qwen VAE）可以打进镜像或做实例本地缓存。

### 3.3 bootstrap（启动引导）

容器 entrypoint 或 VM 的 SSH setup 阶段执行：

```
1. 读 weights.json（镜像内或从 S3 拉）
2. rclone copy --transfers 8 --checksum 缺失文件 → /root/ComfyUI/models/
3. 校验 sha256/size，失败重试
4. 按 model 配置建软链（替代现在 instance_setup.sh 里的硬编码）
5. 启动 ComfyUI，等 /object_info
6. 输出 ASSET_CHECK（沿用现有 p20 assets 逻辑）
```

`bootstrap.py` 要能在两种模式跑：容器内（entrypoint）和 VM 内（SSH 执行），这样 CompShare 和新平台共用。

### 3.4 Provider 适配层

```python
class Provider(ABC):
    def create(spec: InstanceSpec) -> Instance   # 镜像/GPU/磁盘/区域
    def wait_ready(inst, timeout) -> None
    def ssh(inst, cmd, timeout) -> (rc, out)
    def scp_put/get(...)
    def terminate(inst) -> None
    def price(spec) -> float
```

- `CompShareProvider`：包装现有 `compshare.cs`（已完成 90%）；
- `AliyunProvider`：ECS GPU + `docker run`（最接近现有 VM 模式），或 ACK Job；
- `RunPodProvider`：REST API + Pod；
- `LocalDockerProvider`：本机/单卡调试用。

`run.py` 只依赖 `Provider` 接口；`reports/p2/runtime.json` 记录每个 provider 的镜像 digest 和权重桶。

### 3.5 作业流程改造

现有九步不变，只改三处：

| 步骤 | 现状 | 改造 |
|---|---|---|
| provision | `cs.create(image_id=...)` | `provider.create(spec)`，镜像来自 runtime.json |
| setup | `instance_setup.sh` 硬编码软链 | `bootstrap.py` 按 weights.json 拉权重 + 建链 |
| release | `cs.terminate` | `provider.terminate` |

`job.json` 增加 `runtime` 字段（镜像 digest / weights manifest 版本 / provider），manifest 里记录实际用的 GPU/驱动，保证可追溯。

## 4. 技术难点

按“会不会卡住项目”排序：

### 4.1 跨云出网成本（最容易被忽略）

权重 20GB，如果每次作业都从阿里云 OSS 公网拉到 CompShare，按公网流出 ¥0.5/GB 算，**一次 ¥10**，比 GPU 还贵，而且慢。

**解法**：每家云放一份同 region 的对象存储，跨云同步走一次性离线/低峰复制；bootstrap 只读同 region 内网 endpoint（内网流量免费、带宽 1–10Gbps）。代价是存储成本 ×N（500GB × 3 家 ≈ ¥180/月），但比出网费便宜得多。

### 4.2 FUSE 挂载的权限与 mmap

租用平台多是容器实例，`/dev/fuse` 不一定暴露；safetensors 默认 mmap 读，s3fs/ossfs 的 mmap 支持差，容易出现“加载极慢/直接报错”。

**解法**：主路径用“拷贝到本地盘”，不依赖 FUSE；只有磁盘紧张的机型才用 mount，并强制 `--no-mmap` 加载（ComfyUI 支持 `--disable-mmap`）。

### 4.3 GPU 与精度兼容矩阵

这是**画质/速度**的关键：

| 权重精度 | 需要 | 不支持的卡 | 后果 |
|---|---|---|---|
| fp8 e4m3 | sm89+（4090/L40S/H100） | A100(sm80)、V100 | 报错或反量化，速度掉、显存涨 |
| bf16 | sm80+ | V100/T4 | 报错 |
| int8_convrot | 依赖特定 ComfyUI 内核 | 版本不匹配 | 可能加载失败 |

**解法**：每张卡绑定可用的权重变体（同模型准备 fp8/bf16 两份），registry 的 model 配置按 `gpu_family` 选文件；迁移前跑兼容性矩阵，不要假设“能加载就能跑”。

### 4.4 驱动 / CUDA 版本

镜像里是 cu130 wheel，宿主要求驱动 ≥ 580 左右；租用平台的驱动版本参差。

**解法**：镜像提供 cu126/cu130 两个变体（torch 2.7/2.10），按平台驱动选；启动时 `nvidia-smi` 校验，版本不够直接失败并给出人话原因。

### 4.5 镜像分发与冷启动

20GB 镜像首次拉取 5–15 分钟（取决于 registry 和节点带宽），权重再 20GB。作业如果只有 2 分钟，冷启动占比会非常难看。

**解法**：
- 镜像分层，把“很少变”的 torch/ComfyUI 放底层，节点放上层，重建只推上层；
- 节点侧做镜像缓存（多数平台会 cache）；
- 热权重打进镜像（SeedVR2 3.9GB、Qwen VAE 0.25GB 这类小文件），冷权重走对象存储；
- 长作业优先调度到“已预热”的机器。

### 4.6 平台 API 差异

创建参数（CPU/内存配比、磁盘、区域）、SSH 方式、计费单位、库存模型都不同；CompShare 还有 8903/226604 之类的瞬时错误。

**解法**：Provider 接口里统一 `InstanceSpec`，每个适配器自己处理重试/配额/库存；作业层不感知。

### 4.7 凭据管理

ACR、OSS、各家 API key 不能写进镜像/仓库。

**解法**：构建时用 build secret；运行时用实例 role/临时 token 或环境变量注入；`credentials.env` 保持在仓库外（现在已经是）。

### 4.8 可复现性

commit 和 pip 版本 pin 了，但 base image tag、PyPI 包、registry 都可能漂移。

**解法**：base 用 digest；pip 用 `constraints.txt` + 可选 wheel 缓存；每次作业 manifest 记录镜像 digest + 权重 sha256。

### 4.9 许可

ComfyUI 是 GPL-3.0，镜像对外分发要提供源码；节点许可不一；权重不进镜像是正确的（模型许可各不相同）。

**解法**：私有仓库内部用；对外交付前做许可证清单，源码用“书面提供/仓库链接”满足 GPL。

## 5. 对速度的影响

以现有实测为基线（4090 24G）：

| 环节 | 现状（CompShare 镜像） | 新方案（OCI + 对象存储） | 增量 |
|---|---|---|---|
| 镜像准备 | 0（镜像已缓存） | 首次拉 20GB：5–15 min；之后缓存 | 一次性 |
| 建机 | ~65s | 同量级 | ≈0 |
| 权重就位 | 0（/model 软链） | 拷贝 20GB：20s（10Gbps）～3min（1Gbps） | **+0.5–3 min/作业** |
| ComfyUI 启动 | ~60s | 同量级 | ≈0 |
| 推理（SeedVR2 1024→2048） | 21s | 同卡同镜像 ≈21s | ≈0 |
| 推理（Wan2.2 I2V 640² 81f） | 396s | 同卡 ≈396s；换 H100 更快、A100 慢 | 取决于卡 |
| 单图作业总时长 | 1.4 min | 2–5 min | **+40%～3×** |
| 5 分钟视频作业 | ~7 min | 8–10 min | +15%～40% |

**结论**：推理速度不变；影响在“每次作业的冷启动”，尤其是短作业。缓解手段：热权重进镜像、实例复用/预热池、本地盘缓存、长作业优先。

## 6. 对画质的影响

**理论结论：不变。** 前提是：

1. 权重文件 **sha256 完全一致**（同一份 fp8/bf16 文件，不是重新量化）；
2. ComfyUI + 节点 commit 一致（镜像 pin 住）；
3. 采样参数（steps/cfg/sampler/seed）一致；
4. 精度变体与 GPU 匹配（fp8 卡跑 fp8，bf16 卡跑 bf16）。

**实际会有微小数值差异**，来源：

- 不同 GPU 架构的 cuDNN/cuBLAS kernel 不同，浮点累加顺序不同 → 同 seed 不是 bit-exact；
- fp8 在 Ada/Hopper 上有原生 kernel，在 A100 上要么不支持、要么反量化，结果可能不同；
- 不同 attention 后端（SDPA/xformers/flash）会影响数值，但通常肉眼不可见。

**验收标准（建议）**：

- 同 seed、同参数，在两家平台各跑一条：SSIM ≥ 0.98、PSNR ≥ 35dB，人工抽检无结构差异；
- 视频：抽 3 帧比对，无闪烁/结构变化；
- 若达不到，先怀疑“精度变体选错”或“ComfyUI 版本不一致”，而不是平台。

**真正的画质风险**不在迁移，而在为了省显存/提速去换量化版本（fp16→fp8→int8）。迁移本身不改变权重就不改变画质。

## 7. 实施路线

| 阶段 | 内容 | 产出 | 工作量 | 成本 |
|---|---|---|---|---|
| P0 | Dockerfile 构建 + 私有 ACR + digest | 可复现运行时镜像 | 1–2 天 | 构建机 + 存储 |
| P1 | `weights.json` + `bootstrap.py`（拷贝/校验/软链） | 权重外置，CompShare 也能用 | 2–3 天 | 对象存储 ~¥60/月 |
| P2 | Provider 抽象 + CompShare 适配 | run.py 不再直接依赖 cs | 2 天 | 0 |
| P3 | 第二家 provider（建议阿里云 ECS/ACK）+ POC | 双平台可跑 | 3–5 天 | 一台 GPU 机时 |
| P4 | 质量/速度对比 + 切换默认 + 回滚开关 | 迁移决策依据 | 2 天 | 2 条作业 |

**建议先做 P0+P1**：即使不换平台，权重外置也能立刻解决“镜像 210GB / 权重补不进去”的问题；P3 再决定是否真的迁移。

## 8. 风险与回滚

| 风险 | 触发条件 | 回滚 |
|---|---|---|
| 新平台跑不起来 | 驱动/CUDA/权限 | 保留 CompShare provider，`--provider compshare` 一键切回 |
| 权重下载太慢 | 跨云/小带宽 | 热权重进镜像；或本地缓存盘 |
| 画质不一致 | 精度变体/版本错 | 锁定镜像 digest + 权重 sha256，逐条复验 |
| 成本失控 | 多云存储 + 出网 | 每云一份 + 内网 endpoint；出网告警 |

## 9. 一句话总结

**镜像管代码，对象存储管权重，Provider 管平台。** 三者解耦后，加一家平台只是“加一个适配器 + 同步一份权重”；画质由权重和镜像决定，不会因为换平台变差；速度只会多出每次作业 0.5–3 分钟的权重就位时间，可以用热权重和预热池压下去。
