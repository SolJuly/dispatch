# 镜像存储费实测 + 零存储成本路线（2026-11-09）

> 结论先行：
> 1. **镜像确实收费**：¥0.236/GB/月，每天 01:10 日结。我们之前漏算了 —— 它不产生任何 API 事件，只表现为余额阶跃。
> 2. **动作迁移工作流用到的 27 个节点全是 ComfyUI v0.36.0 官方原生**，不需要任何 custom_node。
> 3. 平台公有的 `0.36.0` 镜像与你 v4 钉的 `3c80da7f` **字节级相同**（`nodes_wan.py` 87711B 完全一致）。

### 1.2 为什么之前漏算

`tools/cost_snapshot.py` 原来只记 `balance` 快照，**不记差值**。镜像费不产生 `create`/`terminate`/`job` 任何事件，所以：

- 按事件统计成本 → 完全看不见
- 按余额曲线看 → 只看到「余额掉了」，不知为何

2026-11-08 的成本分析因此结论错误（当时判定「镜像不计费」）。

### 1.3 单价反推

最干净的测量是 **11-08**：实例数 0（最后一次 terminate 是 11-07 21:10:30），唯一自定义镜像 v4 = 70GB，01:10 扣 −¥0.55。

```
¥0.55 / 70GB = ¥0.00786/GB/天 = ¥0.236/GB/月
```

与 [22-v4镜像构建.md](p21/22-v4镜像构建.md) 记录的「70GB ≈ ¥0.56/天 ≈ ¥17/月」吻合。

### 1.4 关键佐证：11-04 全天零实例活动，仍扣 ¥3.59

```
11-04 全天 create/terminate/job/stop 事件数 = 0
11-04 01:10 扣 -¥3.59 → 反推 457GB
当时 v3 = 210GB → 多出 247GB 是 v1/v2 历史残留未删
```

**只有镜像存储能解释这笔扣费。**

|---|---|---|

| **v4** | **70GB** | **¥16.5** |

## 2. 修复：日结扣费显性化

### 2.1 `tools/cost_snapshot.py`

新增 settle 事件：每次采样时对比上次余额，下降超过 ¥0.005 就写一条。

```json
{"ts":1794071402,"at":"2026-11-08 01:10:02","event":"settle",
 "amount":0.55,"from":9.78,"to":9.23,
 "prev_at":"2026-11-08 01:00:02","gap_s":600,
 "activity":[],"attribution":"idle"}
```

字段说明：

| 字段 | 含义 |
|---|---|
| `amount` | 本段余额下降额 |
| `attribution` | `idle`（期间无活动→只可能是日结）/ `job`（期间有作业）|
| `activity` | 期间出现过的事件类型 |
| `gap_s` | 距上次采样秒数；超过 3 小时打 `gap: true` |

改进点：
- `_last_balance()` 从文件尾部倒读，账本上万行也不整文件入内存
- 余额 `round(4)`，避免 `8.459999999999999` 这种浮点尾巴
- `--no-settle` 保留旧行为，`--dry-run` 只打印

### 2.2 `scripts/backfill_settle.py`

把历史 balance 差值回填成 settle 事件，一次性迁移。

```
$ python3 scripts/backfill_settle.py
账本 4004 行，检出 369 笔余额下降，合计 ¥57.93
  归因=job  ¥20.72（含作业开销）
  归因=idle ¥37.21（无活动，只能日结/存储费）
```

幂等：按 `(at, event)` 去重，跑两次不重复写。

> 已执行 `--apply`，账本从 4004 行 → 4373 行（+369 settle）。原文件备份为 `ledger.jsonl.bak`。

### 2.3 idle 归因的分布

297 笔 `idle`、合计 ¥37.21，按小时分布：

| 时段 | idle 金额 |
|---|---|
| 01 时 | **¥13.37**（日结主力）|
| 22 时 | ¥5.98 |
| 17 时 | ¥2.68 |
| 02 时 | ¥2.44 |

**01 时占 idle 总额的 36%** —— 与「01:10 日结」完全吻合，验证了归因逻辑。

## 4. 不止动作迁移：全 54 个工作流的覆盖分析

### 4.1 `3c80da7f` 就是 `v0.36.0`

```
$ curl .../comfyui_version.py@3c80da7f  →  __version__ = "0.36.0"
$ curl .../comfyui_version.py@v0.36.0   →  __version__ = "0.36.0"
```

**同一个版本。** 所以「用平台 0.36.0 替代 v4」在 ComfyUI 核心层面是零差异替换 ——
差异只在 custom_nodes。

### 4.2 两个版本的官方节点集

抓取 `v0.36.0` 与 `v0.43.0` 各自全部 142 个 `comfy_extras/*.py` + `nodes.py`：

| 版本 | 官方节点名 |
|---|---|
| v0.36.0 | **777** |
| v0.43.0 | **787** |

v0.43 新增 12 个：

```
BranchNode  Flux3LayoutPrompt  GetAudioLatentSize  GetLatentSize
ImageSDRToHDR  LatentOperationBlend  ModelMergeMOSSImage  PadImageNode
QwenImage21Cache  ReferenceMultiLatent  TextEncodeQwenImage21  useCustomUp
```

v0.43 移除 2 个：`CreateCameraInfo`、`orbit`。

**已检查：没有任何工作流用到被移除的这两个节点，升级安全。**

### 4.3 关键发现：两个"第三方" Qwen 节点其实是官方的

`QwenImage21Cache` / `TextEncodeQwenImage21` 之前在 v0.36.0 里判定为第三方 —— 错。

## 5. 四条路线

| 路线 | 镜像存储 | 侧载 | 起机 | 可跑 |
|---|---|---|---|---|
| **1. 现状 v4** | **¥16.5/月** | ¥0 | 105s | 54/54 |
| **2. v0.43.0 裸跑** | **¥0** | ¥0 | 105-117s | **50/54** |
| **3. v0.43.0 + 侧载 8.9MB** | **¥0** | **¥0.017/作业** | +0.5min | **52/54**（全 verified）|
| **4. v0.43.0 + 侧载 411MB** | **¥0** | ¥0.786/作业 | +21.9min | 54/54 |

侧载成本按实测 320 KB/s × ¥2.15/h 算。

**盈亏平衡（相对 ¥16.5/月）：**

```
路线 2：无条件更省
路线 3：¥16.5 / ¥0.017 = 970 作业/月（约 32/天）才打平 → 几乎总是更省
路线 4：¥16.5 / ¥0.786 = 21 作业/月（约 0.7/天）→ 跑得多就不划算
```

**结论：路线 3 是最优解。** 零存储费，全 verified 工作流可跑，每作业只多 ¥0.017。

| 镜像存储费是否按小时更细粒度计 | ⚠️ 只观察到每天一次阶跃 |

### 6.1 最大风险：v0.43.0 的运行时版本

v4 镜像钉的是 `torch 2.8.0+cu128`。如果平台 v0.43.0 镜像是 `torch 2.10+cu130`（v3 就是），

那么自定义节点的 ABI 可能不兼容 —— 这正是 v3 → v4 迁移时踩的坑（[22-v4镜像构建.md](22-v4镜像构建.md) §2 第 1 条：KJNodes 报
`comfy_api.latest._io has no attribute 'Autogrow'`）。

**所以侧载 8.9MB 之前，必须先确认 v0.43.0 的 torch 版本。**

### 6.2 建议的验证顺序

1. **先裸跑**（¥0.22）：v0.43.0 + 动作迁移。验证官方节点链路能否跑通。
2. **再验证 LTX/Wan2.2**（各 ¥0.2-0.3）：确认不是只有动作迁移能跑。
3. **最后才侧载**（如需 SeedVR2）：先查 torch 版本再决定。

**如果第 1 步就失败**，说明平台镜像的运行时环境和 v4 差太多，路线 2/3/4 全部作废，继续用 v4。
