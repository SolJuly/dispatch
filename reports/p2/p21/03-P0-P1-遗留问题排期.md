## 2. 重分级说明

1. **N3「写 API」从 P2 升到 P0**：P2.0 阶段 UI 是纯读的，所以写 API 只是"锦上添花"；P2.1 的三项验收（结果预览下载、原图对比、蒙版重绘）全部以"用户提交作业"为前提，没有写接口就没有 5.2/5.3 的产品形态。这不是新增范围，而是原清单里的 P2 项被 P2.1 拉成了关键路径。
2. **N4「文件服务 systemd 化」从 P0 降为 P1**：502 的根因是"交付物依赖容器内临时进程"，而不是"没接 systemd"。改用 nginx 静态目录后该风险已消除；systemd 化本身在容器内做不到（D-Bus 不可达），只能作为部署机的运维动作。
3. **N6 判为"半阻塞"**：不是架构问题，但 `--need` 的静默降级会在接入 SDXL 当天以"资产缺失"的假象出现，浪费半天排查时间，所以提前修。

## 4. 对 P2.1 的阻塞结论

- **硬阻塞 3 项**：N1（基线）、N2（统计口径）、N3（写 API）。三项都在 M0/M1 前 3 天内解决，不影响 11-10 的 5.1 出口。
- **软阻塞 1 项**：N6，M1 第一天顺手修。
- **不阻塞 9 项**：按表内窗口推进，其中 N5/N9/N10 放到 M4 统一收口，避免在 5.1–5.3 开发期制造无关 diff。

## 5. 需要决策的两件事

1. **N2 的失败作业边界**：失败作业写到 `reports/p1/jobs/`（与成功作业同目录、同 schema，只是 `state=FAILED*`）还是单独 `reports/p1/jobs-failed/`？建议**同目录**，`jobctl` 按 state 过滤，避免两套目录逻辑。
2. **N4 的长期归属**：容器内不做 systemd，产物发布改为「作业完成 → 复制到 `share/` → nginx 静态」；`cs-files` 服务只在部署机维护。建议**接受这个降级**，不再追容器内 systemd。
