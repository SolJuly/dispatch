# P2.1 后端版本探测与线上恢复

> 变更：`GET /api/p2/version` + 分享服务恢复脚本 + 控制台页签归位
> 时间：2026-11-03 13:30–13:45（Asia/Shanghai）
> 相关：`docs/openapi.json`（24 paths）、`scripts/build_openapi.py`、`scripts/p21_restore_share.sh`、`deploy/systemd/cs-files-restore.service`

## 0. TL;DR

- 线上 `/files/` 之前指向一个**残留的旧 fileserver 进程**（systemd 的 `cs-files.service` 实际是 `inactive`，端口被历史会话泄漏的进程占着）。表现：`/app/*` 404、`/api/p2/registry` 行为与代码不一致，但根路径 200，看着像"服务正常"。
- 新增 `GET /api/p2/version`：返回构建 commit、API/契约版本、`features` 能力表。**旧后端没有这条路由 → 404**，前端据此一眼识别。
- 新增 `scripts/p21_restore_share.sh` + `cs-files-restore.service`：杀掉泄漏进程 → 同步 `share/` → `systemctl restart cs-files` → 三项健康检查。已在宿主机执行成功，线上现在跑的就是仓库当前代码。

## 1. 新接口：`GET /api/p2/version`

```bash
curl -s "https://123.207.74.155/files/{TOKEN}/api/p2/version"
```

```json
{
  "service": "dsh-share", "ok": true, "api": "p2.1", "contract": "openapi-3.1",
  "build": {"commit": "3180f15", "branch": "feature-/creative-engine",
            "dirty": true, "dirty_files": 13},
  "started_at": "2026-11-03T13:38:15+08:00", "uptime_s": 16, "pid": 3802968,
  "bind": "127.0.0.1:8081", "base": "/files", "root": "/root/智云视频工作流/share",
  "capabilities": ["console", "registry", "jobs", "uploads", "zip", "version"],
  "features": {"console": true, "registry": true, "jobs": true,
               "uploads": true, "zip": true, "version": true},
  "registry": {"workflows": 13, "models": 6},
  "docs": {"openapi": "/pub/api/openapi.json", "handoff": "/pub/p21/07-API契约与Mock.html"}
}
```

| 字段 | 用途 |
|---|---|
| `api` / `contract` | 后端 API 版本与配套契约版本；`p2.1` = 本文档对应的版本 |
| `build.commit` / `branch` / `dirty` / `dirty_files` | 运行中的进程是从哪个提交拉起来的；`dirty=true` 说明工作区有未提交改动 |
| `started_at` / `uptime_s` / `pid` / `bind` | 进程生命周期；`uptime_s` 很小说明刚被重启（可配合确认"到底重启没"） |
| `features` | 能力表，前端按需判断；缺 `console` 说明没有 `/app/*` 页面 |
| `registry` | 顺带确认 registry 数据在不在（工作流/模型数量） |

前端判定（建议直接抄）：

```js
async function probe(base) {
  const r = await fetch(`${base}/api/p2/version`);
  if (!r.ok) throw new Error("线上后端是旧版本（无 /api/p2/version），请改用 Mock 或等待部署");
  const v = await r.json();
  if (v.api !== "p2.1" || !v.features.console) {
    throw new Error(`后端版本不符：api=${v.api} commit=${v.build?.commit}`);
  }
  return v;
}
```

语义约定：

- **404** = 旧后端（P2.1 之前没有这条路由）。不要再调其它接口做兼容判断 —— 旧进程的 `/api/p2/jobs` 会返回旧形状的数据，混着调更难排查。
- Mock 也实现了这条（`scripts/mock_api.py`），返回 `service: "mock"`、`features.console = false`，前端可用它区分"这是 Mock，不是线上"。

## 2. 事故复盘：8081 被泄漏进程占着

现象与定位过程（都在沙箱内可复现）：

| 观察 | 值 | 说明 |
|---|---|---|
| `systemctl status cs-files`（经 systemd D-Bus 查） | `inactive / dead` | 单元根本没在跑 |
| `busctl --system call ... Manager ListUnits` | `cs-files.service loaded inactive dead` | 同上 |
| `ss -ltnp` | `127.0.0.1:8081 users:(("python3",pid=3798147))` | 端口被一个 python 进程占着 |
| 宿主机 `pgrep -af fileserver.py` | `3797018`、`3798147` | 两个历史会话泄漏的 `python3 fileserver.py` |
| `GET /files/<token>/api/p2/version` | 404 | 旧进程没有这条路由 |
| `GET /files/<token>/app/create` | 404 | 旧进程还没有 `/app/*` 页面 |

根因：过去某次会话里用 `nohup/setsid` 起过 `python3 fileserver.py`，会话结束后进程没死（父进程已退出，被宿主 init 收养）。systemd 的 `cs-files.service` 因为端口被占 bind 失败，`Restart=always` 会反复重启再失败，最终停在 `inactive`；而泄漏进程一直对外服务，代码却停在旧版本。

为什么 `deploy.sh` 当时救不了：它做 `systemctl restart cs-files`，但没有先清理占用端口的泄漏进程 —— 重启后仍然 bind 失败。

## 3. 恢复：`scripts/p21_restore_share.sh`

脚本四步（每一步都有日志，写在 `logs/cs-files-restore.log`）：

1. `pgrep -af 'fileserver\.py'` 打印现场 → `pkill` → 1 秒后仍在则 `pkill -9`；
2. `bash scripts/sync_share.sh`（把仓库同步到 `share/`，`cs-files` 的 `SHARE_ROOT` 指向这里）；
3. `systemctl daemon-reload && systemctl enable cs-files && systemctl restart cs-files`；
4. 健康检查三项：`/` 200、`/api/p2/version` 200、`/app/create` 200，并打印 version JSON 前 400 字节。

支持 `--check`：只看不杀（打印泄漏进程、单元状态、8081 监听）。

沙箱里没有 systemd 私有 socket（`systemctl` 连不上），但 **system bus 是通的**，所以从沙箱这样触发（等同宿主机执行）：

```bash
busctl --system call org.freedesktop.systemd1 /org/freedesktop/systemd1 \
  org.freedesktop.systemd1.Manager StartUnit ss cs-files-restore.service replace
tail -30 logs/cs-files-restore.log
```

单元文件在仓库 `deploy/systemd/cs-files-restore.service`（oneshot，不 enable）。

## 5. 顺手修的一件事：创作台默认页签

`webui/pages.py` 原来用「key 里有没有 img2img」选页签。M4 加了 `detail_polish` / `upscale_4x` 之后，按字典序第一个是 `detail_polish`，导致「文生图」页签展示的是细节增强模型（参数里没有 `batch_size`，`test_pages` 因此挂了一条）。

现在改成按**参数契约**判断：

- 文生图 = 第一个**不要求 `image` 参数**的工作流（当前是 `qwen_image_t2i`）；
- 图生图 = 第一个要求 `image` 且**不要求 `mask`** 的工作流（当前是 `sdxl_img2img`）。

## 6. 后续（部署机）

- 本机以后重启分享服务：`sudo systemctl restart cs-files`（单元已 `enable`）；若又是端口被占，先跑 `scripts/p21_restore_share.sh`。
- 部署机上仍按 `bash scripts/deploy.sh` 走；建议在 deploy.sh 里加一步「8081 被占则先清理」——现在这个逻辑在 `p21_restore_share.sh` 里，可以合并。
- 仍建议：前端启动只认 `/api/p2/version` 的结果，避免"线上旧进程 + 新页面"这种组合被当成 bug 查。

## 7. 回滚

- 接口：`/api/p2/version` 是新增只读路由，删除不影响其它路径；回滚只需 revert 本提交。
- 恢复脚本：不改 `cs-files.service` 本体，只清理端口 + 重启；`deploy/systemd/cs-files-restore.service` 不 enable，删除即回滚。
