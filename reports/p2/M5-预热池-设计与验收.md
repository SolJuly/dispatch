# M5 预热池 · 设计与验收

> 分支 `feature/warm-pool`（基于 `v0.3-p2-core`）· 2026-11-01 · 实扣 ¥0.06（V100S 1 台，测试后已销毁）
> **结论先说**：机制做完了、能用；但实测**省的不是 90 秒，是 15–20 秒**。
> 它的真正价值是**绕开无货（226604）**，不是提速。建议保留为可选模式（默认池 1 台），不做大池。

---

## 1. 设计假设 vs 实测

原假设（P1 期数据）：停机的实例 `start` ≈ **12s**，而 `create` ≈ 70–85s → 能省 60–70s。

实测（V100S，已烘焙 media 镜像，停机 3 分钟后启动，两次取样）：

| 指标 | 第 1 次 | 第 2 次 | 说明 |
|---|---|---|---|
| `start` → Running | **62.3s** | **57.6s** | 平台停→启约 60s，与新建 65s 基本持平 |
| `start` → ComfyUI 8188 就绪 | **91.5s** | **91.2s** | 含 VM 引导 + entrypoint 拉起 ComfyUI |
| 对照：`create` → 就绪（M1 基准） | 105–117s | — | media 镜像 105/109.5/112s |

**净收益：105–117s → 91s，省 15–25s（约 18%）。**

为什么差这么多：P1 记的「12s」是接口层面的快速返回，不是 VM 真正进入 Running 的时间。这个错误假设在本次实测中被纠正——**平台侧的 stop→start 和 create 一样，都要重新调度 + 挂盘 + 引导系统**。

## 2. 真正价值：可用性，不是速度

| 维度 | 预热池 | 说明 |
|---|---|---|
| **绕开无货** | ✅ | 今天 4090 现货反复在 0/68 之间跳；池内实例是已建好的，**没货也能跑** |
| 跳过 setup | ✅ | 镜像自带 marker，`instance_setup.sh` 走快路径（省 20–40s） |
| 跳过 ComfyUI 冷启动 | ✅（部分） | 磁盘已预热，但 entrypoint 仍要重启进程 |
| 提速 | ⚠️ 仅 15–25s | 不是数量级改进 |
| 代价 | 占配额 | 账户 5 台，池 1 台 = 并发上限降到 4 |
| 代价 | 停机 ≠ 零风险 | 长期停机可能漂移（已加 `stale_hours=24` 回收） |

## 3. 实现

```
tools/p2/pool.py          池管理（ensure/acquire/release/reconcile/drain/status）
reports/p2/pool.json      池状态（uid/state/job_id/last_used/cloud_state）
run.py --from-pool        provision 优先 acquire，release 时停机回池
batchctl run --from-pool  透传给调度器，每个 worker 都带该标志
```

关键约束（都已实现）：

| 约束 | 实现 |
|---|---|
| 配额保护 | `max_total`（默认 4）；`ensure` 超限只补到剩余槽位 |
| 复用顺序 | 按 `last_used` 最久未用优先（LRU） |
| 就绪判定 | start → Running → sshd → **8188 `/system_stats`** 才交活 |
| 归还 | 默认**停机保留**，不销毁 |
| 漂移回收 | `reconcile()`：云端消失→摘除；外部停机→纠正 idle；>24h 未用→销毁 |
| 卡规 | `GPU_SPEC` 统一到 `p2/config.py`（V100S=10C/64G，写死 16C 会被 8333 拒） |

## 4. 验收

| 项 | 结果 |
|---|---|
| 单测（FakeCS） | **8 条全绿**：创建/幂等/配额/max_total/LRU 取用/归还/reconcile 三种场景/drain |
| 全量单测 | **42 条全绿**（跑两遍无抖动） |
| 真机 `ensure --size 1` | 65s → Running，6s → Stopped，入池 idle ✅ |
| 真机 `acquire` ×2 | 91.5s / 91.2s 到 ComfyUI 就绪 ✅ |
| 真机 `release` | 6s 停机回池，状态 idle ✅ |
| 真机 `drain --terminate` | 实例已销毁，0 残留 ✅ |

## 5. 建议

1. **保留为可选模式**，不进默认路径：`pool ensure --size 1` + `batchctl run --from-pool`。
2. **池大小 1**，不要更大：每多 1 台就少 1 个并发槽，而速度收益只有 20s。
3. **真正的提速方向不在池**：要 90s→30s，得改的是「ComfyUI entrypoint 启动耗时」（预加载模型/懒加载节点），不是调度层。
4. 若 4090 长期无货，池的价值会凸显——它可以让你在无货时仍然跑得动，这是 create 路径做不到的。

## 6. 未做

- 池的自愈（实例被平台回收后自动补位）→ 由 cron 跑 `pool reconcile` 即可，未接 cron。
- 多卡型池（4090/3090/V100S 混合）→ 当前单卡型。
- 池内实例的模型热加载（把常用 ckpt 预读进 page cache）→ 属于镜像侧优化。
