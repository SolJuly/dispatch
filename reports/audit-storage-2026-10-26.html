① SSH 断开后，远程任务还会继续吗

做法：远端放一个 1 秒写一行的计数循环，本地用 ssh 起任务，4 秒后直接 kill 掉本地 ssh 进程（等价于平板关页面、网络断、笔记本合盖），过 25 秒用新连接数行数。行数还在涨 = 任务活着。

组启动方式断开时行数25 秒后进程 PPID结论
A前台裸跑（非交互 ssh，不分配 tty）73941继续跑
Bnohup … &42621继续跑
Csetsid nohup … &（csctl --detach 的写法）11311继续跑
D前台裸跑 + ssh -tt 强制分配 tty55—被杀
机理结论：决定生死的是「有没有 tty」，不是有没有 nohup。
断开 SSH 时，sshd 只会向已分配 tty 的会话发 SIGHUP。非交互 ssh host "命令" 根本不建 tty，所以前台裸跑也能活；而 ssh -t / 交互登录里起的前台进程会被 SIGHUP 打死。
nohup、setsid 的作用是"即使有 tty 也不怕被杀"——三个都活，说明多层冗余是有意义的。

最硬的证据：ComfyUI 本身就不挂在 SSH 上

bash /start.d/comfyui.sh 的父进程是 PID 1，它拉起 python main.py --listen 0.0.0.0 --port 8188。这是容器 entrypoint 启的，跟你的 SSH 会话毫无关系——所以 SSH 断了、平板关了，出图/出片照跑。同理 Jupyter(:8888)、FileBrowser(:8889) 也都是 PID 1 的孩子。

实操建议：长任务一律走 csctl ssh <id> --detach --log /root/job.log，或干脆直接打 ComfyUI 的 HTTP 接口（我们所有生产脚本都是这么干的）。

本轮最重要的新发现：save-image 会让实例里新起的进程失去 GPU。
23:38:26 提交制作镜像 → 23:40:49 镜像可用（30GB，用时 2 分 23 秒）→ 23:42 发现 nvidia-smi 报 Failed to initialize NVML: Unknown Error，torch.cuda.is_available() 变 False。
但同一时刻 ComfyUI 自己的 /system_stats 仍正常报 cuda:0 Tesla V100S-PCIE-32GB——说明 GPU 没掉，是"新进程无法初始化 NVML"，已持有 CUDA context 的老进程不受影响。
恢复方式：stop → start（实测 23:46 完全恢复，torch.cuda True、NVML yes）。reboot 不够稳，直接 stop/start 最干净。
另一个坑（本轮实测）：SSH 会话里 torch.cuda.is_available() 经常是 False。 /dev/nvidia* 都在、libcuda.so.1/libnvidia-ml.so.1 都能 ctypes 加载，但 torch 仍报 "Can't initialize NVML"。
含义：不要用 SSH 里直接跑 torch 脚本来做推理，会静默掉到 CPU。一律打 ComfyUI 的 :8188 HTTP 接口（/prompt、/system_stats），那是服务端视角，永远准。

⑤ 这轮踩到并已修掉的东西

  • SSH 里 pkill -f t1_loop.sh 把自己杀了 —— 远端命令行本身含这个字符串，pkill 匹配到自己。改成 pkill -f '^bash /root/t1_loop.sh'。
