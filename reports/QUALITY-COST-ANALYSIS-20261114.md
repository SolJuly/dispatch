## 零、先说结论

我把 66 张历史产出图、12 个视频全部验证了一遍。**结论和你的判断有出入**：

| 你的判断 | 实测 |
|---|---|
| 「文生图没一个能用」 | ❌ **质量其实不差**（下面有实图），问题是**你根本没看到好图** |
| 「h3 质量非常差」 | ❌ **画质正常**（864×480，构图/一致性/光照都对），问题是**分辨率低 + 你看不到全貌** |

## 二、那为什么你觉得「没一个能用」

### 根因 1：**你看到的可能不是这些图**

`/pub/` 返回 401，视频**根本加载不出来**。你能看到的只是：
- 列表页的缩略图（如果 ffmpeg 抽帧成功）
- 或者一直转圈的加载状态

**你以为「没产出好图」，实际上好图在服务器上，只是传不到你眼前。**

### 根因 2：**默认参数不等于最佳效果**

以 `zimage_turbo_t2i` 为例：

```json
"steps": 8,        // 蒸馏模型，8 步就够，但细节不如 20 步
"cfg": 1.0,        // 蒸馏模型标准值，但创意幅度受限
"sampler": "res_multistep"
```

**8 步 = 快（3 秒出图），但质量是「够用」不是「惊艳」。** 想要更好要上 `t2i_hq`（14 节点，多一层细化）。

**你没选对工作流，不是工作流不行。**

### 根因 3：**480p 视频按 1080p 标准看**

H3 输出 864×480。**这个分辨率在手机上看还可以，在平板/显示器上就是糊的。**

但这是**模型能力上限**（121 帧 14B 模型，4090 显存限制），不是配置错误。想要 1080p，得换 Wan 2.2 或 LTX 2.5——**而它们的权重恰好缺失**。

## 三、成本真相：0.044 元/秒，但 71% 在空转

### 实测一次 h3 作业

```
总耗时：385 秒
花费：  385/3600 × 2.15 = 0.230 元
成片：  5.17 秒
折算：  0.044 元/秒成片   ← 你感知的「0.1 元/秒」
```

### 385 秒去哪了

| 阶段 | 耗时 | 占比 |
|---|---|---|
| 建机 + 装环境 | 120s | **31%** |
| ComfyUI 启动 + 加载 14GB 模型 | 110s | **29%** |
| **实际推理** | **110s** | **29%** |
| 拉取 + 校验 + 销毁 | 45s | 12% |

**只有 29% 的时间在真正生成内容。**

### 如果热机复用

```
环境已就绪：110s 推理 + 45s 收尾 = 155s
费用：155/3600 × 2.15 = 0.093 元
省 60%
```

**你的 `tools/p2/pool.py` 预热池就是干这个的，但没启用。**

## 五、真正该修的 5 件事

### P0-1 · 修视频加载（你「看不到」的根因）

| 问题 | 修法 |
|---|---|
| `/pub/` 返回 401 | nginx 加 `auth_basic off`（或前端改用 `/files/<token>/pub/`） |
| 不支持 Range | `fileserver._pub_file` 改成流式 + `Accept-Ranges: bytes` |
| 全量读内存 | 改 `shutil.copyfileobj` 分块发送 |

**效果**：视频能边下边播、能拖进度条、首帧秒出。

### P0-2 · 预热池启用（省 60% 成本）

`tools/p2/pool.py` 已实现但没开。启用后：
- 同一批任务复用实例
- 省掉 120s 建机 + 110s 加载模型
- **成本从 0.23 元/次降到 0.09 元/次**

### P0-3 · 工作流分级 + 推荐标记

给每个工作流加两个字段：

```json
{
  "quality_tier": "commercial",   // commercial / draft / experimental
  "cost_hint": "0.23元/次 @ 480p 5s"
}
```

**UI 上明确告诉用户**：
- 🌟 商业级：SDXL 1536、FLUX、Qwen-Image
- ⚡ 快速草稿：ZImage 8步
- 🎬 视频（480p，非高清）

**预期管理是产品的一部分。**

### P1-1 · 权重下载（让 LTX/Wan VACE 真正可用）

缺失清单 152 行，其中 LTX 全系 50 行。

**要么下载权重，要么明确淘汰。** 不要留着「点了报错」的选项。

### P1-2 · 分辨率提升路径

| 当前 | 上限 | 想要更高 |
|---|---|---|
| H3 864×480 | 模型上限 | 换 Wan 2.2（需权重） |
| ZImage 1024 | 可上 1536 | 改 `width/height` 参数 |
| SDXL 1536 | 可上 2048 | 显存允许 |

## 七、下一步建议（按你的目标「开箱即用」）

### 第一周：让它「能用」

```
1. 修 /pub/ 加载（Range + 流式）        ← 你能看到东西
2. 启用预热池                            ← 成本降 60%
3. 工作流加 quality_tier + cost_hint     ← 用户知道点哪个
```

### 第二周：让它「好用」

```
4. 权重下载决策（LTX 50 行要不要下）     ← 决定淘汰还是补全
5. 分辨率提升（ZImage 上 1536）          ← 质量提升
6. 前端重做（推倒重来）                   ← 体验
```

### 关键判断

**你说「宁愿镜像贵点、工作流少点，质量要好」——这个方向是对的。**

具体落地：
- 镜像贵不贵**不影响单次成本**（镜像是固定 ¥16.5/月存储费，起机不额外收）
- **真正影响单次成本的是「空转时间」**，不是镜像
- 所以：**保留 v4 镜像（贵但含全部环境）+ 启用预热池 = 质量不掉、成本降 60%**
