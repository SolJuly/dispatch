# 花费闸：日预算 + 余额安全线

日期：2026-11-12
触发：`autostart` 补位路径一道钱上的闸都没有。

---

## 问题

系统里**只有调度器**有预算熔断（`scheduler.py` 的 `daily_budget`），
而调度器是死代码（从 queue.db 领活，没人往里放活）。

真跑作业的 `autostart` 补位路径：

```
补位能连续拉起作业 → 每个建机 ¥2.15/h → 一天 ¥200+ 无人拦
```

当时的实际情况：余额 ¥17.92，四台并发满负荷 = ¥206/天 → **4 小时烧光**。

不是理论风险 —— 一次参数填错导致的连环重试就够了。

---

## 三道闸，各防各的

```
① 日预算    今天花了多少 → 超了停补位
② 余额线    账户还剩多少 → 低于安全线不建新机
③ 单作业    这一个预估多少 → 超了拒绝（run.py 里早有）
```

必须三道都有，因为防的不是同一件事：

- 只有 ① → 余额剩 ¥3 时照样建机，跑到一半没钱，留下孤儿实例
- 只有 ② → 余额 ¥17 能被四台并发在 4 小时内烧光
- 只有 ③ → 拦不住"十个作业各花 ¥1"

阈值：日上限 **¥8**（比历史单日最高略高）、余额线 **¥5**（`run.py` 自己
也有 `bal < 5` 的下限，两边对齐）。可用 `P1_DAILY_CAP` / `P1_BALANCE_FLOOR` 覆盖。

---

## 为什么是「停补位」而不是「杀在跑的」

杀掉正在跑的作业 = 白烧那部分 GPU 时间（不退）。补位是**入口**，
在入口拦住的成本是零。

所以熔断只关入口，让在跑的跑完。`run.py` 自己的建机闸仍在，双保险。

---

## 核心发现：账本会低估 ¥0.55

这是做这件事过程中挖出来的真问题。

实测 2026-11-12 01:00：

```
账本最后一条 balance:  01:00:03  ¥17.92
平台实时余额:                    ¥17.37
                                  差 ¥0.55，账本里一条记录都没有
```

根因：账本是**本地采样**（`csctl settle` 按周期回填），采样之间就是黑洞。
采得越稀疏，低估越多。

后果：如果熔断只读账本，它看到 ¥1.20 而真实是 ¥1.75。上限 ¥8 实际会烧到
**¥12 才熔断**。

### 修法：用余额差校正

```
当日第一条 balance 采样  −  当前余额  =  真实花了多少
```

与账本取 **max**：

- 两者都在涨，取大的（宁可早熔断）
- 充值导致余额上升时，余额差是负数 → 钳到 0，不会算成负花费
- 当天还没采样过 balance → 退回账本数（**不能拿当前余额当基线**，
  那会算出"已花 0"，永远不熔断）

实测效果：

```
01:09  今日已花 ¥1.75 / 上限 ¥8.00 · [账本 ¥1.75] · 余额 ¥17.37
```

账本此刻还停在 ¥1.20，校正后拿到 ¥1.75 —— 和真实一致。

## 一个反直觉的选择：读不到余额时**放行**

```python
if bal is None:
    return True, "读不到余额（按放行处理）"
```

理由：这是**最后兜底闸**，不是主闸。网络抖一下把所有作业堵死，
代价比偶尔多花几毛钱大得多。

但必须**说出来** —— 静默放行会让人以为查过了。

## 残余风险

1. **`P1_DAILY_CAP=8` 对现在的余额偏高**。¥8/天 × 一个月 = ¥240。
   建议按实际节奏调，或者改成"余额百分比"（如余额的 20%）。
2. **账本仍会低估**。校正依赖 `balance()` API 能通；API 挂了就退回账本数，
   低估回来。要根治得让 `csctl settle` 采样更密（现在 10 分钟一次）。
3. **单作业闸在 `run.py` 里，那条路径我这次没动**。它的余额闸是
   `bal < 5`，比 `P1_BALANCE_FLOOR` 硬编码 —— 将来改一处得记得另一处。
