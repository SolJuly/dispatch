## 2. `FAILED_VERIFY` 的处理：不重试 + 返回视频 + 告知情况

这是你第 1 条拍板，也是最需要设计的一块。

### 2.1 先说现在的实际情况（我核实过）

好消息：**产物在你看到失败之前就已经在本地了。**

九步的顺序是：`fetch`（拉回产物）→ `verify`（复验）→ `persist`（写 manifest）→ `release`

所以 `verify` 失败时，`artifacts/` 目录里**文件已经存在**。

坏消息：**`verify` 抛异常后，`persist` 和 `release` 都不会执行。**

```python
def _execute(job_id, job, opts, ctx, start_at="provision"):
    for name in STEP_ORDER[...]:
        _do_step(name, ...)      # ← verify 在这里抛 RunError，整个循环跳出
```

后果：
- ❌ 没有 `manifest.json` → 没有 sha256、没有成本记录
- ❌ 不会发布到 `/pub/` → 前端拿到的 URL 可能 404
- ❌ `release` 不执行 → **实例不会被销毁**（这个靠信号兜底和清理兜）
- ✅ 但 `artifacts/` 里的文件在，UI 的详情页也确实会显示它们
  （实测 `renderResult()` 里 `<div class="media">` 的判断独立于失败状态）

### 2.2 要改成什么样

**核心思路：把 `verify` 的失败从"硬失败"改成"软失败"。**

```
现在的语义：
  verify PASS  → 继续 persist → DONE
  verify FAIL  → FAILED_VERIFY（终结，产物不落 manifest、不发布）

改后的语义：
  verify PASS        → 继续 persist → DONE
  verify FAIL        → 仍然 persist（照常写 manifest + 发布）
                       → 状态标成 DONE_WITH_ISSUES（新状态）
                       → 产物可下载、可播放
                       → 记录"哪几项没过、为什么"
```

### 2.3 新增状态 `DONE_WITH_ISSUES`

为什么不是留在 `FAILED_VERIFY`：那是个"终点"，语义是"这条废了"。
但实际是"产物能用，只是有毛病" —— 这两种状态对用户的含义完全不同：

| 状态 | 用户看到 | 能不能用产物 |
|---|---|---|
| `FAILED_VERIFY`（现状） | 「复验失败」+ 一个红条 | 技术上能下载，但 UI 没说清 |
| `DONE_WITH_ISSUES`（新增） | 「完成，但有 2 项检查没过」+ 明确的清单 | ✅ 明确可用 |

**`DONE_WITH_ISSUES` 仍然是终态**（和 `DONE`/`FAILED`/`ABORTED` 并列），
但**不是失败** —— 它不进 `ORDER_FAIL()` 那个红条分支。

### 2.4 "告知该工作流情况"具体告知什么

你说「返回视频并告知该工作流情况」，我理解成三层信息，都要给：

#### 第一层：这条作业哪里没过

```
复验未通过的项（verify.py 的七项）：
  · freeze   冻结检测：静止帧占比 34% > 阈值 20%
  · params   参数回读：seed 期望 1646959504，实际 42
```

现有 `verify.py` 已经产出这个结构（`res["artifacts"][*]["failed"]`），只是没落盘。

#### 第二层：质量分（这一层已经有了）

上一轮做的质量评分正好用在这里：

```
质量：🔴 D 32.0 分
  · 边缘能量 0.56 < 0.8：画面糊/抽象/缺细节
  · 帧差 0.10 < 0.6：画面基本没动
```

#### 第三层：**这个工作流的历史情况**（这是你说的"该工作流情况"）

我理解你要的是"这条工作流一直这样，还是偶发"。这个数据现在没有，要新建：

```sql
-- 按工作流聚合的历史统计
SELECT workflow_key,
       COUNT(*)                                    AS total,
       SUM(CASE WHEN ok THEN 1 ELSE 0 END)         AS passed,
       AVG(quality_overall)                        AS avg_quality,
       常见的 failed 项 + 出现次数
FROM job_history
GROUP BY workflow_key
```

UI 上显示成：

```
工作流 qwen_image_t2i 最近 20 条：
  ✅ 18 条正常  ⚠️ 2 条有检查未过
  最常见问题：freeze（2 次）
  平均质量：81.3 分
```

**这一层是新东西**，要新增一张聚合表。工作量约 0.5 天。

### 2.5 实现要点

```python
def step_verify(job, opts, ctx, arts):
    res = verify_mod.verify_job(...)
    res["quality"] = _score_quality(job, res, arts)   # 已有
    
    if res["verdict"] != "PASS":
        # 不再抛 RunError。标记为软失败，继续往下走。
        ctx["verify_issues"] = [f"{a['file']}: {','.join(a['failed'])}"
                                for a in res["artifacts"] if a["verdict"] != "PASS"]
        job_soft_fail = True
    return res

def step_persist(job, opts, ctx, res, arts):
    manifest = {...}
    if ctx.get("verify_issues"):
        manifest["verdict"] = "WARN"           # 不是 PASS，也不是 FAIL
        manifest["issues"] = ctx["verify_issues"]
    ...
    
# 收尾时
final = state.DONE_WITH_ISSUES if ctx.get("verify_issues") else state.DONE
state.transition(job_id, final, reason=...)
```

**关键约束（已核实代码，是安全点不是风险）：**

`tools/p20/p20ctl.py:460` 的 `compat verify` 判据是：

```python
if job.get("state") != "DONE" or man.get("verdict") != "PASS":
    _die(f"证据作业未成功：state={job.get('state')} verdict={man.get('verdict')}")
```

新增 `DONE_WITH_ISSUES` + `verdict="WARN"` 时，这两道判据**都会拒绝** ——
因为 `state != "DONE"`（是 `DONE_WITH_ISSUES`）且 `verdict != "PASS"`（是 `WARN`）。

**这是想要的行为**：一条有检查未过的作业，本来就不该被当成"这个工作流已验证"的证据。
不需要改 `p20ctl`，现有判据天然正确。只需在测试里钉住这条。

## 3. 分组键定稿（方案 C）

你拍板了，这里写死细节。

### 3.1 分组键

```python
group_key = model_key
约束条件  = 目标工作流的 {节点类集合, 资产文件名集合} ⊆ 实例的「已验证集」
```

### 3.2 「已验证集」怎么建

```python
@dataclass
class InstanceSlot:
    uid: str
    model_key: str
    verified_nodes: set[str]        # 这台机器上真跑成功过的工作流的节点并集
    verified_assets: set[str]       # 同上，资产文件名并集
    workflows_ok: list[str]         # 跑成功过的工作流 key 列表
    ...
```

**只记录"真跑成功过"的**，不用 `object_info` 全量。
理由（实测支撑）：`object_info` 只能证明 ComfyUI "认识"这个节点类，
不能证明它的依赖软链好了。比如 `UpscaleModelLoader` 认识，但
`4x-UltraSharp.pth` 可能没软链 —— 只有真跑成功才算数。

### 3.3 检查的两个时机（实测必要）

| 时机 | 查什么 | 为什么不能合并 |
|---|---|---|
| **排队时** | 节点类在不在 `verified_nodes` | 不用渲染，能提前决定去哪台机 |
| **渲染后** | `{{UPSCALE_MODEL}}` / `{{LORA}}` 指到的**具体文件**在不在 `verified_assets` | 实测这俩是占位符，参数填了才知道指向什么 |

### 3.4 冷启动怎么办

新实例 `verified_nodes` 是空的 —— 什么都跑不了。

**解法**：新实例建好后，**先跑一次"节点基线"**：
用该模型最基础的那个工作流（比如 `sdxl_t2i`）跑一条，成功后
`verified_nodes` 就有内容了。这一条的成本是必须付的（相当于原有的首条装载开销）。

**或者更省**：建机时从 `object_info` 取一次全量节点集，**只当作"候选"**，
真跑成功一条之后才升级成"已验证"。这样第一条不会被拒。

## 7. 一个我必须提醒的点

你的第 1 条拍板「不重试，返回视频并告知情况」，对一个场景**有副作用**：

**如果是"拉回来的文件本身是坏的"**（比如传输截断），`verify` 会报
`decode` 或 `size` 失败 —— 但那不是"产物有毛病"，是"文件没拉全"。

这种情况下：
- 返回视频：用户下载到的是坏文件，播不了
- 不重试：明明重拉一次就能好

**建议区分**：`verify` 的七项里，`decode` / `size` / `frames` 属于
"文件完整性"，这类失败**允许重试一次**（重拉）；`freeze` / `black` /
`params` 属于"内容质量"，这类**不重试**（重跑也一样）。

**这个要不要采纳，你定。**
