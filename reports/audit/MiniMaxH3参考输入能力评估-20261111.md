## 0. 先回答你的问题

> MiniMax H3 R2V 只有两张参考图吗？有些工作可以上传参考音频，我们的工作流里面有吗？

**两张图不是上限，是官方示例只连了两个。**

节点定义（`objectinfo-v4.json` → `MiniMaxH3ReferenceToVideo.input.optional`）：

| 槽位 | 类型 | 上限 | 说明（节点自带 tooltip） | 我们接了 |
|---|---|---|---|---|
| `ref_images` | IMAGE | **9** | 短边超 2048 会降采样，不会放大 | 2 |
| `ref_videos` | IMAGE | **3** | 参考视频帧，24fps，2–15 秒 | **0** |
| `ref_video_audios` | AUDIO | **3** | 「同序号参考视频的音轨」 | **0** |
| `ref_audios` | AUDIO | **3** | 独立参考音频 | **0** |

**参考音频：节点支持，我们没接，官方示例也没接。**

---

## 1. 节点描述里最关键的一句话

```
<Picture i> / <Video k> / <Audio j> reference conditioning for MiniMax H3.
Use the same tags when prompting.
```

**必须在 prompt 里用 `<Picture 1>` / `<Video 1>` / `<Audio 1>` 这样的标签引用**，
输入才会被用上。这决定了实现方式：不只是「加个上传框」，还要**让用户知道怎么写标签**。

## 2. 我们现在的图有个真实缺陷

### 2.1 `minimax_h3_r2v`：prompt 要求用音频，却没有音频

prompt 原文（这是从官方模板继承的）：

```
Use <Picture 2> and <Picture 1> as reference frames and <Audio 1> exactly as it is.
```

| prompt 声明的 | 实际接的 |
|---|---|
| `<Picture 1>` `<Picture 2>` `<Audio 1>` | `ref_image_0` `ref_image_1` |

**`<Audio 1>` 指向一个不存在的参考音频。** 模型会尝试用它，但拿不到东西。
这条现在是 `verified`（real-run，我昨晚跑的 66.5/B）—— 也就是说它**能跑通、画面不错**，
只是音频那部分指令是空转的。

这是「跑通了但没干成该干的事」的又一例：质量分只看画面，看不出音频缺失。

### 2.2 `minimax_h3_multiframe_reference`：4 张图走了两条不同的路（**不是缺陷**）

我一开始以为这条断线了 —— 4 个 LoadImage 只连了 1 个进 `ref_images`。
查下去发现**是两种机制并用，设计正确**：

| 图 | 去向 | 作用 |
|---|---|---|
| `164` h3_frame_ref_1 | `136.ref_images.ref_image_0` | **身份参考**（交给 ReferenceToVideo） |
| `157` h3_frame_ref_2 | `147 MiniMaxH3AddGuide.image` | **帧引导**（指定某一帧的内容） |
| `159` h3_frame_ref_3 | `162 MiniMaxH3AddGuide.image` | 同上 |
| `167` h3_frame_ref_4 | `169 MiniMaxH3AddGuide.image` | 同上 |

所以「4 张图只有 1 张在 ref_images 里」是**对的** ——
另外 3 张走的是 `MiniMaxH3AddGuide`（帧引导），不是参考图。
这条没有缺陷，我最初判错了。

（`verified` / `manual`，11-06 的 trial 证据，没走完整 P1 闭环 —— 这一点没变，
但它缺的是「闭环证据」，不是「功能残缺」。）

### 2.3 `fasth3_ominiref_r2v`：prompt 只用 1 个标签，接了 2 张图

反过来：接了两张 `ref_image_0/1`，但 prompt 只写了 `<Picture 1>`。
第二张图被传进去但没被引用 —— 不报错，但可能白占显存/影响 conditioning。

## 3. 加参考音频要改什么

四个环节，**两个缺失**：

| 环节 | 现状 | 改动量 |
|---|---|---|
| ComfyUI 节点 `ref_audios` | ✅ 支持 | — |
| schema `PARAM_TYPES` | ✅ 已有 `audio` | — |
| `run.py` 上传 | ✅ 正则 `(?:image\|mask\|audio\|video)(?:_\d+)?` 已含 audio | — |
| **`sniff_upload()`** | ❌ 只认 PNG/JPEG/WebP/MP4/MOV/WebM/AVI/GIF，**WAV/MP3/FLAC → 415** | 加 magic bytes + 扩展名 + `_cap_for` |
| **前端渲染** | ❌ 没有 audio 字段类型（`app.js` 里 grep `audio` 零命中） | 加 audio 上传控件 |
| registry 参数 | ❌ 没有 `ref_audio` 参数 | 加参数 + 绑定 `ref_audios.ref_audio_0` |

### 3.1 各项的具体改动

**① `sniff_upload()`（webui/api.py）**

要加三种格式的识别：

```python
if data[:4] == b"RIFF" and data[8:12] == b"WAVE":     return ".wav"
if data[:3] == b"ID3" or data[:2] in (b"\xff\xfb", b"\xff\xf3"):  return ".mp3"
if data[:4] == b"fLaC":                                return ".flac"
```

注意 WAV 也是 `RIFF` 头，和现有的 WebP/AVI 判断共用前缀，**顺序不能错**
（WebP 判 `data[8:12] == b"WEBP"`，AVI 判 `b"AVI "`，WAV 判 `b"WAVE"`，三者互斥）。

**② `_cap_for()`**

音频比图片大、比视频小。WAV 24bit/48kHz 立体声音乐约 **17MB/分钟**，
一段 10 秒参考音频 ≈ 3MB。建议归类到 `MAX_UPLOAD`（20MB）就够，
或单开一个 `MAX_UPLOAD_AUDIO`（建议 64MB，容得下 3 分钟无损）。

**③ 前端 audio 控件（web/dist/app.js）**

现在 `submitJob()` 里媒体字段的判断是：

```js
if (spec.type === 'image' || spec.type === 'video') { ...取 S.uploads[name]... }
```

要加 `'audio'`。上传控件（`doUpload`）也要接受音频的 `accept` 属性。

**④ registry 参数（registry/workflows/*.json）**

```json
"ref_audio": {
  "type": "audio",
  "required": false,
  "description": "参考音频。**必须在 prompt 里用 <Audio 1> 引用才会生效**。",
  "bindings": [{"node": "136", "input": "ref_audios.ref_audio_0"}]
}
```

`ref_audio_2/3` 同理（上限 3 段）。

**⑤ 图里加 LoadAudio 节点**

```json
"180": {"class_type": "LoadAudio", "inputs": {"audio": "{{REF_AUDIO}}"}}
```

然后 `136.inputs["ref_audios.ref_audio_0"] = ["180", 0]`。

## 4. 但有个绕不过去的验证问题

**参考音频的效果没法靠机器验证。**

我们的质量评分（`tools/p2/quality.py`）只看画面：

| 指标 | 测什么 |
|---|---|
| `sharpness` | 边缘能量 |
| `luma_mean` / `luma_range` | 亮度分布 |
| `noise_keep` | 噪点保留率 |

**完全不看音频。** 所以加上 `ref_audio` 之后：

- ✅ 能确认「跑通了、不报错、产物里有音轨」
- ❌ **不能确认「生成的音频和参考音频有关」**

要判断后者只有两条路：

1. **人耳听**（你听完判断）
2. 加音频相似度指标（MFCC/频谱距离、或者更简单的：比对生成音频的时长/节拍/基频）

第 2 条技术上可行，但属于**新建一套音频质量评估**，量级和当初做画面质量分差不多。

## 5. 三个选项的代价

| 方案 | 改动 | 真机验证 | 能验证到什么 |
|---|---|---|---|
| **A. 只加 `ref_audio` 参数** | sniff_upload + 前端 + registry + 图，约 4 处 | ¥0.25/条 | 跑通 + 产物有音轨；**效果靠你听** |
| **B. A + 参考视频 `ref_videos`** | 多一个视频字段 + 抽帧（`LoadVideo` 已有） | ¥0.5/条 | 同上 |
| **C. A + 音频质量指标** | 多一套音频分析（MFCC/频谱距离） | 额外 ¥0.5 做校准 | 能自动判断「音频是否真的像参考」 |

### 5.1 顺带能修的旧账

不管选哪个，下面两条**建议一起修**（都是 ¥0 的静态修改）：

**① `minimax_h3_r2v` 的 prompt 去掉 `<Audio 1>`**
既然没接音频，prompt 里就不该提。或者反过来 —— 加上音频让这个标签有意义。
现在这样是「要求了但没给」，属于隐性失败。

**② `multiframe_reference` 补一次完整闭环证据**
它标 `verified` / `manual`，依据是 11-06 的 trial，**没走过 P1 九步闭环**。
功能本身没问题（§2.2 查过，4 张图走两条路，设计正确），
缺的是「走完整流程 + 产出可查」的 real-run 证据。约 ¥0.25。

**③ `fasth3` 的 prompt 要引用 `<Picture 2>`**
接了两张图却只写了一个标签，第二张图被传进去但没被引用。
（这条同时说明 §2.3 的现象是「给了没要求」，和 §2.1 的「要求了没给」正好相反。）

## 6. 我的建议

**如果参考音频是你的真实需求，选 A。** 理由：

- 改动集中在 4 处，都是小改
- ¥0.25 就能验一次
- 效果你听完就能判断，不需要我建音频评估体系
- `minimax_h3_r2v` 现有 prompt 里那个 `<Audio 1>` 终于有意义了

**不建议先做 C（音频质量指标）**：在没确认「这个功能对你有没有用」之前，
先建一套评估工具是本末倒置。等你实际用几次、确认参考音频真的有效果，再考虑自动化。

**无论选什么，都建议先修 §5.1 那三条旧账** —— 它们现在是「看起来有功能、实际是空的」，
比缺功能更容易误导。

**参考音频支持加，但我们的上传链路（`sniff_upload` 拒 WAV）和前端（没有 audio 控件）
两处是断的，现在加参数也传不上去。**

  · `minimax_h3_r2v` 的 prompt 写着 `<Audio 1> exactly as it is`，
    但整张图里没有 LoadAudio、`ref_audios` 也没接 —— 要求了但没给
  · `fasth3` 接了两张参考图，prompt 只写了 `<Picture 1>` —— 给了但没要求

两条都属于「标了 verified 但有一半是空转」，质量分看不出来（它只看画面）。
