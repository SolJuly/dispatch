## 1. 需求的准确形式

你说的三条，我先翻译成可执行的判据：

### 规则 A · 闲置清理

> 「超过二十分钟，且没有进行作业的实例直接清掉」

```
for each 实例:
    if (now - 实例有意义的起始时间) > 20min and 实例上没有正在跑的作业:
        terminate
```

**关键在"有意义的起始时间"** —— 现有代码用 `CreateTime`（创建时间），
这是个错误判据：一台实例创建了 3 小时、但刚刚 1 分钟前开始跑作业，会被误杀。

正确的判据应该是 **"最后一次有作业结束/开始的时间"**，也就是「空闲时长」：

```
idle_since = 该实例上最后一个作业的结束时间（没有作业则 = 实例 start 时间）
if now - idle_since > 20min: terminate
```

### 规则 B · 同工作流串行

> 「同一工作流提交多份任务，不应该建多台实例，而是在同一台实例里任务串行，
> A 完成进行 B，B 完成进行 C」

```
group_key = (workflow_key, model_key, gpu_type)
if 该 group 已有实例在跑 → 新任务排进该实例的队列，不建机
```

### 规则 C · 不同工作流并发

> 「只有不同工作流的情况下，才启动多台实例并发完成」

```
实例数上限 = min(并发上限, 不同 workflow 的数量)
```

这和「作业数上限」不同 —— 现在 `concurrency.py` 数的是作业数，
提交 5 份同一工作流的任务会直接撞上限，而按你的规则它们应该共用一台机器。

### 规则 D · 同实例内并行（显存允许时）

> 「在进行某个工作流任务时，如果显卡还有能力生成的话，在实例里并发完成两至多个任务」

```
if 实例上剩余显存 ≥ 该工作流单任务峰值 × 1.2:
    允许再塞一个任务进同一实例
```

## 2. 现状审计：每条规则差多远

### 2.1 规则 A · 闲置清理 —— 现在**完全没在做**，而且代码有 bug

`tools/p2/scheduler.py:110`：

```python
def reap_instances(ttl_min: int = TTL_MIN) -> list[str]:
    """超 TTL 且没有活跃队列项的 p2-* 实例 → terminate。"""
    active = {i["job_id"] for i in queue.items() if i["state"] in ("claimed", "running")}
    killed = []
    now = time.time()
    for inst in live_instances():
        name = str(inst.get("Name") or "")          # ← 算了不用
        uid = inst.get("UHostId")
        created = inst.get("CreateTime") or 0       # ← 用创建时间，不是空闲时间
        age_min = (now - float(created)) / 60
        if age_min >= ttl_min and uid:              # ← active 在这里本该参与判断
            terminate(uid)
```

**三个问题叠加**：

| # | 问题 | 后果 |
|---|---|---|
| 1 | `active` 变量算完从不使用（实测：函数体里只出现 1 次，就是赋值那行） | 判据退化成"创建超时即杀"，不看有没有作业 |
| 2 | 用 `CreateTime` 而不是空闲时长 | 跑 50 分钟的长作业会被腰斩 |
| 3 | 唯一调用方 `p2-dispatch` 已停用 | **现在完全没有人巡检** |

`name` 同样算了不用。这是抄改代码留下的痕迹 —— 注释描述的意图和实际行为已经分家。

**这就是审计报告里那 ¥37.99 空转（65% 的花费）的制度性原因。**

### 2.2 规则 B · 同工作流串行 —— 现在是**每条作业建一台机**

作业的执行模型是**一条作业 = 一个实例的完整生命周期**：

```
tools/p1/run.py 的九步：
  provision（建机）→ setup → ready → submit → wait → fetch → verify → persist → release（销毁）
```

`step_release` 是九步里必走的一步（实测两处调用点：正常路径 + 失败路径），
所以**作业结束 = 实例销毁**。同一个工作流提交 5 份，就是建 5 次机、销毁 5 次。

成本对比（4090，¥2.15/h）：

| | 建机时间 | 装载模型 | 建机费 |
|---|---|---|---|
| 现在：5 条各建一台 | 5 × ~2min | 5 次 | 5 × ¥0.08 ≈ ¥0.40 |
| 你的方案：1 台串 5 条 | 1 × ~2min | **1 次** | ¥0.08 |

省的不只是建机费，**省的是模型装载时间** —— 这是大头。

## 3. 方案

### 3.1 规则 A · 闲置清理（改动最小，收益最大）

新建 `tools/p2/reaper.py`，替换 `scheduler.reap_instances()`：

```python
IDLE_LIMIT_MIN = 20        # 你的要求

def reap(idle_min=IDLE_LIMIT_MIN, *, dry_run=False) -> list[dict]:
    """清理「空闲超过 idle_min 分钟」的实例。

    判据是**空闲时长**，不是创建时长：
        idle_since = max(该实例上最后一个作业的结束时间, 实例 start 时间)
    这样跑 50 分钟的长作业不会被腰斩，而建了机什么都没干 21 分钟会被清掉。
    """
    busy = {实例上有 state in (RUNNING, SUBMITTED, VERIFYING...) 的作业}
    for inst in live_instances():
        if inst.uid in busy:            # ← 有作业在跑，跳过
            continue
        idle_since = last_job_end_on(inst) or inst.start_time
        if (now - idle_since).minutes >= idle_min:
            yield inst
```

**"有作业在跑"怎么判**（三层，取并集，任一命中就不杀）：

1. `queue.db` 里有 `claimed/running` 且 `instance_id == uid` 的项
2. `reports/p1/jobs/*/job.json` 里有非终态作业且 `instance.uhost_id == uid`
3. 云端 `nvidia-smi` 显示 GPU 利用率 > 5%（最硬的证据，但要 SSH，可选）

前两层是纯本地、毫秒级，够用。第三层作为**保险**：如果本地状态全烂了（比如作业目录被删），
GPU 在转就说明机器在干活。

**为什么不用 `CreateTime`**：见 §2.1。一台实例可以活 8 小时跑 20 个作业，
`CreateTime` 判据会在第 45 分钟就把它杀掉。

**怎么让它真的跑起来**：`reaper` 要做成独立的一次性命令，
挂在 systemd timer 上（每 5 分钟一次），**不依赖调度器**。
理由：调度器是"找活干"的逻辑，可能因为没活而长期闲着；清理是"安全兜底"，必须独立存活。

```ini
# deploy/systemd/p2-reaper.timer
[Timer]
OnUnitActiveSec=5min
```

### 3.2 规则 B · 同工作流串行（核心改造）

这是改动最大的一块。核心思路：**把"实例"从"作业的附属品"提升成一等公民**。

#### 现在的模型

```
作业 ──建机──> 实例 ──销毁──> 作业结束
（1:1，作业死了实例就死）
```

#### 目标模型

```
工作流组 ──> 实例（长生命周期）──> 队列里的作业 A → B → C
（1:N，实例活着，作业一个个进去）
```

#### 数据模型

新增 `instance_pool` 表（`reports/p2/instances.db`）：

```sql
CREATE TABLE instance_slot (
  uid           TEXT PRIMARY KEY,
  workflow_key  TEXT NOT NULL,          -- 绑定关系：这台机器只跑这个工作流
  model_key     TEXT NOT NULL,
  gpu_type      TEXT NOT NULL,
  state         TEXT NOT NULL,          -- provisioning/running/draining/stopped
  started_at    REAL NOT NULL,
  idle_since    REAL NOT NULL,          -- 最后一个作业结束的时间（规则 A 用）
  vram_total_mb INTEGER,
  vram_peak_mb  INTEGER,                -- 该工作流实测峰值
  current_jobs  TEXT                    -- JSON 数组：正在跑的 job_id
);
```

**为什么按 `workflow_key` 而不是只按 `model_key` 绑定**：

同一模型可以挂多个工作流（比如 `qwen_image_t2i` / `_landscape` / `_portrait` 共用
`qwen_image` 模型），它们**该共用一台机器** —— 权重一样，不用重新装。

所以分组键应该是 **(model_key, workflow_key 的集合)**。简化做法：
**按 `model_key` 分组**，因为权重装载的代价取决于模型，不取决于工作流的节点连法。

> 这一条我倾向于按 `model_key` 分组，然后 `workflow_key` 只是排队顺序的依据。
> 理由：你说"同一工作流提交多份"是典型场景，但"同模型不同工作流"也应该共用机器 ——
> 它们是同一批权重的不同用法。

#### 执行流程

改造 `tools/p1/run.py`，把 `provision` 和 `release` 两步变成**可跳过**：

```python
def step_provision(job, opts, ctx):
    # 新增：先看有没有可复用的实例
    slot = slots.find_for(job)            # 按 model_key 找 running 的
    if slot:
        ctx.update(slot.as_ctx())
        ctx["borrowed"] = True            # 标记：这台机器不是我的，别销毁
        _note_instance(slot.uid)          # 但还是登记，以防进程被打断
        return
    # 没有才建机
    ...

def step_release(job, opts, ctx):
    if ctx.get("borrowed"):
        slots.touch(ctx["uhost_id"])      # 只更新 idle_since，不销毁
        return
    ...  # 原有的销毁逻辑
```

**并发安全已核实：产物不会互相覆盖。**

`tools/p20/render.py:149` 把 `job["job_id"]` 直接当 `filename_prefix`：

```python
graph, meta = render(wf, model, res["params"], job["job_id"], graph=wf.get("graph_obj"))
```

所以每条作业的输出文件天然带自己的 job_id 前缀（实测产物名
`00-primary-p1-20261108T1352-3d1616_00001_.mp4` 就是这个机制）。

**这意味着同一实例上并行提交在文件层面是安全的**，不需要额外的目录隔离。
但 v1 仍先做**串行**（A 完成再 B），理由不是安全，是**可观测性**：
串行时一条作业失败能立刻定位是哪条；并行时一堆日志混在一起，排查成本高。

#### 谁来做排队

两条路，我建议**第二条**：

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| ① | 让 `run.py` 自己等实例锁 | 改动小 | 每个作业一个 run.py 进程，5 条作业 = 5 个进程在等，日志乱 |
| ② | **调度器持有实例，逐条 spawn run.py** | 状态集中、好观测 | 要调度器可靠 |

方案 ② 就是现在 `scheduler.py` 的架构（它已经会 spawn `run.py --batch`），
只需要加一层「实例槽位管理」。这也顺便解决了 §4 的队列问题。

### 3.3 规则 C · 不同工作流并发

改 `concurrency.py` 的计数口径：

```python
def slots_used(jobs_dir=None) -> int:
    """按**模型分组**数，不按作业数。

    5 份 qwen_image_t2i = 1 个槽（共用一台机排队）
    3 份不同模型       = 3 个槽
    """
    groups = {job_model_key(j) for j in active_jobs(jobs_dir)}
    return len(groups)
```

这样：
- 提交 5 份同工作流 → 1 个槽 → 只建 1 台机 ✅
- 提交 3 份不同工作流 → 3 个槽 → 上限 2 时第 3 个降级排队 ✅

### 3.4 规则 D · 同实例并行（**先验证，再决定**）

#### 必须先验证的事

| # | 问题 | 怎么验 | 花费 |
|---|---|---|---|
| 1 | ComfyUI 0.36 的 `/prompt` 队列是串行执行还是并发执行 | 塞 2 个 prompt 看 `history` 的 `started_at` 是否重叠 | ¥0.5 |
| 2 | 同样两个任务并发时显存峰值 | `nvidia-smi` 每 1s 采样 | 同上 |
| 3 | SDXL 类（10GB）能不能稳定塞 2 个 | 同上 | 同上 |
| 4 | 视频类模型的显存峰值（**从没测过**） | 跑一条 Wan/LTX 采样 | ¥0.13 |

#### 如果 ComfyUI 是串行执行队列

那"塞 2 个任务"**没有收益，只有风险**：两个任务排队，但第二个的模型可能已经
预加载进显存 → 双倍占用 → OOM。

这种情况下规则 D **不应该用"塞任务"实现**，而应该用 **batch 参数**：
- 现有 `params.batch_size` 已经支持（实测 Qwen batch 1–4 都能跑）
- 这才是"一张卡多出几张图"的正确做法，显存占用可控

#### 如果是并发执行

才值得做任务级并行。配置大概是给 ComfyUI 加执行线程数（不同版本参数名不同）。

**补充证据**：`batch_size` 参数在关键工作流上都已经存在（实测）：

| 工作流 | batch_size | 说明 |
|---|---|---|
| `qwen_image_t2i` | 1–4 | 已有，默认 1 |
| `sdxl_t2i` | 1–4 | 已有，描述里明确写了"批量能省下重复的建机与加载时间，但显存占用会成倍上升" |
| `zimage_turbo_t2i` | 无 | 部分工作流没开这个参数 |

所以"一张卡多出几张"**已经有现成开关**，只是 UI 上没把它和"要不要多任务"联系起来。

**我的判断**：规则 D 大概率**不该按"塞任务"做**，而该按 `batch_size` 做。
理由：

1. 实测数据表明 Qwen 在 24G 卡上余量只有 0.3–3.2GB，塞不下第二个
2. 即使 48G 卡能塞，ComfyUI 默认执行模型是串行的，塞进去也是排队
3. `batch_size` 是**同一个 checkpoint 一次前向出多张**，比"两个独立任务"更省显存 ——
   因为计算图复用、不需要重复装载

**所以规则 D 我建议改写成：**

> 当显存余量 ≥ 单任务峰值的 1.2 倍时，**优先用 batch_size 放大单任务产出**，
> 而不是并行塞多个任务。

除非真机验证证明 ComfyUI 确实支持任务级并发且显存够用，否则不做。

## 4. 顺带要解决的两件事

### 4.1 队列现在是"有轮子没车"

`jobqueue.py` 有完整 schema（8 状态 + 退避重试 + 租约心跳），但：
- 调度器 `p2-dispatch` 已停用

规则 B 的"排队"必须有队列支撑，所以这块要么接通、要么用更简单的方案。

**建议：接通队列**。因为规则 B 天然需要"实例 × 队列"的结构，
而 `jobqueue` 已经有 `batch_id` / `model_key` / `instance_id` 字段，缺的只是消费者。

### 4.2 预检的软链盲点（顺手修）

依赖预检准确 —— 所以这个得一起修。

## 5. 工作量与风险

### 分阶段
