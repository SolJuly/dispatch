## 1. 120 秒这个数的经济性核实

我把账算了一遍，**结论是"按纯成本算略亏，但换了时间体验，值得"**。

### 1.1 复用的真实净收益

```
建机 59s  = ¥0.0352   ← 停机后 start 可省
setup 47s = ¥0.0281   ← 烘焙快路径只花 5s，净省 ¥0.0251
                       ────────
可省合计  = ¥0.0603

ComfyUI 停机后要重启 ~40s = ¥0.0239   ← 省不掉
                       ────────
复用净省  = ¥0.0364  ≈ 61 秒的价值
```

### 1.2 空转 120 秒的代价

```
120s × ¥2.15/h = ¥0.0717
```

### 1.3 按「下一单多快会到」分情况

| 下一单间隔 | 空转损失 | 复用收益 | 净 |
|---|---|---|---|
| 0s（立刻） | ¥0.0000 | ¥0.0364 | **+¥0.0364** |
| 30s | ¥0.0179 | ¥0.0364 | **+¥0.0185** |
| 60s | ¥0.0358 | ¥0.0364 | **+¥0.0006**（打平） |
| 90s | ¥0.0537 | ¥0.0364 | −¥0.0173 |
| 120s | ¥0.0717 | ¥0.0364 | −¥0.0352 |

**纯成本口径下，盈亏平衡在 61 秒。120 秒是亏 ¥0.035。**

### 1.4 但为什么 120 秒仍然是对的

**因为它买的不是省钱，是"用户不用等"。**

长任务跑完后用户往往会：

- 看一眼结果，不满意 → 微调参数再跑
- 满意 → 换下一组参数

这个"看一眼 + 改参数 + 再提交"的动作，实测（我自己用）大概 30–90 秒。

**如果用 61 秒窗口**：一半的复现尝试会超窗，用户要重新等 113 秒建机。
**如果用 120 秒窗口**：绝大多数能接上。

而长任务本身的成本是 ¥0.36–0.45（10 分钟推理），多花 ¥0.035 换"不用重等 113 秒"——
占任务成本的 8%，换来的是体验从"要等两分钟"变成"接着就能跑"。

**你的判断成立。** 我按 120 秒执行。

### 1.5 短任务为什么不该给窗口

短任务（推理 < 2 分钟）本身只花 ¥0.087–0.136。

```
给 120s 空转 = ¥0.0717 = 任务成本的 53–82%
```

**这是纯亏**。而且短任务往往是"试一下看看"，用户不会马上接着跑。

**所以「短任务不空转」是对的。**

## 3. "怎么判定长任务"

你上一轮说的「不能按工作流认定」，结合这一轮的 UI 勾选，实际是：

### 3.1 判定的三条来源（优先级从高到低）

| 优先级 | 来源 | 说明 |
|---|---|---|
| 1 | **用户在 UI 勾选「长任务」** | 显式意图，最高优先级 |
| 2 | 估算 > 10 分钟 | 自动判定（需要模型 `perf` 数据，见下） |
| 3 | 都没有 | **默认按短任务** |

**默认短任务** 的理由：短任务不空转是"省钱"的方向，判错代价小；
反过来默认长任务会让所有作业都空转 120s，那是纯浪费。

### 3.2 估算现在做不了

49 张模型卡**零性能声明**。所以第 2 条（自动判定）现在只能留空，
等其他阶段补上 `perf` 字段。

**这意味着短期内只有"用户勾选"这一条路。** 这没问题——你说的就是"用户点击选择"。

### 3.3 勾选状态存在哪

`job.json` 里加一个字段：

```json
{
  "task_class": "long",          // "short" | "long"
  "task_class_source": "user",   // "user" | "estimated" | "default"
  "idle_after_done_s": 120       // 作业结束时由代码写入，便于审计
}
```

**为什么要记 `source`**：以后估算上线了，能对比"用户标的"和"估出来的"差多少，
用来校准估算模型。

## 4. 三个时间参数

| 参数 | 值 | 环境变量 | 说明 |
|---|---|---|---|
| 长任务空转窗口 | **120 秒** | `P2_LONG_IDLE_S` | 你定的 |
| 停机保持 | **2 小时** | `P2_STOPPED_TTL_MIN=120` | 你定的（从 4h 改成 2h） |
| 短任务空转窗口 | **0 秒** | — | 不空转 |

### 4.1 为什么短任务不需要参数

短任务是"立即归还槽位"，没有等待窗口。写死 0 而不是给个可配项，
是因为**给 0 开口子容易被误配成非 0**（比如有人觉得"短任务也给 30 秒吧"），
那就回到了我们刚否掉的设计。

### 4.2 2 小时的合理性

```
停机期间 ¥0（实测）
占配额（账户 5 台）
```

2 小时够覆盖：
- 用户看一眼结果、改参数、再提交（分钟级）
- 出去吃个饭回来接着跑

超出 2 小时销毁的理由：**腾配额**。账户 5 台上限，
如果 5 台都停在"2 小时前跑过任务"的状态，新任务就没槽了。

### 6.2 `reaper` 的三态判定（核心逻辑）

```python
def decide(inst, now):
    """返回 (动作, 理由)。三态：保持 / 停机 / 销毁。"""

    # ① 有作业在跑 → 保持
    if inst.busy:
        return "keep", "有作业未结束"

    # ② 刚跑完长任务，在 120s 窗口内 → 保持
    if inst.idle_since and (now - inst.idle_since) < long_idle_s:   # 120
        if inst.last_task_class == "long":
            return "keep", f"长任务空转窗口内（剩 {long_idle_s - elapsed:.0f}s）"

    # ③ 云端还在 Running → 该停机
    if inst.cloud_state == "running":
        return "stop", f"空闲已超窗口，停机（停机后 ¥0）"

    # ④ 已停机，在 2 小时保留期内 → 保持
    if inst.cloud_state == "stopped":
        if (now - inst.stopped_at) < stopped_ttl_min * 60:          # 120 分钟
            return "keep", f"停机保留期内（剩 {剩余:.0f} 分钟）"
        return "terminate", "停机超过 2 小时，销毁回收配额"

    return "keep", f"状态 {inst.cloud_state}，不处理"
```

**关键：短任务不进入第 ② 步的等待**（`last_task_class == "short"` 时直接跳到 ③）。

### 6.3 一个必须处理的边界

**用户勾了长任务，但跑完之后 2 小时内又提交了同一模型的任务序**：

```
T+0     作业 A 跑完（长任务）→ 空转 120s → 停机
T+30m   用户提交作业 B（同模型）
        → reaper 发现停机 30 分钟 < 2 小时 → 保持
        → run.py start 唤醒（62s）→ 跑 B
T+35m   B 跑完（长任务）→ 空转 120s → 停机
        → 停机计时器**重置**
```

**停机计时从「最后一次停机」算**，不是从第一次。否则跑完 B 之后实例立刻被销毁。

## 8. 一句话

**按你定的做**：短任务不空转（因为它本身只花 ¥0.09–0.14，给 120s 空转等于涨 53–82%）；
长任务给 120 秒窗口（按纯成本算略亏 ¥0.035，但换掉"重新等 113 秒"的体验，占任务成本 8%），
然后停机 2 小时（停机 ¥0，只占配额），过期销毁腾地方。

**120 秒这个数的经济账**：复用净省 61 秒 = ¥0.036，空转 120 秒 = ¥0.072。
60 秒打平，120 秒略亏 —— 但换来的是用户不用重新排队。

**UI 上要写清的那句话**：
> 建机要 113 秒，空转 120 秒的费用和重新建机基本抵消 —— 给你留出微调参数再跑一次的时间。
