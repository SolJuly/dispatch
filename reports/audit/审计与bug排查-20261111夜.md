## 事故：我用 `pkill -f` 误杀了一个正在跑的作业

### 发生了什么

2026-11-11 23:47:42，作业 `p1-20261111T2326-f76311`（H3 文生视频，
已推理 1095 秒、花了 ¥0.65）收到 SIGTERM 退出。它的信号兜底把实例定在
10 分钟后关机，23:57 真正停机。

**直接损失：¥1.08，任务半途而废。**

### 根因

我是这么重启文件服务的：

```bash
pkill -f "fileserver.py"; sleep 2; (setsid nohup ... python3 fileserver.py &)
```

`pkill -f` 匹配的是**完整命令行**，不是进程名。而我的每次工具调用都是
`bash -c "<整条命令>"`，那条命令里就写着 `pkill -f "fileserver.py"` ——
**这个 bash 自己也被匹配上**并收到 SIGTERM。连带地，任何命令行里含这串字的
进程都会中枪。

### 已修

新增 `scripts/restart_fileserver.sh`，按 **PID + `/proc` 实读**定位：

- 不用 `pkill -f` / `pgrep -f`（两者的误伤机制相同）
- 判据：① 首参是 python*；② 末参文件名是 `fileserver.py`；③ 该进程
  `/proc/<pid>/cwd` 就是本仓库
- 验证过：造一个无关的 `sleep 30` 进程，跑完重启脚本它**仍然活着**

> 附带一条经验：进程的实际 cmdline 是相对路径 `python3 fileserver.py`
> （启动时 cwd 就是仓库根），不是绝对路径。按绝对路径严格比对会匹配不到，
> 结果是重复启动撞 `Address already in use`。

## Bug 1：作业卡在 RUNNING 永远不消失

### 现象

23:47 作业被打死后，到 23:58 页面上**仍然显示「执行中 44%」**，
而进程早已退出、实例 23:57 也关机了。

### 根因

对账脚本 `jobs_reconcile.py` 的判定顺序错了：

```
① 进程还在 → keep
② 静默 < 60min → keep        ← 卡在这里
③ 读不到云端 → keep
④ 进程没了但实例还在 → fail_run
⑤ 进程和实例都没了 → 按证据收尾
```

作业满足"②"（静默才 0.3h），于是被判 keep。**但它永远不可能再变化了** ——
进程退了、实例也关机了，没有任何东西会替它推进。

阈值是给"进程还在、只是没写日志"那种慢作业的保守兜底，不是给"进程和实例
都已消失"这种终局用的。

### 修法

把**证据充分**的终局判定提到阈值之前：

- 进程没了 + 实例**已不在云端** → 终局
- 进程没了 + 实例**已关机（Stopped）** → 同样终局
  （关机状态下推理不可能继续）

同时保留"读不到云端 → keep"的保守分支 —— 那是**证据不足**，不是终局，
两者必须区别对待。

### 附带修掉的一个测试缺陷

`Base.judge(insts=None)` 里写着 `if insts is None: insts = {}`，
把"读不到云端"悄悄降级成"确认没有实例"。后果：

- `judge(d, insts=None)` 实际测的是 `insts={}`
- 名为 `test_cloud_unreadable_*` 的用例**根本没测到读不到的分支**
- 更危险：那条保守分支从未被验证过

改用哨兵值 `UNREADABLE` 区分三种含义（读不到 / 确认没有 / 实例还在）。

## Bug 2：queue.db 从 11-01 起就没再写入

### 现象

队列页说「0 在跑」，数据库也是空的 —— 但任务页明明有作业在跑。

### 根因

`jobqueue.enqueue()` 定义了，但**全库没有任何调用方**（`grep enqueue(` 零命中）。
queue.db 里剩的 8 条是 P2 队列功能的历史残留，最新一条停在 **2026-11-01 18:22**。

队列功能只做了一半：调度器能领活，但没人往里放活。

### 后果：屏幕上的数字互相矛盾

截图里的 KPI：

```
作业总数 47 · 已完成花费 ¥7.35
失败 26 · 完成 20
```

- 「47 / 失败 26 / 完成 20」来自 job.json（真实）
- 「已完成花费 ¥7.35」来自 queue.db 的 8 条旧记录

**两个数字属于两套互不相干的数据源，加起来没有任何意义。**
真实花费是 **¥3.86**（20 条 manifest 的 `amount` 合计），差了一倍。

### 修法

1. 前端 KPI 的花费改用 `S.jobs` 里每条的 `cost` 字段 —— 与总数同源
2. `/api/p2/queue` 如实标注：`active: false`、`stale_since: "2026-11-01 18:22:54"`、
   并说明「队列没有生产者，本表是历史残留，真实状态看 /api/p2/jobs」

## Bug 3：`/api/p2/dispatch` 契约外路由，一直 404

### 现象

前端 `GET /api/p2/dispatch` 一直 404，于是 `renderDispatchBar` 走进
`if (!d) { box.hidden = true; }` —— **整条提示被隐藏**，
「作业不会自己跑」这句最该说的话一起消失。

### 根因

这条路由**不在 `docs/openapi.json` 契约里**，是 SPA 初版自己发明的。
契约没覆盖、测试也没覆盖，于是烂了两个月。

### 修法

实现它，判据用**进程 + 队列活跃数**：

```json
{"alive": false, "running": 0, "slots": 2, "age_s": null,
 "note": "没有调度器在跑：CREATED 作业不会自己启动，需在任务页点「执行」"}
```

`age_s` 只认 10 分钟内的心跳 —— queue.db 里那些 11-01 的记录有个 10 天前的
`heartbeat_at`，照实返回会显示「调度器 10 天前活动过」，比 null 更误导。

同时前端文案改成按 `alive` 分支：没有调度器时明说"点执行"，而不是让人以为
"等一会儿就轮到了"。

## Bug 4：续跑时作业会「自我否决」

### 现象

`p1-20261111T0058-8302f5`（ltx2_3_flf2v）：推理失败后 restart，
状态 `FAILED_RUN → RESUMING → PROVISIONING` 只隔 **3 秒**，
接着被判 `FAILED_PROVISION`：

```
云端已有 2 台 p1-/p2- 实例在跑（上限 2）
```

**而那 2 台里有一台就是它自己** —— 上一轮的实例还没销毁完，仍在 Running。
重启变成自我否决，作业直接判死。

### 修法

`check_provision(exclude=...)` 支持排除指定 UHostId，
`run.py` 传入本作业自己的 `instance.uhost_id`。

只排自己 —— 别人的实例必须照数，否则并发上限就没意义了（有测试守着）。

## Bug 5：正常运行时不设平台侧定时关机

### 现象

riskmon R02：「运行中实例无定时关机 · 1 台」。

### 根因

`_on_signal` 只在 SIGTERM/SIGINT 时执行，**`kill -9`、OOM killer、控制机重启
都不走任何信号处理器**。那时 `_ORPHAN_UID` 只活在内存里，实例仍在 Running 计费。

### 修法

建机成功后**立刻**调 `cs.stop_at()` 设一个平台侧兜底：

- 时长 = `budget.max_minutes` + 15 分钟（覆盖推理后收尾/拉产物/写 manifest）
- 设的是**平台侧**定时关机，控制机挂了它照样生效
- 设不上不中断作业（reaper 还在），但**必须打日志**说明只剩 reaper 兜底

> 讽刺的是，这次救场的正是这个信号兜底 —— 我误杀作业时它把实例定在
> 10 分钟后关机，否则会一直烧到有人发现。
