## 0. 一句话结论

**代码质量高，但产品完整度低。**

系统是一个**打磨得很好用的单人本地创作工具**，而文档描述的是一个**面向市场的多云交易平台**。
两者之间的差距不是"再补几个功能"，而是**缺三个完整的业务层**（用户、交易、多云）。

| 维度 | 完成度 |
|---|---|
| L6 创作执行层 | 🟢 **85%** |
| L4 任务控制层 | 🟢 **75%** |
| L5 多云与资产层 | 🟡 **30%**（资产有，多云无） |
| L1 用户与组织层 | 🔴 **0%** |
| L2 市场与商品层 | 🔴 **0%** |
| L3 交易与计费层 | 🔴 **5%**（只有成本记录，无交易） |

**离 MVP 的诚实距离：约 4-6 周全职**（详见 §5），前提是先修 §4 的安全漏洞。

| 能力 | 状态 | 证据 |

| 并发 | 🔴 | **全局串行**，一次只能跑 1 个作业 |

**最关键的缺陷**：

```python
# tools/p1/run.py:297
cap = float((job.get("budget") or {}).get("max_cost") or 0)
_say(f"预算上限 ¥{cap}……")        # 只打印，全仓库搜 "if.*cap" 零匹配
```

`max_cost` 是个装饰品。真正兜底的是余额 <¥5 拒绝建机，以及 `max_minutes` 超时。

**第二关键**：`tools/p2/jobqueue.py` 里有完整的队列 + `max_concurrency`，但：
- 调度器进程没在跑（`pgrep scheduler` 空）
- UI 提交**不传 `--batch`**，所以每次都走全局串行锁
- 结果：第二个人提交会静默排队最多 4 小时（`QUEUE_WAIT_S=14400`）

## 4. 明显的漏洞

### 4.1 🔴 极危：Token 明文挂在公网（**今天复核仍存在**）

```bash
$ curl -sk https://123.207.74.155/pub/api/openapi.json
200
$ grep -c "23e00ec2" /srv/dsh-pub/api/openapi.json
3
```

**完整攻击链（全匿名，我实测过）：**

1. 从 `/pub/p21/*.md`、`/pub/api/openapi.json` 捞到 token（**13 个公开文档含 token**）
2. `https://…/files/<token>/ui/` → 200，进控制台
3. `/api/p2/jobs` → 200，读所有作业
4. `POST /api/p2/jobs` → 400（业务校验），**说明请求进到业务逻辑了**
5. `/pub/jobs/` autoindex 开着 → 用户上传的原始照片、成片、完整 prompt 全部可下载

**根因**：

```python
# scripts/build_openapi.py:21
TOKEN = "23e00ec2"                                    # 硬编码
# nginx
location /pub/ { auth_basic off; autoindex on; }      # 公开 + 可列目录
```

**这个必须今天修。** 我上一轮指出过，至今未动。

### 4.2 🔴 高危：`max_cost` 不生效

见 §1 L4。任何作业的实际花费只受 `max_minutes=40` 和余额下限约束。

按 4090 ¥2.15/h 算：单作业最坏 ¥1.43。余额 ¥8.38 → 最多被烧 5 次。

**如果你充值到 ¥1000，最坏损失就是 ¥990。**

### 4.3 🟡 中危：转售合规未确认

文档 §5.3 和 §16 都提到"云平台条款不允许转售"。

**这是整个商业模式的存亡问题。** 如果智云条款禁止"以服务形式向终端用户提供算力驱动的生成服务"，那 L2/L3 建得再好也没用。

**建议**：在写第一行订单代码之前，先去拿书面确认。BYOK 模式可以绕过（用户自己开户），但那就不是"市场"了。

### 4.4 🟡 中危：全局串行 + 4 小时静默排队

```python
QUEUE_WAIT_S = 14400        # webui/api.py:46
```

两个人同时提交，第二个静默排队 4 小时，**UI 显示"提交成功"**。

修法极简：UI 提交加 `--batch`（`run.py:1312` 已实现作业级锁）。**30 分钟工作量，收益最大。**

### 4.5 🟡 中危：24 个工作流从未真机验证

44% 的工作流是 `experimental`。UI 上标了"未开发"（`.mcard.undeveloped`），但用户点了会发生什么？

会被 `registry.resolve()` 拒绝（`409 该工作流×模型组合是 experimental`）。**这个处理是对的。** 但意味着 44% 的目录是死的。

### 4.6 🟢 低危：`http_download` 是死代码

```python
# tools/p20/comfy.py:119
def http_download(url, dest, timeout=300): ...
```

全仓库只有测试引用。文档 §7.4 说的"未命中时从中央仓库下载"完全没有实现路径。

## 7. 最后一句实话

**这套代码的工程质量，配得上一个产品。**

388 条测试、七项产物验证、14 状态机 + 守卫、幂等去重、断点续跑、账本审计 —— 这些不是"demo 级"的东西。

**但产品完整度配不上一个市场。** 文档描述的是"连接算力供应商、工作流开发者、创作者的交易平台"，而现在是一台"很好用的单人创作机"。

差距最大的不是技术，是 **L1/L2/L3 三个零**。而这三层里，L3 的支付和 L2 的转售授权，都是**法务问题，不是代码问题**。

**建议**：先把安全堵上（2 小时），然后**去拿云平台的书面授权**，再决定要不要投入 4-6 周做 MVP。

如果授权拿不到，整个 L2/L3 的方向要重做（转 BYOK），那 4-6 周就白花了。
