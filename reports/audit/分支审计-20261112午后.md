## 一、已修的 6 个

### ① `rebuild_from_jobs` 不写 `gpu_type`【中，复用静默失效】

```python
s = seen.get(uid) or Slot(uid=str(uid), model_key=str(mk))
```

`Slot.gpu_type` 默认 `"4090"`（24G）。而 `find_compatible(min_vram=N)` 靠
`gpu_type` 过滤。**槽位表丢了重建之后，所有槽位都被当成 24G** ——
一台真跑在 48G 上的机器也会因为默认值被升卡作业拒绝复用。

方向是保守的（不烧钱），但复用机制等于悄悄失效，**没有任何报错**。
上次真机升卡后的作业如果撞上重建过的槽位表，就会"宁可新建也不复用"，
每次多花一轮建机费（¥0 + 90s）。

**修**：从 `job["instance"]["gpu"]` 带出来。

### ② `step_release` force 分支不更新 `pool.json`【中，自愈但每次白试】

升卡销毁 `from_pool` 实例时，池记录还写着 `busy`。
下次 `pool.acquire()` 会去 `start` 一个已销毁的 uid → 失败 → 标 dead。
自愈，但每次都白试一轮（12s 超时 + 一次 API 调用）。

**修**：销毁后直接把池记录标 dead。刻意**不**调 `pool.release(uid, keep=False)`
—— 那会再 terminate 一遍（对已销毁的 uid 必然报错），只为落到同一个 dead 状态。

### ③ `jobctl show` 不显示升卡状态【中，操作员盲区】

升卡后"这个作业下次要求 ≥48G"这个**关键事实只存在于 job.json** 里。
操作员看 `jobctl show` 完全看不到，会以为还是声明的卡型 ——
然后奇怪为什么 `--resume` 不去抢 4090。

**修**：

```
⤴ 已升卡 2 次 → 下次要求 ≥48G（4090(24G)¥0.0717：4090(24G)¥0.0717）
```

### ④ `_pick_gpu` 的 N+1 API 调用【低，性能】

`cs.stock()` 每次都打一遍 `DescribeCompShareGpuInventory`（**无缓存**）。
我加的"阶梯补卡"对每张额外卡各调一次（最多 3 次往返），
而 `_oom_stock()` 自己的注释里就写着"逐个查要 11 次 API 往返"——
**同一个文件里，一个地方修了这个问题，另一个地方又造了一遍。**

**修**：抽 `_StockTable`（一次 inventory，全卡型复用），补卡和主循环共用。

### ⑤ `upgrade_audit` 缺文件直接 traceback【低，体验】

`--target` 路径打错（这个工具最常见的错误）得到的是一屏 `FileNotFoundError` 栈。

**修**：人话报错 + 提示先去采集快照的命令。

## 二、留决的 3 个（都有明确代价，取舍该由你定）

### A. `KEEP_MINUTES=15` 与卡价无关

失败后保留实例等 `--resume`，时长写死 15 分钟：

| 卡型 | 15 分钟空转的代价 |
|---|---|
| 4090 | ¥0.54 |
| 4090_48G | ¥0.95 |
| **H20** | **¥1.88** |
| A100 | ¥2.69 |

**真机那轮 H20 超时后就被保留了** —— 我 13:19 手动 abort，
空转了约 9.5 分钟 ≈ ¥1.19。

三个选项：

| 方案 | 效果 |
|---|---|
| 按卡价缩放（贵卡留短） | H20 留 5 分钟 ≈ ¥0.63，牺牲一点续跑窗口 |
| 固定金额上限（如 ¥0.5） | 简单，但 4090 也会跟着缩到 14 分钟，等于没变 |
| 不改 | 人工 abort 兜底，但没人在场时就是纯烧 |

我倾向第一种，但这改变了"失败后能续跑"的语义，该你拍板。

### B. `classify_oom` 的 NOT 优先可能吃掉真 OOM

判定顺序是**先查"不是 OOM"的字样，再查"是 OOM"**。实测：

```
日志同时含 use_missing_models（旧错误）+ CUDA out of memory（新错误）
→ 判成 "no" → 不升卡
```

这是刻意的设计（防止权重文件名里恰好带 "out of memory" 触发误升级），
但副作用是**日志尾部混着旧错误时会漏掉真 OOM**。

要修就得按行拆开、取最后一条错误再判 —— 判定更准，代码也更复杂。
目前 `_oom_evidence` 只读末尾 200 行，撞上的概率不高。

### C. `oom_escalate` 的日志没有作业前缀

批量模式下 run.py 的日志都带 `[job_id]` 前缀，`oom_escalate` 的不带。
两个作业并行时升卡日志分不清是谁的。

修起来容易（把 job_id 传进去），但 `_say` 刚被当死代码删了——
说明这个模块本来就没直接打印过东西，打印都在 run.py 侧。
**现状其实是对的**，列出来只是确认过、不是遗漏。

## 四、这次审计的方法（记下来，下次照用）

1. **`git diff --stat` 圈定改动面** —— 3830 行里 6 个文件是代码，其余是文档/测试
2. **每个新函数找调用方** —— `grep -rn` 全仓引用计数，**零引用 = 死代码或接线断裂**，
   两种都要查（这次 5 处是前者，真机那 4 个 bug 是后者）
3. **顺着数据流查状态落盘** —— `floor_vram` 写进 job.json 后，谁读它？
   `_gpu_candidates` / `_pick_gpu` / `step_provision` / `find_compatible` / `rebuild_from_jobs`
   五处，逐一核对 —— **就在第五处发现了 `gpu_type` 缺失**
4. **异常路径手推** —— `_try_escalate` 三条 return False 的路径，
   每条推"实例此刻是什么状态、谁来收尾"
5. **公开 API 的调用次数** —— `cs.stock()` 无缓存这一点，
   `_oom_stock` 的注释里自己写了，说明写的时候知道，加新代码时忘了

第 2 条和第 3 条是这次抓到问题最多的两个动作。
