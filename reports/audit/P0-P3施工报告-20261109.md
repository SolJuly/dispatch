## 1. 施工前先纠正了一个错判

上一轮我说「65% 的花费是空转」，依据是账本 settle 的 `attribution` 字段。
这轮动手前复核，发现**这个证据链不成立**：

```
settle 共 372 条，其中 backfilled = 369 条   ← 98.9%
非 backfilled 合计 ¥0.86
```

`backfilled: true` 表示「长时间没采样后一次性补账」，补的是一段时间的总和，
**归因标签（idle / job）是事后猜的，不可信**。

用可靠口径重算（余额首尾差）：

```
10-26 18:09 → 11-09 23:00（14.2 天）
¥52.94 → ¥8.15，共花 ¥44.79，日均 ¥3.15
其中作业自报 ¥15.14
```

作业自报只是**下界**（不含建机空档、模型装载时间）。所以"空转占多少"
这个问题**现在没有可靠答案** —— 我不该给一个精确的 65%。

**但这不改变施工内容**，因为真正的缺口是另一件我已经核实过的事：

```
queue.db        8 条，instance_id 全是 None
job.json        5 条，uhost_id 全有
交集            0 条
```

清理逻辑查 `queue.db`，而真实作业在 `job.json` —— 它看不见任何真实作业。这是事实。

### 顺带发现：现有清理不是"完全没做"，是"判据不对"

复核时发现 `csctl.py watch` **一直在跑**（cron 每 5 分钟），而且**真关过 3 次机**：

```
[17:35:05] uhost-...  gpu=0% cpu=3% gpuprocs=0 idle=15m
  → 空闲 15 分钟，执行stop 省钱
```

它的判据是 **GPU 利用率 ≤5% 且 gpuprocs==0，连续 15 分钟**。

这个判据有两个问题：

| 问题 | 后果 |
|---|---|
| 看 GPU 利用率，不看"有没有作业" | 作业刚提交、正在装模型时 GPU 还是 0%，15 分钟后被 stop 中断。SDXL 装载 21s、Qwen 53s，装完还要跑，很容易撞上 |
| 只 `stop` 不 `terminate` | 实例占配额（账户 5 台上限），频繁建机撞 8903 |

所以 `reaper.py` 的定位是：**用"作业状态"替掉"GPU 利用率"这个代理指标**。
`watch` 留着当粗网，`reaper` 是细网。

## 2. 改了什么

### P0 · `tools/p2/reaper.py`（新增，约 300 行）

**判据**：不看 GPU，看作业状态。三源合一，任一说"在忙"就不动。

```
① job.json       reports/p1/jobs/*/job.json 的 state + instance.uhost_id
                 真实作业的唯一可靠来源（实测 queue.db 是空的）
② queue.db       队列里的 claimed/running（接通后才有内容）
③ 云端状态       实例是 Running 还是 Stopped
```

**空闲时长怎么算**：

```python
idle_since = max(最后一个作业的结束时间, 实例的 StartTime)
```

不能用 `CreateTime`：一台实例可以活 8 小时跑 20 个作业，
按创建时间判会在第 45 分钟就把它腰斩。

**规则 B 让路**：队列里还有同 `model_key` 的待跑作业 → 不清理。
否则「A 跑完、B 还没被领取」的瞬间会关掉机器，B 起来要重新建机 + 装模型。

**默认 `stop` 不是 `terminate`**：关机后算力费归零、系统盘 ≤100G 免费、
保住磁盘上的 ComfyUI + 权重软链，下次 start 只要 ~12s。销毁不可逆。

### P0.5 · 修 `reap_instances`（`tools/p2/scheduler.py`）

老实现的三处问题：

```python
def reap_instances(ttl_min: int = TTL_MIN):
    """超 TTL 且没有活跃队列项的 p2-* 实例 → terminate。"""   # ← 注释这么说
    active = {...}        # 算出来
    name = str(...)       # 算出来
    if age_min >= ttl_min:   # ← 只判创建时长，active/name 从没用过
```

实测：函数体里 `active` 只出现 1 次（赋值那行）。现在整块委托给 `reaper.reap()`。

`TTL_MIN = 45` 也去掉了 —— 统一由 `reaper.idle_minutes()` 提供（默认 10，
`P2_IDLE_REAP_MIN` 可调），避免两处配置漂移成两个数。

### P1 · 并发口径改分组（`tools/p2/concurrency.py`）

```python
def slots_used(jobs_dir=None) -> int:
    return len(groups_used(jobs_dir))     # 数**模型分组数**，不是作业数
```

效果：

| 提交 | 改之前 | 改之后 |
|---|---|---|
| 5 份 `qwen_image_t2i` | 占 5 个槽，撞上限 2，第 3 份降级 | **1 个槽** |
| 3 份不同模型 | 3 个槽 | 3 个槽 |

### P2 · `tools/p2/instance_slots.py`（新增，约 350 行）

槽位表：让「一台实例」成为长生命的一等公民。

```python
group = model_key
条件  = 目标工作流的节点/资产 ⊆ 该实例的「已验证集」
```

**为什么不按裸 `model_key`**：实测同模型的不同工作流节点集能差 6–9 类。

**为什么不按 `workflow_key`**：太碎。`sdxl_juggernaut` 那 5 个工作流
**全部共用同一份** `juggernautXL_v8Rundiffusion_V8.safetensors`，分 5 台机纯浪费。

#### 施工中踩到的一个坑（值得记）

第一版把节点检查写成「算子集 ⊆ `verified_nodes`」，结果：

```
sdxl_img2img  → 换机器（缺 ImageScale, LoadImage, VAEEncode）
sdxl_inpaint  → 换机器（缺 ImageBlur, ImageToMask, LoadImage）
```

**每个工作流都换机器，规则 B 直接失效。**

根因：我把两种"缺节点"混为一谈了。

| 类型 | 含义 | 处置 |
|---|---|---|
| 镜像里没有 | 这个工作流根本跑不了 | 换机器也没用 |
| 这台上没跑过 | 只是没验证过，多半能跑 | **不该拒** |

`ImageScale` / `LoadImage` / `VAEEncode` 都是 ComfyUI **内置节点**，每台实例都有。

**改法**：节点判定用 `image_node_classes()`（镜像能力快照 1757 类），
**不是** `verified_nodes`；资产才用已验证集（`{{UPSCALE_MODEL}}` 这类占位符
指到的具体文件，只有真跑过才知道在不在）。

修完后：

```
sdxl_t2i        → 复用
sdxl_img2img    → 复用
sdxl_inpaint    → 复用
detail_polish   → 复用
sdxl_t2i_lora   → 复用
```

而镜像真缺节点的仍然拒绝：

```
pack_image_qwen_image_2_1_image_edit → 拒绝
  「镜像缺节点类：QwenImage21Cache, TextEncodeQwenImage21（换机器也没用）」
```

#### 产物会冲突吗（已核实不会）

`tools/p20/render.py:149` 用 `job["job_id"]` 当 `filename_prefix`：

```python
graph, meta = render(wf, model, res["params"], job["job_id"], ...)
```

实测产物名形如 `00-primary-p1-20261108T1352-3d1616_00001_.mp4` ——
每条作业的输出天然带自己的 id，同一实例上多条作业不会互相覆盖。

### P2 · `tools/p1/run.py` 接入

新增 `_try_borrow_slot()`，在 `step_provision` **开头**先试复用：

```python
def step_provision(job, opts):
    borrowed = _try_borrow_slot(job, opts)
    if borrowed:
        ...登记实例（信号兜底要用）...
        return borrowed          # ← 不建机
    ...原有建机逻辑...
```

`step_release` 对应加分支：

```python
if ctx.get("borrowed"):
    slots.touch(uid, job_id=..., busy=False)
    return                       # 不销毁，等下一单或空闲回收
```

`step_done` 里登记「这台机器上跑成功过这个工作流」——
这是「已验证集」的来源。

新增两个开关：

| 参数 | 作用 |
|---|---|
| `--no-borrow` | 不复用现成实例（调试/对比基准时想要干净机器） |
| `--slot-parallel` | 允许塞进正忙的槽位（同实例并行，默认关） |

### P3 · 调度器按分组限流（`tools/p2/scheduler.py`）

`self.slots` 限制的从「同时几个作业」改成「同时几个**模型分组**」：

```python
while len(self._active_groups()) < self.slots:
    item = queue.claim(WORKER)
    ...
```

作业之间的串行复用由 `run.py` 自己的 `_try_borrow_slot()` 决定 ——
调度器不用盲管一层，否则状态会分裂成两份。

### 部署

`deploy/systemd/p2-reaper.service` + `.timer`（每 5 分钟）。

独立于调度器：清理是**安全兜底**，必须在调度器停摆时照样活着
（上一轮实测调度器停用了一周）。

**默认未启用** —— 不擅自开定时任务，等你 P6 验证后再装。

## 7. 一个需要你知道的行为变化

**作业结束后不再销毁实例**（借用的那些）。

以前：作业 DONE → `release` 销毁机器 → 下次重装（SDXL 21s / Qwen 53s）
现在：作业 DONE → 归还槽位 → 机器留着 → 下一条直接跑

**代价是机器会多开一会儿**，由 reaper 在 10 分钟后关掉。
如果你某个工作流只跑一次就再也不用了，这 10 分钟是净成本（¥0.36）。

**如果觉得不划算**：`P2_IDLE_REAP_MIN=3` 可以把窗口压到 3 分钟
（但会打断"跑完一条、1 分钟后又来一条"的连续性）。
