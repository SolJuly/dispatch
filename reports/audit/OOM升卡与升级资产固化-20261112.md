## 二、OOM 自动升卡

### 2.1 修的是哪个洞

改造前，一条作业撞上显存不足：

```
step_wait 探测到 ComfyUI 进程没了
  → raise RunError("疑似显存不足/崩溃", FAILED_RUN)
  → 保留实例 15 分钟等人工 --resume
  → 人来了，--resume，还是同一张 24G 卡
  → 同样的地方以同样的方式 OOM
```

**钱花了两遍，结论一遍都没多。**

根因不是"没人写重试"，而是**整条链上没有任何地方记录「上次失败是因为显存」这个事实**：

```
required_gpu  提交时写死的列表，从不改变
_pick_gpu     只按"有没有货"挑，不看显存
RunError      只有 fail_state，没有失败原因的结构化字段
```

### 2.2 三道闸，缺一个就变成烧钱机器

自动重试的风险不是不生效，是**无限生效**。

| 闸 | 判据 | 不过时 |
|---|---|---|
| **① 判定闸** | 日志里**确诊**显存不足（`classify_oom() == "certain"`） | 进程崩了但没 OOM 字样 → 不升卡 |
| **② 次数闸** | 最多升 2 次（24G → 48G → 80G） | 到上限即停 |
| **③ 预算闸** | **已花 + 将花** < `budget.max_cost` | 不够就按普通失败处理 |

任何一道不过 → **行为与加这个功能之前完全一致**（保留实例、提示 `--resume`）。
这是刻意的：不改变既有语义，只是多一条出路。

#### 判定闸为什么要这么严

进程消失的原因至少有四种，**只有前两种换大卡有用**：

| 原因 | 换大卡有用？ |
|---|---|
| CUDA OOM | ✅ |
| 被系统 OOM killer 杀（dmesg `Killed process`） | ✅ |
| 段错误 | ❌ 换个卡一样崩 |
| 我们自己的代码抛异常退出 | ❌ |

判错的代价是 **¥3.80/h 重跑一遍，然后在同一点以同样方式失败**。

所以 `_oom_evidence()` 会真去读远端日志（`/root/comfy_run.log` /
`/root/ComfyUI/comfy.log` / `comfyui_8188.log` / `comfy.out` 四选一），
外加 `dmesg | grep 'killed process'`。"崩了但没证据"归 `likely`，
默认不升卡（`P1_OOM_ESCALATE_ON_CRASH=1` 可开，那是赌博，用户自行承担）。

还有一个反向判据：`_OOM_NOT` 里的字样说明**不是**显存问题，即使同时出现 OOM 字样。
典型例子 `use_missing_models: out of memory checkpoint.safetensors` ——
权重名里就有 "out of memory"，按关键词匹配会误触发升卡。

#### 预算闸为什么必须算"已花"

早期设计只看"这一轮预估 ¥2.85 < 预算 ¥3"，会放行，然后这一单实际花 ¥5.35。

```
预算 ¥3.00
第一轮 24G 烧了 ¥2.50
第二轮 48G 预估 ¥2.85
只看单次 → ¥2.85 < ¥3 ✅ 放行
算上已花 → ¥5.35 > ¥3 ❌ 拒绝
```

"这条作业有没有超支"的定义就是累计，不是单次。

`已花` 的口径也纠过：按 `instance.hourly`（建机时 `cs.price()` 的实时返回）算，
**不用**静态价格表。表过期会让"已花"偏低 → 预算闸在已经超支时放行。

### 2.3 显存阶梯（2026-11-12 实测）

库存与价格都是实时查的：

| 卡型 | 显存 | ¥/h | 库存 | 可作升卡目标 |
|---|---|---|---|---|
| `4090` | 24G ✓ | 2.15 | 54 | 起点 |
| `4090_48G` | 48G ✓ | 3.80 | 2 | ✅ |
| `5090` | 32G | 3.99 | 0 | ✅（常无货） |
| `A800` | 80G | 7.36 | 0 | ✅（常无货） |
| `H20` | 96G | 7.50 | 2 | ✅ |
| `A100` | 80G | 10.75 | 1 | ✅ |
| `V100S` | 32G | 1.41 | 1 | ❌ **Volta sm_70** |
| `P40` | 24G | 0.40 | 0 | ❌ Pascal sm_61 |
| `3090` | 24G | 1.19 | 0 | 不比 4090 大 |
| `3080Ti` | 12G | 0.74 | 0 | 更小 |
| `2080` | 11G | 0.42 | 0 | 更小 |

**V100S 显存够（32G）但被排除。** 理由不是价格，是架构：

我们的权重是 int8 / fp8 量化的（`comfy-aimdo` / `comfy-kitchen` 的解码内核），
这些内核要 tensor core。V100S 是 Volta sm_70（无 int8 tensor core、无 bf16），
P40 是 Pascal sm_61（连 fp16 tensor core 都没有）。

升到这两张卡的后果不是"慢一点"，而是**换一种方式失败**，然后再花一轮钱。
跳过理由会打进日志（`skipped_note()`），否则运维看到"V100S 有货为什么不用"
会以为是 bug，或者手动 `--gpu V100S` 绕过去。

### 2.4 只升不降，且下限跨进程生效

`next_targets()` 只返回显存**严格更大**的卡。降级等于把已经证伪的配置再跑一遍。

`instance.oom_escalation.floor_vram` 是那个跨进程生效的字段：

```json
"oom_escalation": {
  "attempts": [{"gpu": "4090", "vram": 24, "hourly": 2.15,
                "minutes": 12.3, "cost": 0.44, "why": "CUDA out of memory ..."}],
  "floor_vram": 48,
  "last_gpu": "4090_48G"
}
```

只要 `floor_vram` 在，**四条路径全都遵守它**：

```
首次运行  ─┐
--resume  ─┼→ _gpu_candidates() 过滤 → 不会再选回小卡
--restart ─┤
升卡重跑  ─┘
```

把下限检查放在 `_gpu_candidates()` 而不是"升卡那一刻"是关键：
升卡发生在 `_run_inner` 的失败分支，真正建机是下一轮 `step_provision` 调
`_pick_gpu()` → `_gpu_candidates()`。放这里，四条路径自动覆盖。

### 2.5 复用路径也必须遵守下限

这条差点漏掉，漏了升卡就是笑话：

```
24G 卡 OOM → 决定升到 48G → 释放 24G 实例 → 下一轮建机前先看槽位
→ 槽位里有另一台同模型的 24G 实例正空闲 → 复用它 → 再次 OOM
```

复用是为了省装载时间（SDXL ~21s / Qwen ~53s），但省 53 秒换一轮失败不划算。
所以 `find_compatible()` 加了 `min_vram` 参数：显存不够的槽位直接不参与复用，
宁可新建一台 48G。

### 2.6 升卡时旧实例必须真销毁

`step_release` 有四条分支，前三条都是"保留"：长任务空转窗口、借来的槽位、预热池。
**升卡的情形一条都不适用** —— 那台机器已经证明跑不了这个作业。

所以 `force_release` 分支排在所有"保留"判断**之前**，且直接 `terminate`：

- 保留长任务窗口 → 一台跑不了作业的机器按 ¥2.15/h 空转
- 保留借来的槽位 → 下一单还会复用它，然后再次 OOM
- 保留预热池 → 下次从池里取出来还是这张小卡

### 2.7 接线错误的代价（这次踩到一个）

我最初把带 `cs.terminate(uid)` 的代码**直接插在 `step_release` 最前面**。
功能是对的，但两个既有测试立刻红了：

```
FAIL: test_long_task_does_not_destroy
  AssertionError: 1941 not less than 1067 : 长任务分支要在销毁之前
FAIL: test_release_does_not_destroy_borrowed
  AssertionError: 1155 not less than 1067 : 借用实例的 return 要在销毁之前
```

它们靠"函数体内第一个 `cs.terminate(` 出现在所有保留分支之后"来守语义。
**测试的判断方向没错**（它守的正是"长任务和借来的实例不该被销毁"），
错的是我的插入方式：强制销毁是一个独立动作，不该在同一个函数体里和保留分支抢位置。

改法：抽出 `_terminate_with_retry()`，`force_release` 分支只调用它。
现在 `step_release` 体内只有一处 `cs.terminate(`（在负责销毁的收尾分支），
两条不变量同时成立。

新增的两个测试从相反方向锁住同一件事：
`test_terminate_helper_is_the_only_terminate_in_release` 断言
`step_release` 里 `cs.terminate(` 只出现 1 次。

### 2.8 另一处接线错误

`step_wait` 里我写了 `state.load_job(job["job_id"])` 去取 gpu。
这炸掉了 `tools/p20/tests/test_run_hooks.py` 的三条测试
（`FileNotFoundError: 作业不存在`）—— 那些测试只构造内存 job。

问题不在测试脆弱，在于**新的判断逻辑不该依赖磁盘状态**。
改成 `_ctx_gpu(job, ctx)`：先取 `ctx["inst"]["GpuType"]`（平台返回的实例描述，最权威），
再退回 `job["instance"]["gpu"]`，都不知道就不猜（`plan()` 会因此拒绝升卡）。

## 三、升级资产固化

### 3.1 新工具 `tools/upgrade_audit.py`

**这件事做过三次了**（v3→v4、v4→0.43、v4→0.45 论证），每次都从零重新推一遍：
哪些节点没了、哪些签名变了、54 条工作流里哪条会死。
2026-11-12 那次靠临时脚本算的，脚本没留下来。

判据不一致的代价是真实的：如果第一次算"安全"而第二次算"不安全"，
决策就取决于当时用了哪个脚本，而不是取决于镜像到底变了什么。

工具只做**离线比对**，不建机、不花钱、不联网：

```bash
python3 -m tools.upgrade_audit audit --target oi-new.json          # 影响面
python3 -m tools.upgrade_audit diff --base A.json --target B.json -v  # 明细
python3 -m tools.upgrade_audit diff --base A.json --target B.json --json
```

四档判据，按危害排序：

| 档 | 含义 | 会死吗 |
|---|---|---|
| `LOST` | 节点类在新镜像里没了 | **会** |
| `OUTPUT` | 输出变短 / 顺序变了 | **会** |
| `INPUT` | 必填输入新增（无默认值）或类型改变 | **会** |
| `ADDED` | 只多了可选输入、多了节点、**输出纯追加** | 不会 |

**四档必须分开统计。** 混成一个数字就等于没说 ——
"变了 765 处"听起来严重，其中 107 处是新增节点（无害）。

### 3.2 这个工具立刻抓出我们一个判断错了

第一版把输出 `[STRING] → [STRING, STRING]` 判成 `OUTPUT` 破坏性变更，
报「破坏性变更 5 处，6 条工作流受影响」。

而真相是：**那 6 条在真机上全部跑通**（全部只用 idx 0）。

判据必须分三种：

```
ob 比 oa 短                  → 真的坏（索引越界）
ob[:len(oa)] == oa 且更长    → 纯追加，无害
数量相同但顺序/类型不同      → 危险（idx 指向了另一个类型）
```

**这类误报的代价比漏报更难发现** —— 它让你因为假警报放弃一次本来可用的升级。

修正后同一份数据：`baseline 1757 → 1818，破坏性变更 0，54 条工作流全部不受影响`。
与真机结论一致。

### 3.3 三次升级的真实审计数据

| 升级 | 基线节点 | 目标节点 | 破坏性 | 受影响工作流 |
|---|---|---|---|---|
| v4 → v4+核心 0.43.0 | 1757 | 1818 | **0** | **0/54** |
| v4 → 裸 0.45.0 | 1757 | 1094 | **765**（全 LOST） | 4/54 |
| v4 → 0.45.0 + 侧载节点包 | — | — | 预期接近 0 | 待测 |

**裸 0.45.0 的 765 个 LOST 全部是自定义节点包**（Impact-Pack / KJNodes /
FaceParsing / SeedVR2 / TTPlanet …）—— 平台镜像只带 ComfyUI 核心，不带我们的
13 个节点包。这是"不能拿裸镜像直接换"的定量证据。

### 3.4 新文档 `docs/升级与新增工作流-坑与正确流程.md`

两条独立流程、20 条坑，每条标注**哪个命令能在花钱之前拦住它**：

| 流程 | 坑数 | 能 ¥0 拦住的 |
|---|---|---|
| 新增工作流 | 8 | 6 |
| 镜像升级 | 9 | 4 |

文档的核心不是"经验总结"，是执行清单。每条坑写四件事：
现象、真因、**本轮能拦 / 不能拦**、以及对应的命令。

拦不住的四条明确列进"已知边界"，不让它们看起来像能自动兜住：
`memfd_create` 类运行时 bug、张量形状、显存峰值、成片质量。

同时把 `docs/新增工作流手册.md` 里"18 条门禁规则"的口径改成实际的 19 条，
并与新文档互相交叉引用。

新增的测试锁的是**具体的坎**，不是覆盖率：

**`test_oom_escalate.py`（31 条）**

- `use_missing_models` 里带 "out of memory" 字样时不算 OOM
- `no kernel image`（cu130 库跑在 cu128 上）不算 OOM —— 换大卡没用
- 已花 ¥2.5 + 将花 ¥2.85 超预算 ¥3 → 拒绝（只算单次会放行）
- `max_cost=0` 是"不限制"，不是"一分钱都不许花"
- 余额读不到时不能当成 0（那会锁死系统）
- 从 4090 只升到 4090_48G，不直接跳 96G
- 5090 库存 0 时不出现；A800 无货时不出现
- 显存未知的卡型拒绝升卡（不猜）
- `apply()` 必须清 `steps`（否则从 wait 而不是 provision 重跑）、作废 `up_at`

**`test_oom_wiring.py`（16 条）** —— 决策对但接线错，结果一样是白花钱

- `floor_vram` 收窄候选 / 列表全太小则从阶梯补 / `--gpu` 人工指定优先
- `_oom_evidence` 四态：确诊 OOM / 日志干净 / dmesg Killed process / 日志读不到
- `force_release` 分支必须排在 `_idle_after_done` 和 `borrowed` **之前**
- `step_release` 里 `cs.terminate(` 只能出现 1 次

**`test_upgrade_audit.py`（21 条）**

- 输出纯追加 → `ADDED`；输出变短 → `OUTPUT`；同长但错位 → `OUTPUT`
- 新增必填项有默认值 → 不算破坏
- `COMBO` 的 spec[0] 是候选列表，必须归一（不归一会全是误报）
- 拿仓库里三份真实快照跑：v4→0.43 必须零破坏、TextGenerate 必须归 ADDED、
  裸 0.45 必须报 >500 个 LOST

最后三条用的是真数据。它们是"上一次踩坑的结论"的存储 ——
红了说明判据被改回去了。
