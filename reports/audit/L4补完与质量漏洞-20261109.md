## 2. 六处真缺口

### A · 并发没有上限 `tools/p2/concurrency.py`（新增）

上一轮把全局串行锁改成作业级锁，并行度从 1 变成「想开几台开几台」。
那把锁解决的是**能不能并行**，没解决**最多并行几个**。

账户 5 台配额，5 × ¥2.15/h = ¥10.75/h，余额 ¥8.15 —— 点五次就烧穿。

两道闸，位置不同：

```
① 提交闸（webui/api.py）  数 job.json 非终态作业，快、无网络，HTTP 层就能拦
② 建机闸（tools/p1/run.py）问平台要 running 实例数，慢但唯一可信
```

**为什么两处都要**：`job.json` 会撒谎。有孤儿实例（进程被 kill、状态卡 RUNNING）时，
本地看只有 1 个作业，云端真实有 3 台机在跑。只信本地就持续超建。

**默认上限 2，不是 5**：配额不是预算。另外实测两条视频作业并行时 4090 会抢显存，
第二条 OOM（钱照扣）。并行度「能开」不等于「该开」。

**满了怎么办：降级，不拒绝。**

```python
defer_reason = ""
if run:
    ok, why = conc.check_slot(jobs_dir)
    if not ok:
        run = False
        defer_reason = why
```

返回 `{"deferred": true, "deferred_reason": "..."}`，作业停在 CREATED。
直接 429 会丢掉用户刚填好的一整套参数（prompt / 输入图 / seed），
那比"躺在 CREATED 等人点执行"难受得多 —— 后者零风险、可随时启动。

### B · 孤儿实例 `tools/p1/run.py`

`run.py` 以前**没有任何信号处理**。worker 被 systemd 重启、Ctrl-C、kill -9、调度器超时强杀
—— 无论哪种，进程消失后**实例还在 Running**，按 ¥2.15/h 继续计费，而 `job.json` 冻在 RUNNING。

两层兜底，因为「优雅」和「暴力」能做的事不同：

| 层 | 覆盖 | 动作 |
|---|---|---|
| ① SIGTERM / SIGINT / SIGHUP | 进程还能执行代码 | `stop_at` 定时关机（N 分钟后），**不销毁** |
| ② 进程直接消失 | kill -9 / OOM / 断电 | 下次建机时查云端对账（A 的建机闸） |

**为什么优先停机而不是销毁**：销毁不可逆，会把正在跑的推理和已产出但没取回的文件
一起干掉。停机是可续跑的（`--resume` 能接上），停机后算力费归零，系统盘 ≤100G 免费。

`stop_at` 失败时才降级到 `terminate` —— 宁可丢一次续跑机会，不留计时炸弹。

### C · 熔断器失明 `tools/p2/spend.py`（新增）

**这是最贵的一个**。三份实现，口径全不一样：

```
tools/p2/scheduler.py:today_cost()   累加 r.get("cost")（不筛 event）
csctl.py:ledger_today_cost()         只累加 event == "cost"
tools/riskmon.py:_today_cost()       转调 csctl，兜底再抄一份
```

**三份都看不见真实扣费**。账本里的记录长这样（今天实测）：

```json
{"event": "job",    "job": "p1-...", "cost": 0.2222}          ← 作业自报
{"event": "settle", "amount": 0.23, "from": 8.38, "to": 8.15}  ← 平台真扣
```

`settle` 记的是 **`amount`**，不是 `cost`。三份都只读 `cost`：

```
today_cost() = ¥0.00      ← 熔断器看到的
真实扣费     = ¥0.86      ← 账本 settle 加起来的
```

熔断阈值 ¥8.00，看到的永远是 0 → **永远不会熔断**。P4 要真机跑 24 条，
没有任何东西拦得住连续烧钱。

**口径怎么定**：`settle` 和 `job` 会重叠（settle 通常已包含那些 job 的花费），
相加会重复计数一倍。取 **max** 而不是求和：

```python
total = max(Σ settle.amount, Σ job.cost)
```

熔断要的是"别让它烧穿"的下界，宁可略微高估也不要低估。

三处现在都转调 `spend.py`，实测都是 ¥0.86。

（顺带证明 C 的严重性：那句 ¥10.91 是熔断器**自己**算的，而它算的其实只是

### E · 运行中预算不复查 `tools/p1/run.py:step_wait`

`max_cost` 以前只在建机前查一次。建机之后就不再管了：

```
预估 20 分钟 ¥0.72 → 实际卡了 40 分钟 ¥1.43 → 静默超支一倍
```

`step_wait` 现在两条上限同时跑，取先到的：

```python
cost_limit = int(cap / hourly * 3600) if (cap > 0 and hourly > 0) else 0
if cost_limit and cost_limit < limit:
    limit = cost_limit
```

**为什么按时间折算而不查余额**：查余额要一次 HTTP 往返，而这里是 5 秒一轮的轮询；
而且余额被多条作业共享，差额不一定是"本作业"花的。按 `hourly × 已跑分钟` 折算
只依赖自己知道的信息，可复算、可解释。

超时报文也分开了 —— 混成一句用户不知道该调帧数还是调预算：

```
预算超时：按 ¥2.15/h 折算，¥1.60 只够跑 44 分钟，已用尽（推理仍未完成）。
推理超时（2400s）
```

用户会以为在跑、实际在等，而他不去点「执行」，作业就永远躺在 CREATED。

## 3. 质量评分：一个会让纯噪声拿满分的漏洞

### 发现方式

参照你给的三个工具（[ComfyUI-VideoQuality-Metrics](https://github.com/jajos12/ComfyUI-VideoQuality-Metrics)、
[ComfyUI-ImageQualityEvaluator](https://github.com/zx725tt/ComfyUI-ImageQualityEvaluator)、
`aigcqa`）的指标清单去核对现有评分，发现原评分**没有任何噪声维度**，于是造了合成噪点验证：

```bash
$ ffmpeg -f lavfi -i nullsrc=s=480x480 -vf "geq=random(1)*255:128:128" syn-noise.mp4
$ python3 -m tools.p2.l5l6 quality syn-noise.mp4
🟢 100.0 A  syn-noise.mp4
        清晰 95.16 · 运动 70.277 · 亮度 127.2 · 范围 255.0 · 变异 0.002
```

**纯雪花视频 100 分 A 级。** 三项都"对"：边缘能量 95.16（正常片 0.9–6.3，清晰度满分）、
每帧都在变（运动满分）、灰度填满 0–255（曝光满分）。结论完全错。

### 根因

**「清晰度」这个指标分不清「细节」和「噪点」。** 两者在高频能量上是同一件事，
区别在**结构** —— 噪点没有结构，细节有。

### 判别方法

先 `gblur` 再量边缘能量，看保留多少：

```
有结构的边缘 → 模糊后塌得慢
噪点          → 模糊后几乎全塌
```

实测（13 条真实素材 + 8 条合成噪点，2026-11-09）：

| 样本 | raw edge | blur edge | 保留率 |
|---|---|---|---|
| syn-noise / n40 / n80 / grain | 30–95 | 3–14 | **10.7–15.0%** |
| v4-wan-i2v（最低的真实素材） | 6.32 | 1.79 | **28.3%** |
| video-10s / 00-primary | 2.45 / 2.78 | 0.96 / 0.95 | 34–39% |
| h3 / wan / seedvr2 系列 | 0.9–1.8 | 0.5–0.8 | 44–55% |

**线定在 20%**：离噪点最高值（15.0%）留 5 个点，离真实最低值（28.3%）留 8 个点，
两边都不贴边。**不能定 25%** —— 会把 `v4-wan-i2v`（28.3%，全库最好的样本）判成噪点。

### 实现

```python
NOISE_KEEP = 20.0   # 模糊后边缘能量保留率 < 20% → 判为噪点/无结构

keep = _noise_keep(st.get("edge_blur") or [], edge)
is_noise = keep is not None and keep < NOISE_KEEP
if is_noise:
    q_sharp = 0.0          # 清晰度项直接否决
    s.issues.append(f"模糊后边缘能量只剩 {keep:.0f}% < {NOISE_KEEP}%：画面是噪点/无结构，不是细节")

cap, why = _bucket_cap(..., noise_keep=keep)   # 封顶 20 分，排在所有检查最前面
```

**封顶 20 分，比"糊"（32）还狠**：糊至少还有内容，噪点是彻底没有内容。
**排在所有检查最前面**：噪点的边缘能量很高，不会触发"糊"的封顶，
顺序错了就永远轮不到它。

**拿不到模糊序列时不表态**（`None`），不当成 0 —— 把 `None` 当 0 会把一次
ffmpeg 抖动变成"这条片子是垃圾"的结论。评分器自己出错时应当不表态。

### 关于参照工具的取舍

| 工具指标 | 要不要接 | 理由 |
|---|---|---|
| PSNR / SSIM / ΔE2000 | ❌ | **全参考**指标，要和参考片比对。我们评的是"这条片子自己好不好"，没有参考 |
| FID / FVD / IS | ❌ | 需要**一批**样本对比分布。单条作业只有一个产物 |
| CLIP / DOVER / FAST-VQA | ❌ | 要 torch + 预训练权重。**评分器不能引入自己的依赖故障源** —— 而且换云浮点差异会让分数变，破坏「换云结果一致」这个目标 |
| Warping / Flickering | ✅ 已有 | 就是现有的 `sharpness_cv`（边缘序列变异系数） |
| **Noise / 结构判别** | ✅ **本轮补上** | 见上 |

`aigcqa` 那类工具的核心是 MOS 预测（要训练数据 + GPU），同样是"评分器自己变成依赖"，
与 `quality.py` 里写死的前提（只用 ffmpeg 的 signalstats，纯标准库）冲突。
