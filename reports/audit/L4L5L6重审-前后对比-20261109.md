### 这一轮真正解决的（6 处）

**① 并发没有上限。** `93ae85f` 把全局串行锁改成作业级锁，并行度从 1 变成"想开几台开几台"。
5 台配额 × ¥2.15/h = ¥10.75/h，余额 ¥8.15 —— 点五次就烧穿。
现在两道闸（提交闸数本地、建机闸问云端）+ 默认上限 2。满了降级成"建作业不执行"，不拒绝。

**② 孤儿实例。** `run.py` 之前**没有任何信号处理**。kill -9 后实例留在 Running 按 ¥2.15/h 计费，
`job.json` 冻在 RUNNING。现在三信号 → `stop_at` 定时关机（不销毁：可 `--resume` 续跑）。

**③ 熔断器失明（最贵的）。** 三份 `today_cost` 实现口径全不同，且都只读 `cost` 字段 ——
而平台真实扣费记在 `settle.amount` 里。

```
today_cost() = ¥0.00      ← 熔断器看到的
真实扣费     = ¥0.86      ← 账本里躺着的
```

熔断阈值 ¥8.00，看到的永远是 0 → **永远不会熔断**。现在三处统一转调 `spend.py`，口径取
`max(Σsettle, Σjob)`（两者重叠，相加会重复计数一倍）。

**④ 僵尸调度服务。** `p2-dispatch` active 了一周，`ExecStart` 指向的 `/root/wt-ui` 已删除。
已 stop + disable，修正版 unit 进仓库（默认不启用）。

**⑤ 运行中预算不复查。** `max_cost` 只在建机前查一次：预估 ¥0.72 实际卡 40 分钟 ¥1.43，
静默超支一倍。现在钱和时间两条上限同时跑，取先到的。

**⑥ 前端显示三态。** 降级时显示"已创建，未执行"+ 原因，不再一律显示"已提交"。

### 仍然缺的

**① 队列形同虚设。**
`jobqueue.py` 有完整 schema（8 状态 + 退避重试 + 租约心跳），但：
- 调度器 `p2-dispatch` 已停用（它跑的代码被删了，且没修好之前不该开）
- **UI 提交直接 `spawn run.py`，从不入队**

所以队列现在是"有轮子没车"。实测 `queue.db` 里 8 条全是历史遗留（4 done / 4 cancelled），
活跃项 0。

有意为之：消费者刚被停掉，入队 = 作业永远躺着没人领，比"停在 CREATED 等人点执行"更糟。

**② 并发上限是硬编码的 2。**
没有"按配额动态算"（账户 5 台，但配额会随等级变），也没有"按余额动态算"（¥8 够开 3 台且留安全余量）。

## 4. 🔴 审计翻出来的最大问题：65% 的钱花在空转上

这是本轮最重要的发现，**不在任何旧报告里**。

```
$ python3 -c "from tools.p2 import spend; ..."

按归因分的花费（全历史 372 条 settle）:
  idle      299 条   ¥ 37.99      ← 机器开着，没跑作业
  job        73 条   ¥ 20.80      ← 真在跑作业
  合计      372 条   ¥ 58.79
```

**空转占 65%，¥37.99。**

按天看：

| 日期 | 空转 | 作业 | 空转占比 |
|---|---|---|---|
| 10-26 | 0.22 | 1.31 | 14% |
| 10-28 | 2.49 | 2.41 | 51% |
| 10-29 ~ 10-31 | 0.71 | 0.00 | **100%** |
| 11-02 | 2.54 | 0.00 | **100%** |
| 11-04 | 4.03 | 0.00 | **100%** |
| 11-05 | **10.66** | 2.75 | 79% |
| 11-06 | 5.38 | 0.31 | 95% |
| 11-07 | 4.82 | 4.32 | 53% |
| 11-09 | 0.78 | 0.08 | 91% |

**有 4 天是 100% 空转**（10-29/30/31、11-02、11-04）—— 那几天一台机开着，一个作业没跑。

### 为什么会这样

三个原因，本轮修了两个：

| 原因 | 状态 |
|---|---|
| ① `run.py` 无信号处理，进程被打断后实例留 Running | ✅ **已修**（定时关机兜底） |
| ② 熔断器失明，空转到 ¥10.66 也不熔断 | ✅ **已修**（认 settle） |
| ③ **`reap_instances` 有缺陷：超 TTL 就 terminate，不看状态** | 🔴 **仍在** |

第③条是本轮审计新发现的，代码在 `tools/p2/scheduler.py:119`：

```python
def reap_instances(ttl_min: int = TTL_MIN) -> list[str]:
    """超 TTL 且没有活跃队列项的 p2-* 实例 → terminate。"""
    active = {i["job_id"] for i in queue.items() if i["state"] in ("claimed", "running")}
    for inst in live_instances():
        age_min = (now - float(created)) / 60
        if age_min >= ttl_min and uid:      # ← 只看 age，完全不看 active
            terminate(uid)
```

**注释说"且没有活跃队列项"，但 `active` 算出来之后一次都没用过**（实测：函数体里
`active` 只出现 1 次，就是赋值那一行；`name` 同样算完就扔）。
判据只有 `age_min >= ttl_min` —— **不看实例状态、不看有没有作业在跑**。

后果有两条，方向相反：
- **该杀的没被杀**：停机实例 `CreateTime` 很老，但 age 判据会一直命中，
  而 `Stop` 之后 `terminate` 又因为别的原因失败时，它就一直躺在列表里
- **不该杀的会被杀**：一条跑 50 分钟的长作业（TTL 是 45 分钟）会被直接 terminate，
  作业中途丢实例

而 `Scheduler._reap_instances()` 是它唯一的调用方，调度器现在停用，
所以**实际上没有任何东西在巡检实例**。

而且这个函数只在 `p2-dispatch` 的 `_reap_instances()` 里被调用，而调度器**已经停用**，
所以现在**完全没有人做实例巡检**。

### 这意味着什么

修好并发闸和熔断器，只是让"未来的钱"不再白烧。
**过去的 ¥37.99 已经烧掉了**，而"没有任何东西在巡检实例"这个状态**现在仍然存在**。
