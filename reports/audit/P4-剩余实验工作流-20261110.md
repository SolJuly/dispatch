## 1. 第一件事：预检自己判错了 4 条

开始 P4 前先跑预检（这是上一轮做的工具）：

```
工作流 54 条 · 可执行 35 · 阻塞 19
```

19 条阻塞里，我看到几个熟悉的名字：

```
no_weight  qwen_image_t2i          缺 qwen25vl7b_std.safetensors, qwen_std_vae.safetensors
no_weight  qwen_image_edit_2509    同上
```

**但这几条是 verified —— 真机跑通过、有作业证据的。**

矛盾。查下去发现预检有两个漏判：

### 漏判 ① 没读 `compat_links.txt`

`tools/p1/compat_links.txt` 记录的是「ComfyUI 里该用什么名字 → 实际指向哪个文件」：

```
text_encoders  qwen25vl7b_std.safetensors  →  qwen2.5vl-7b-bf16.safetensors
vae            qwen_std_vae.safetensors    →  qwen_image_vae.safetensors
```

**名字故意不同，有软链就能用。** 模型卡写的是 ComfyUI 侧的名字（工作流图里引用的就是它），真实文件叫别的名字完全正常。

预检只查 `weights-full.txt` 里 `/model` 下的真实文件名，不读这张映射表 → 判定"缺"。

**这是判据漏了一条证据来源，把已验证说成不可用。**

### 漏判 ② `_match` 区分大小写和连字符

```python
_match("LTX-2.3-ID-LoRA-TalkVid-3K.safetensors", {"contains": "ltx-2.3-id-lora-talkvid-3k"})
→ False     # 明明同一个文件
```

修法：加 `_norm()` 归一（小写 + `-`→`_`），**但只做这两件事** ——
`rank_111` vs `105`、`fp8` vs `int8`、`3b` vs `7b` 必须保持可区分，
归一过头会让作业静默用错权重。

### 修完的效果

```
35 → 40 → 43 条可执行（¥0）
```

多出来的 8 条里，有 4 条是 verified 被误报，4 条是名字写法不同而已。

## 2. 第二件事：真机验证暴露了更深的根因

挑了一条参数最少的（`pack_video_ltx2_3_i2v`：单图 + 提示词）真跑。

### 第一次失败

```
[23:33:41] ⚠ 这些权重在 /model 里没找到：ltx_2.3_22b_distilled_1.1_lora...、gemma-3-12b...
[23:33:44] ✗ 模型资产不可见：['upscale']
```

但我明明补了 `compat_links`。上实例查：

```bash
$ find /model -maxdepth 7 -name "ltx-2.3-spatial-upscaler-x2-1.1.safetensors"
/model/ModelScope/Lightricks/LTX-2.3/ltx-2.3-spatial-upscaler-x2-1.1.safetensors
$ ls /root/ComfyUI/models/upscale_models/ | grep ltx
（空）
```

**文件在，软链没建。**

### 根因：`find -name` 是精确匹配

自动补链的逻辑是「find 找到 → 建软链」。`find -name` 一模一样的字符串才算命中。

```
模型卡写的  ltx_2.3_22b_distilled_1.1_lora_dynamic_fro09_avg_rank_111_bf16
库里真名    ltx-2.3-22b-distilled-1.1_lora-dynamic_fro09_avg_rank_111_bf16
```

差一个 `_` / `-` → find 找不到 → 认为缺失 → 不建软链 → 资产检查失败。

**而文件一直在库里。**

### 三次尝试

| 尝试 | 做法 | 结果 |
|---|---|---|
| ① | `-name` 精确 | ✗ 差连接符就找不到 |
| ② | `-iname` + 全量替换 | ✗ 真名是**混合**写法：前半 `-`、后半 `_`，两种全量替换都不对 |
| ③ | 枚举所有连接符组合 | ✗ 12 段 = 2048 种，为不炸命令行必须截断，截断恰好漏掉最长的名字 |

### 最终做法：不在 shell 里表达等价关系

```python
# 远端只做一件事：把候选全捞回来
find /model -maxdepth 7 -type f \( -iname '*.safetensors' -o ... \) \
    -printf '%f\t%p\n' | head -8000

# 本地归一后比对
def _norm_name(s):
    return s.lower().replace("-", "_").replace(".", "_")
```

实测：3539 行、~4 秒。比拼 2048 个 `-iname` 便宜，且彻底消除这类问题。

### 顺手修的另两处

- **`LOADER_DIRS` 缺 3 个 loader**（`LatentUpscaleModelLoader` / `ControlNetLoader` /
  `UnetLoaderGGUF`），落到默认 `diffusion_models`。upscaler 的软链建到了
  `diffusion_models/` 而 ComfyUI 只在 `upscale_models/` 找 → 看不见。
  这份表和 `tools/p2/preflight.py` 的同名表漂移过，已补齐。

- **`neg_prompt` 默认值是某个人物场景的描述**：
  `"Egyptian royal in blue-and-gold headdress and high collar..." `
  从官方模板原样导入的，与任意提示词都不匹配。换成通用负向词。

### 代价

**两次失败共 ¥0.57，一次推理都没跑 —— 全是资产检查阶段烧的。**

这是这篇报告最该记住的一条：**资产检查应该能在开机前做完。**
现在它发生在开完机、跑完 setup 之后（约 3 分钟），失败就是纯损失。

## 3. 剩余 19 条的真实情况（**修正**）

一开始我把"预检可执行 43"和"compat experimental 19"混在一起说，两者**口径不同**：

- `preflight` 判的是「**结构上跑得起来吗**」 → 11 条阻塞

**所以 19 - 11 = 8 条是「结构齐备、只差一次真机验证」。**
这才是 P4 真正待办的东西，我前面说错了，这里纠正。
