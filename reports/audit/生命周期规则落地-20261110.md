## 1. 一处偏离：策略放在新文件而不是 `concurrency.py`

你清单第 1 项写的是改 `concurrency.py`。我新建了 `tools/p2/lifecycle.py`。

**理由**：`concurrency.py` 的职责是「同时在跑几个作业 / 能不能再开一台」——
是**并发闸门**。生命周期是「跑完之后这台机器留多久、什么时候停机、什么时候销毁」——
是**成本策略**。两者没有共享状态，混在一起会让那个文件同时承担两种判据，
而它现在的注释已经写满了并发相关的推导。

新建文件的收益：`webui` / `run.py` / `reaper` 三方 `from tools.p2 import lifecycle`
就够，不用为了拿一个默认值去 import 一个会读 `jobs_dir` 的模块。

**代价**：多一个文件。如果你坚持放 `concurrency.py`，把这些函数剪过去即可，调用方不用改。

## 2. 生命周期状态机（已实现）

```
作业 DONE
   │
   ├─ 短任务（默认）────► release 立即销毁 → 结束
   │
   └─ 长任务（UI 勾）
        │ 写 idle_after_done_s ∈ {60,90,120} 到 job.json
        │ 不销毁，归还槽位
        ▼
   reaper 每 5 分钟巡检
        │
        ├─ 窗口内（剩 N 秒）──────► keep
        └─ 超窗口 ────────────────► stop（停机 ¥0）
                                       │ 记 stopped_at.json
                                       ▼
                                  停机保留 2 小时
                                       │
                                       ├─ 2h 内来新单 → run.py start 唤醒 62s（清计时器）
                                       └─ 2h 到期 ─────────► terminate（销毁腾配额）
```

### 为什么长任务不在 `run.py` 里自己 sleep 等

`run.py` 是**作业进程**，它 sleep 就占着作业锁、占着并发槽位、日志还在滚。
而"等下一单"本质是**实例**的状态，不是作业的状态。

所以 `run.py` 只负责把「该等多久」这个事实写进 `job.json`，由 `reaper` 执行停机。

**代价：停机精度是 5 分钟（巡检间隔），不是 90 秒。** 这个精度够用——
90 秒窗口的意义是「下一单能复用」，而复用由 `_try_borrow_slot` 在**提交瞬间**就完成，
不依赖 reaper。reaper 只负责「没人来的时候别一直烧钱」。

## 5. 施工中发现的 4 个真实缺口（都已修）

前两个是**上真机才会暴露**的，属于这一轮的主要收获。

### 5.1 停机计时器用 `-1` 同时表示两种语义 → 实例永不销毁

```python
# 修之前
def stopped_remaining_min(uid):
    if not since:
        return -1.0            # 不可判
    return round((since + ttl*60 - now)/60, 1)   # 已过期也是负数！
```

停机 **121 分钟**的实例算出来是 `-1.0`，和「没有记录」的哨兵撞在一起，
于是被当成「不可判」→ 永远保留 → **5 台配额被僵尸实例吃满，新任务报 8903**。

改成 `None` 表示不可判，负数只表示已过期。

### 5.2 定版之前停掉的实例没有记录 → 永久保留

`stopped_at.json` 是这一版才有的文件。仓库里那台 `uhost-1xhk1c21vlfw`
已经停机 **21 小时**，一条记录都没有。

按「无记录就不销毁」处理，它永远占着配额。加了两条兜底：

1. **账本回查**：本地没记录时查 `.compshare/ledger.jsonl` 的 `stop`/`terminate` 事件
   （实测那台有 2026-11-09 11:36:21 的 stop）
2. **认领**：仍然拿不到时间的，从「第一次被看到停机的时刻」起算保留期。
   起点**晚于**真实停机时刻，所以保留期只会更长、不会更短，不会误杀

### 5.3 陈旧停机记录会误销毁刚跑完的机器

「停过 → 被唤醒 → 又跑过 → 又停了」的实例，本地记的还是老时间。
按老时间算得出「已过期」，一停机就被销毁。

实测那台就撞上了：账本 stop 是 `11-09 11:36`，而云端 `StartTime` 是 `11-09 18:27`——
账本那条早于本次开机 7 小时，是陈旧记录。

加守卫：**停机起点必须 ≥ 本次开机时刻**，否则当「时长未知」保留。
为正反两条都写了测试（`test_adoption_timestamp_after_start_is_trusted`）。

### 5.4 账本路径从可替换的全局推导 → 兜底逻辑在测试里静默失效

`_ledger_stop_ts` 一开始写的是：

```python
p = _stopped_path().parent.parent.parent / ".compshare" / "ledger.jsonl"
```

单测把 `STOPPED_JSON` 指到临时目录后，账本就永远找不到——
**兜底逻辑在测试里静默失效，真实环境才暴露**。

改成独立常量 `LEDGER_JSON`，并加了 `test_ledger_path_is_independent_of_stopped_json` 锁死。

### 5.5 一处测试污染（已清理）

改测试前那次失败的运行用了真实 `jobctl`，把作业写进了 `reports/p1/jobs/p1-20261110T1038-4f0c6e`。
发现后立即删除，目录回到原来的 6 项。

### 8.1 一个查过、不成立的担心

我一度担心：`_try_borrow_slot` 第一行是 `if not _registry_meta(job): return None`，
如果 UI 提交的作业没有 `model.registry`，那它们**勾了长任务就是付空转钱但拿不到复用**。

**核实结论：不存在这个问题。**

`p20ctl._make_spec()` 会**无条件**把 `registry_meta` 放进 `spec.model.registry`：

```python
registry_meta = {"workflow_key": ..., "model_key": ..., ...}
return {..., "model": {..., "registry": registry_meta}}
```

而 `webui.api.create_job()` 一定走 `_make_spec`。所以 UI 提交的作业 100% 带 meta，
复用路径成立，空转窗口的成本逻辑（省 ¥0.036 vs 花 ¥0.054）是真在算的。

实测：

```
python3 tools/p1/jobctl.py new --spec <qwen_image_t2i 的 spec>
→ spec.model.registry = {"workflow_key": "qwen_image_t2i", "model_key": "qwen_image", ...}
→ job.json 里同样有 model.registry
```

加了两个测试锁死这个前提（`TestBorrowPrecondition`）：
① `_make_spec` 一定产出 registry meta；② 读源码确认那段赋值里没有 `if`
——防止哪天有人把它改成条件化的，UI 提交的作业静默掉进 legacy 分支。
