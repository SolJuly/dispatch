# 提交后自动跑：`auto_run` 补位机制

日期：2026-11-12
触发：用户选「提交后自动跑要好一点」，放弃开常驻调度器那条路。

---

## 为什么不用现有调度器

`tools/p2/scheduler.py`（`batchctl run`）从 **queue.db** 领活，而
`jobqueue.enqueue()` 没有调用方 —— UI 提交的作业根本不进 queue.db。

实测它启动后：

```
[sched] 启动：slots=1 gpu=4090 hours=1.0 daily_cap=¥3.0 quota=5
[sched] 预算 当日 ¥1.08 / ¥3.00 · 配额剩余 5 · 槽位 1
[sched]   队列为空，无事可做
```

而且 `p2-dispatch.service` 配的是 `Restart=always` + `RestartSec=15`，
调度器又是「队列空就退出」—— 开了会变成**每 15 秒重启一次的循环**。

所以走另一条：`webui.api.run_jobs()` 这条实际在用的路径，但**不用常驻进程**。

---

## 设计：事件驱动，不是轮询

「有空槽了」**只可能发生在某个作业结束之后** —— 那是唯一让出槽位的事件。
所以把补位挂在终态上，延迟是零，也不需要常驻进程。

```
作业进入终态 → run.py 调 autostart.after_terminal()
             → 扫一遍 auto_run 且 CREATED 的作业
             → 还有空槽就拉起最靠前的那个
```

例外：进程被 `kill -9` 时不会走终态，也就不会触发补位。那种情况由
`jobs_reconcile.py`（cron 每 15 分钟）收尾；再漏的，用户点一下「执行」。

---

## 关键区分：两种 CREATED 不是一回事

这是整个功能最核心的一点。

| 用户操作 | 提交时 | 结果 |
|---|---|---|
| 勾了「立即执行」，并发有空 | 直接跑 | — |
| 勾了「立即执行」，**并发已满** | 降级成只建作业 | **`auto_run: true`** → 排队，前面跑完自动开始 |
| **没勾**「立即执行」 | 只建作业 | 无此字段 → 一直等人点「执行」 |

第三种绝不能自动拉起 —— 那会花他没打算花的钱。

---

## 并发判据用「模型分组」，不是作业条数

```python
cap = conc.max_parallel()      # 默认 2
used = conc.slots_used(root)   # 不同模型的分组数
room = cap - used
```

同一模型的多个作业会挤在一台机器上**串行**（`run.py` 的 `_try_borrow_slot()`
负责挂靠），所以它们只占 **1 个槽**。

按作业条数判的话，5 份同模型的活会被错当成"占满 5 槽"而全部拒绝 ——
那台机器明明还能接活。

与提交时的 `check_slot` 是**同一口径**，两处不会打架。

### 为什么用 `_with_autostart` 包一层

`run()` 里的 return 点有七八个（成功／各类失败／abort／salvage／restart／
异常）。逐个加补位必漏，而漏掉的那条路径会让后面排队的作业**永远卡住**。

包一层之后只管一个地方，并且**必须判终态**：

```python
if st not in state.TERMINAL:
    return rc      # 失败但保留实例等 --resume，槽位没真让出来
```

否则"保留实例待续跑"那种情况会被误判成让出了槽位，下一个作业撞上并发上限
白白失败一轮。

## 真机验证

用最便宜的 `flux2_klein_4b_fast`（4 步，约 1.7 分钟），建两条 `auto_run` 作业：

```
00:35:xx  两条作业 CREATED，auto_run=True
00:36:00  手动启动作业1 → PROVISIONING
00:38:30  作业1 RUNNING
00:38:53  作业1 DONE（1.8 分钟 ¥0.0645，质量 A）
          └─ 同一秒：▶ 自动启动 p1-20261112T0035-6295bc（并发 2/2 组）
00:41:20  作业2 RUNNING
00:42:10  作业2 DONE（1.6 分钟 ¥0.0573）
```

**作业 1 结束到作业 2 启动，间隔 0 秒。**

两单共 ¥0.12。余额 ¥18.04 → **¥17.92**。0 台实例在跑。

> 附带收获：`flux2_klein_4b_fast` 质量评级 A，1.8 分钟 ¥0.06 —— 是目前
> 跑过的工作流里性价比最高的一个，适合做日常验证。

## 测试

**Python 862**（p20 211 / p1 127 / webui 167 / p2 357）+ **JS 6 个文件**，全绿零跳过。

新增 18 条覆盖：

- 只挑 `auto_run` 的，不碰其他人的
- 按创建时间先来先跑
- 按模型分组判并发
- 没槽时不启动、读不到并发状态时保守不动
- 启动子进程失败不拖累后面的
- 坏 job.json 跳过
- 源码接线：意图写入 + 终态触发，断任何一处功能就是死的

顺手修掉一个测试缺陷：`submit_deferred.test.js` 原来**手抄了一份渲染模板**，
源码改了它不知道，于是报"文案没说明没执行"——而源码早就说清楚了。
改成从 app.js 真实抽取那一段，源码怎么改测试就怎么变。
断言也从「必须是某个具体字符串」改成「必须表达这个意思」。

## 现在的完整行为

```
提交（勾了立即执行）
  ├─ 有空槽 → 立刻跑
  └─ 并发满 → 排队（auto_run）
                ├─ 前面的作业结束 → 同一秒自动开始
                └─ 用户也可以手动点「执行」提前跑

提交（没勾立即执行）
  └─ 一直等，点「执行」才跑
```

排队期间不占 GPU、不花钱。

## 剩下的

1. **`kill -9` 的作业不会触发补位**（不走终态）。由对账 cron 兜底，
   最坏延迟 15 分钟。要更快得给 run.py 加独立的心跳看门狗。
2. **`queue.db` 那条路还是死的**。要么把 `enqueue()` 接上，
   要么把队列页去掉 —— 现在是「能看不能喂」。
3. **`p2-dispatch.service` 仍是 disabled**。有了 auto_run 补位，它更没必要了；
   建议保持关闭，并把 service 文件标注清楚"与 auto_run 功能重复"。
