# 队列禁用（不删）

日期：2026-11-12
决定：用户定「enqueue 先不忙着删，禁用就行」。

---

## 为什么禁而不是删

队列本身**没坏**：`enqueue()` 实现完整、`claim()` 原子、心跳/退避/审计
都有测试覆盖。坏的是**没有生产者** —— UI 提交的作业直接写
`reports/p1/jobs/`，从不进 queue.db。

于是它唯一还在起作用的地方是让界面数字互相矛盾：

```
「完成 20 / 失败 26」     ← job.json 的 47 条（真实）
「已完成花费 ¥7.35」      ← queue.db 的 8 条历史残留
                            真实花费是 ¥3.86，差一倍
```

969 行代码一行没删，随时可回滚。

---

## 最容易踩的坑：删文件 ≠ 禁用

`connect()` 原本长这样：

```python
def connect():
    DB.parent.mkdir(parents=True, exist_ok=True)
    _ensure_schema()
    c = sqlite3.connect(str(DB))
    c.executescript(DDL)          # ← 建表
    ...
```

**任何一次只读调用都会把删掉的库重新建出来。** 实测确认：

```
删库后存在: False
stats():    {'total': 0, 'by_state': {}}
调用后存在: True          ← 真被重建了
```

所以「删掉 queue.db 文件」根本不算禁用 —— 下次谁读一次它就回来了，还是个
空库，继续骗人。

**这也是为什么闸必须放在 `connect()` 里**，而不是各函数各自判断。

---

## 实现

```python
ENABLED = False        # 模块默认关
P2_QUEUE_ENABLED=1     # 环境变量可临时打开（排障/回滚，不用改进程）
```

`connect()` 第一行就挡：

```python
if not is_enabled():
    raise QueueDisabled(_disabled_note())
```

然后分两类处理：

| 类型 | 行为 | 理由 |
|---|---|---|
| **读**（stats / items / claim / stale …） | 返回空结果，**不抛** | 读方都是一次巡检里的附加信息，为一条读不到的队列让整轮巡检崩掉不值当 |
| **写**（submit / finish / cancel …） | 抛 `QueueDisabled` | 静默丢弃会**丢作业** —— 调用方以为提交成功了，实际什么都没记下 |

## 加开关时挖出的真 bug

改完之后跑测试，`instances.snapshot()` 直接崩了：

```
File "tools/p2/instances.py", line 229, in _audit_rows
    c = queue.connect()
QueueDisabled: 队列已禁用（没有生产者）...
```

`_audit_rows()` 里 `connect()` 写在 `try` **外面**：

```python
c = queue.connect()      ← 在 try 外
try: ...
```

它不属于 `queue.items()` 那种有 `is_enabled()` 保护的路径，所以异常穿透了，
**实例页直接 500**。

修法是把 `connect()` 挪进 try。同时加了一条 AST 静态检查，防止别处再犯 ——
这类"绕过闸"的调用运行时测试覆盖不到所有调用点，漏一个就是一个页面的 500。

## 连带修掉的欺骗性显示

禁用后 `stats()` 返回 `{"total": 0}`，而**"0 项"和"队列空着待命"长得
一模一样**。照实显示会让人以为这套机制在正常工作。四处都改了：

| 位置 | 改前 | 改后 |
|---|---|---|
| `/api/p2/queue` | `total: 0` | `enabled: false` + 说明 |
| `/monitor` 页面 KPI | 「队列待跑 0」 | 「队列已禁用 —」 |
| `/monitor` 队列表 | 「队列为空」 | 「队列已禁用（没有生产者）…」 |
| `arch.py` 架构图 | 「队列 0 项」 | 「队列：已禁用（无生产者）」 |
| `riskmon` R17/R18 | 「队列为空」 | 「P2 队列已禁用（无生产者，跳过）」 |
| `status2.json` | `{"total":0}` | 加 `"enabled": false` |
| 前端 SPA | 每轮轮询 `/queue` | 不再请求（注释说明如何恢复） |

## 测试

**905 条全绿**（p20 211 / p1 143 / webui 167 / p2 384）+ JS 6 个文件，零跳过。

新增 27 条（`test_queue_disabled.py`）：

- 12 个读接口禁用后返回空
- 7 个写接口抛 `QueueDisabled`
- **禁用时绝不创建数据库文件**（"真禁用"的判据）
- 开关能真的打开并工作（不然"随时可回滚"是空话）
- `ENABLED` 默认必须是 `False`（锁住产品决定）
- 服务端/架构图/看板/riskmon 都如实报告"已禁用"
- 前端不再请求 `/queue`，但 `dispatch` 保留

顺手修了两处测试自身的问题：

1. **三个测试文件**（test_queue / test_idempotency / test_scheduler）在
   `setUp` 里显式设环境变量启用队列 —— 它们测的就是队列本身，
   改 `ENABLED` 常量会污染同进程里别的用例
2. **AST 检查的第一版是文本匹配**，把 docstring 里的示例代码
   `c = queue.connect()  ← 在 try 外` 当成了真实调用误报。
   改成 AST 后按 `try` 覆盖的行号判断"是否被保护"，
   并用 bad.py / good.py 实测确认它真能抓错、也真能放过对的

## 要恢复时怎么做

```bash
# 1. 拷回归档（如果要历史数据）
cp reports/p2/archive/queue-disabled-20261112.db reports/p2/queue.db

# 2. 打开开关（二选一）
#    a) 临时：环境变量，不用改代码
P2_QUEUE_ENABLED=1 python3 tools/p2/batchctl.py run
#    b) 长期：改 tools/p2/jobqueue.py 里的 ENABLED = True

# 3. 但**必须先接上生产者**
#    否则就是回到"没有生产者"的原点。
#    需要接的地方：webui.api.create_job() 里，jobctl new 之后
#    加一句 queue.submit(...)。
```

第 3 步是关键：**开关只是让队列不撒谎，不解决"没人往里放活"**。
