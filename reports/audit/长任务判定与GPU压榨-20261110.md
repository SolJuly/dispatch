## 0. 先把你的判断用数据验证一遍

你说：

```
同一个工作流 h3_t2v_121f，跑过三种时长：
  273s   frames=121  768×512  steps=20
  516s   frames=241  768×512  steps=20
  641s   frames=240  768×512  steps=25
```

**同一个工作流，最长和最短差 2.3 倍。**

反向的例子也有：

```
video 类里面也有一批只跑 33–41 秒的（frames=73, 768×512）
而 image 类里有跑 88 秒的（qwen_image_t2i, 1024², steps=20）
```

所以 **`kind: video` ≠ 长任务，`kind: image` ≠ 短任务**。

## 1. 到底是什么决定了时长

我把 23 条实测按「推理秒数 / (宽×高×帧数)」归一化：

| 推理 | 帧数 | 分辨率 | 步数 | s/百万像素帧 |
|---|---|---|---|---|
| 641s | 240 | 768×512 | 25 | **6.79** |
| 516s | 241 | 768×512 | 20 | **5.45** |
| 443s | 80 | 640×640 | — | 13.52 |
| 282s | 49 | 832×480 | 20 | 14.41 |
| 278s | 251 | 1280×768 | 45 | **1.13** |
| 273s | 121 | 768×512 | 20 | 5.74 |
| 41s | 73 | 768×512 | — | 1.43 |
| 33s | 73 | 768×512 | — | 1.15 |

**同样 73 帧 768×512：有的 33 秒，有的 641 秒 —— 差 19 倍。**

差异来自三处，按影响从大到小：

| 因素 | 影响 | 证据 |
|---|---|---|
| **① 模型架构**（步数/蒸馏/量化） | **最大**，可达 19 倍 | 同为 73 帧 768×512，33s vs 641s |
| **② 帧数 × 分辨率**（总像素） | 线性 | 121f→240f，273s→641s（2.0×→2.3×） |
| **③ 步数** | 线性 | 20 步 vs 45 步，明显差异 |

所以「长任务」的判定不能看工作流名字，得看**这批参数实际要算多少**。

## 2. 三层判定：估算 → 用户声明 → 实测校准

### 第 1 层：估算（默认，零成本）

用「工作量」估：

```
work_units = 宽 × 高 × 帧数 × 步数 / 1e6
```

但**同一 work_units 在不同模型上的秒数差 19 倍**，所以必须乘上
每个模型的「速度系数」。

**问题：49 张模型卡没有任何一张声明显存或速度。**

现状核实：

```python
# registry/models/*.json 的字段
['schema','key','name','version','kind','family','primary',
 'files','defaults','constraints','setup','notes']
# 没有 perf / speed / latency / bench / throughput
```

**这是必须先补的数据结构。** 建议给模型卡加：

```json
"perf": {
  "s_per_mpx_step": 0.28,        // 每百万像素每步的秒数
  "source": "measured",           // measured | estimated
  "samples": 23,                  // 实测样本数
  "gpu": "4090",                  // 在什么卡上测的
  "measured_at": "2026-11-07"
}
```

有了这个，估算就有据可依：

```
预计秒数 = 宽×高×帧数/1e6 × 步数 × s_per_mpx_step
```

拿现有 6 条数据反推 `s_per_mpx_step`：

| 工作流 | 实际秒 | 推算系数 |
|---|---|---|
| h3_t2v（741 帧步） | 641 | **0.87** |
| h3_t2v（121f/20步） | 273 | **0.30** |
| wan2_2_i2v | 462 | 待算 |
| ltxv_2b_t2v（251f/45步） | 278 | **0.03** |
| 73f/768×512（快模型） | 33 | **0.15** |

**跨度 0.03 – 0.87，28 倍。** 这就说明为什么必须按模型标定，
不能用一个全局系数。

### 第 2 层：用户声明（显式覆盖）

估算会错，因为模型的 `s_per_mpx_step` 可能是估的、参数可能超出标定范围。

所以要给用户一个**显式的开关**：

```
任务提交时的选项：
  ○ 短任务（< 2 分钟）—— 默认，按 90 秒窗口回收
  ● 长任务（按估算，> 5 分钟）—— 整个任务期间独占实例、不回收
  ○ 自定义预计时长 [__] 分钟
```

**这一层最重要**，因为：
- 用户自己知道自己要跑什么（比如"我这个是 4K 60 帧 10 秒的片子"）
- 估算只能看参数，看不到"我要连跑 20 条"这种意图

### 第 3 层：实测校准（持续学习）

每跑完一条，把「实际秒数 / work_units」回写到模型卡：

```
s_per_mpx_step = 加权平均(历史实测)
```

这样模型卡会**越跑越准**。第一条可能估错，跑 3 条之后就准了。

**这也是唯一能弥补"19 倍差异"的机制** —— 因为差异来自模型架构，
只能靠实测标定，推不出来。

## 3. 「压榨 GPU」到底指什么

你说的「用户在进行长时间任务的时候，尽量压榨完 GPU 性能」。

我把实测数据摆出来，说明**压榨的正确手段不是"并行塞任务"**：

### 3.1 batch_size 的边际收益（M1 实测，4090）

| 分辨率 | batch | 显存峰值 | 总耗时 | **每张** | 相对 batch1 |
|---|---|---|---|---|---|
| 1024×1024 | 1 | 23.1 GB | 74.1s | 74.1s | — |
| 1024×1024 | **2** | 20.8 GB | 48.0s | **24.0s** | **+68%** |
| 1024×1024 | 4 | 22.6 GB | 146.6s | 36.7s | +51% |
| 768×1024 | 2 | 22.6 GB | 34.0s | 17.0s | — |
| 768×1024 | **4** | 22.0 GB | 65.3s | **16.3s** | +4% |
| 512×512 | 4 | 20.3 GB | 21.4s | 5.3s | — |

**但这组数据有个自相矛盾的地方，必须先指出来：**

报告的**文字结论**写「耗时随 batch 增长」，但**数字**是：

```
1024×1024  batch=1  →  74.1s
1024×1024  batch=2  →  48.0s    ← 比 batch=1 还快？违反直觉
1024×1024  batch=4  →  146.6s
```

batch=2 比 batch=1 快 35%，这在物理上说不通（batch 大只会更慢）。

**合理解释**：这两条大概率不是同一次运行 —— batch=1 那条可能是**冷启动**
（含模型装载），batch=2 那条可能在同一进程里紧接着跑（模型已在显存）。
报告没写测量顺序，无法确认。

**所以这张表只能得出一个可靠结论**：

```
batch 从 2 → 4：48.0s → 146.6s，每张 24.0s → 36.7s
→ 加 batch 不是免费的，1024² 上 batch=4 明显更差
```

其他横向对比（batch1 vs batch2）**不可信，需要真机重测**。

**这条我要标注为待验证项，不能拿它当"快 3 倍"的依据。**

### 3.2 所以「压榨 GPU」有三条路，优先级如下

| 手段 | 收益 | 风险 | 该不该做 |
|---|---|---|---|
| **A 选对 batch_size** | 每张最多快 34%（2→4 那些） | 无（已有参数） | ⚠️ 先补测再定默认值 |
| **B 同实例串行排队** | 省装载 ~113s/条 | 无 | ✅ 已在 P2 做了 |
| C 同实例并行塞任务 | 提高 GPU 利用率 | **OOM 风险**（Qwen 23.7GB/24GB） | ⚠️ 只在 48G+ 卡开，默认关 |

**但"该设多少"现在还不能定** —— 因为上面那张表有一半数据不可信。

**能确定的是**：
- `batch_size=1` 是**保守但正确**的默认（不会 OOM、不会变慢）
- 无脑调到 4 是错的（1024² 实测每张从 24s 劣化到 36.7s）
- 768×1024 batch=4（每张 16.3s）看起来可信，因为 34.0s→65.3s 是单调增长的

**要做的是**：P6 真机补测 1024² 的 batch=1 / 2 到底谁快，补完再定默认值。
在那之前**不动默认值**。

### 3.3 但 A 有个前提：用户要的是"一张"还是"四张"

`batch_size=4` 会出 4 张图，用户可能只要 1 张。

所以不能无脑调大。应该是：

```
用户要 1 张 → batch=1，跑 74 秒
用户要 4 张 → batch=2 × 2 轮 = 48×2 = 96 秒（比 batch=1 × 4 轮 = 296 秒快 3 倍）
            或 batch=4 × 1 轮 = 146.6 秒
```

**可以确定的只有一条**（batch 2→4 那一组是同一个数量级，可信）：

```
1024² batch=4 一轮 = 146.6s（每张 36.7s）
1024² batch=2 两轮 = 48.0 × 2 = 96.0s（每张 24.0s）
→ 要 4 张时，两轮 batch=2 比一轮 batch=4 快 34%
```

但这个结论**建立在"batch=2 是 48.0s"这个可疑数据上**。
如果真实值接近 74.1s（同 batch=1），那两轮就是 148s，比 batch=4 慢。

**所以：整张 batch 策略表都要等 P6 真机重测才能定。**

现在唯一能确定的是：**"无脑调到 batch=4"是错的**（1024² 上每张反而更慢）。

## 4. 长任务怎么影响实例策略

你问的核心：**长任务时怎么"保证没有更多消耗"**。

### 4.1 现在的机制

| 场景 | 现状 |
|---|---|
| 作业跑完 | `step_release` 销毁实例 |
| 失败 | `KEEP_MINUTES=15` 保留 15 分钟 |
| 空转 | `watch` GPU<5% 15 分钟 → stop |

### 4.2 长任务真正的问题不是"跑的时候"（GPU 满载）

实测长任务时间线：

```
p1-20261107T1143   装载 116s · 推理 641s · 总计 763s
p1-20261107T1149   装载 117s · 推理 462s · 总计 583s
```

**推理期间 GPU 一直在跑，没有空转。** 唯一固定开销是开头 115 秒装载。

所以长任务的浪费点在**两头**：

| 位置 | 浪费 | 成本 |
|---|---|---|
| 开头：装载 | 115s | ¥0.068 |
| 结尾：跑完到销毁之间 | `manifest` → `release` 约 8s | 可忽略 |
| **失败后保留** | **15 分钟** | **¥0.54** ← 最大 |

**关键：长任务失败一次，保留 15 分钟 = ¥0.54，比它的装载成本贵 8 倍。**

### 4.3 按任务时长分档的策略

| 任务类型 | 判定条件 | 实例策略 |
|---|---|---|
| **短任务** | 估算 < 2 分钟 | 跑完 90 秒后停机（不销毁） |
| **中任务** | 估算 2–10 分钟 | 跑完 90 秒后停机 |
| **长任务** | 估算 > 10 分钟 **或** 用户标记 | 跑完停机；**失败后保留压到 2 分钟** |
| **批量** | 队列里同模型 ≥2 条 | 期间不回收，串行复用 |

为什么长任务的失败保留要更短：因为它跑得久，**重跑一次的成本更高**，
留着等人工续跑的价值更大 —— 但也正因为跑得久，**留着空转的代价也更大**。

```
长任务（10 分钟）保留 15 分钟 = 白烧 ¥0.54 = 该任务推理成本的 90%
```

建议：**统一压到 2 分钟**。够人工反应（有 `--resume` 命令提示），
不够的地方靠"停机不销毁"兜底（停机后随时能 start，57 秒）。

## 5. UI 上要怎么说明（你说要说明）

你明确要求「这个在后续的 UI 设计中，应予以说明」。我建议三处：

### 5.1 提交页：任务时长预估

```
预计耗时  ████████░░  约 4 分 20 秒
          基于 768×1024 · 4 张 · batch=2（实测 24s/张）

          [ ] 这是长任务（> 10 分钟），独占实例不回收
          [ ] 指定预计时长  [__] 分钟
```

**为什么要显示**：用户看到"4 分 20 秒"就知道这不是随手跑跑，
会倾向于一次配好参数而不是反复试。

### 5.2 任务列表：实例状态说明

```
实例 uhost-xxx  ● 运行中（本任务占用）
                       跑完 90 秒后自动停机，不停机可点「保持运行」
```

**为什么要说明**：用户会疑惑"为什么我的机器还在跑"。
说清"90 秒后会自动停"就不慌了。

### 5.3 成本页：装载开销单独列

```
本次花费  ¥0.2222
  ├ 建机+装载  ¥0.068  (113s · 31%)
  └ 推理       ¥0.154  (300s · 69%)

💡 同一模型连跑 N 条可共用装载开销
```

**为什么要列**：这是唯一能让用户理解"为什么跑 30 秒的图要 1 分钟"的方式。
不说，用户会觉得系统慢；说了，用户知道是装载，且知道可以复用。

## 7. 三个我要提醒你的点

### ① 「长任务」这个标签本身要谨慎

如果让用户自己标记"长任务"，会出现两种误用：

- 全标成长任务（怕被回收）→ 等同于没标
- 从不标 → 估算错了也没兜底

**建议：估算为主，用户标记只作为"覆盖"而非"必需"**。
UI 上默认显示估算值，用户只在估算明显不对时才改。

### ② 模型卡 `perf` 会随镜像/环境变

`20-跨平台运行时与权重外置方案.md` 里提过：换云换卡后同一模型的速度会变。

所以 `perf` 必须带 `gpu` 字段，且**跨云时不能直接复用**。
比如 4090 上 `s_per_mpx_step=0.30`，换到 A100 上可能是 0.18。

**这一条在接第二家云时会变成必须处理的**。

### ③ 「压榨 GPU」和「省钱」有时冲突

- 压榨 = 让 GPU 满载（batch 大、多任务并行）
- 省钱 = 少开机、早停机

**两者只在"任务已经提交、机器已经开着"的时候一致** ——
那时当然要满载跑完。但"要不要开机"是另一个决策。

建议把这两件事在 UI 上**分开表达**：
- 「这台机器上还能塞多少」→ 压榨
- 「这个任务跑完 90 秒就停」→ 省钱

## 8. 一句话

**你说得对：不能按工作流分长/短任务。** 同一个 `h3_t2v_121f` 跑过 273s 和 641s，
而 `video` 类里有 33 秒的、`image` 类里有 88 秒的。

**判定应该三层：估算（按模型速度系数 × 工作量）→ 用户声明（可覆盖）→ 实测校准（越跑越准）。**

**而"压榨 GPU"最直接的手段不是并行塞任务，是"按分辨率选对 batch_size"** ——
但现有实测数据有一半不可信（1024² batch=1/2 的 74.1s vs 48.0s 违反物理直觉），
需要 P6 真机补测才能定默认值。

**唯一确定的是：无脑调到 batch=4 是错的**（1024² 上每张从 24s 劣化到 36.7s）。
