## 2. setup 第二步：多行脚本本身没问题

**做法**：在新实例上原样执行当初崩掉的那段多行脚本（`step()` 函数 + pkill + mv + ln 全塞在一个 `--exec` 里）。

```bash
step() { echo "STEP: $*"; }
pkill ...; step "pkill1 rc=$?"
...
ln -sf ...; step "link-vae rc=$? readable=$([ -r ... ] && echo yes || echo no)"
step "prepared"
```

实际输出：

```
rc=0
STEP: pkill1 rc=1
STEP: pkill2 rc=0
STEP: manager-disabled rc=0
STEP: link-vae rc=0 readable=yes
STEP: prepared
```

**全部成功，`prepared` 正常打印。**

**所以"多行内嵌脚本语法错误"这个假设被排除了。**

### 那当初为什么崩？

现在能缩小到两个方向：

| 可能 | 证据 |
|---|---|
| **A. `csctl ssh` 输出捕获失败** | 当时用的是 `$CS ssh`（csctl 封装），不是裸 sshpass。`PREP=$(...)` 可能拿到空串或带 `[exit=N]` 的串，导致 `grep 'STEP: prepared'` 失败 → `die` |
| **B. `die` 的错误被 stdout 捕获吞掉** | `die` 写 `>&2`，而当时的 run.py 只读 `p.stdout`，所以只看到"停旧进程…"就没了 |

两者叠加就能解释当时现象：**脚本执行成功了，但检查逻辑判定失败，且错误信息看不见。**

现在这版用两个手段彻底规避：
1. 拆成 3 条独立命令，**不依赖输出内容做判断**（每条 `|| true`）
2. run.py 同时捕获 `stdout + stderr`

> 没能 100% 复现的原因：当时的实例已销毁、日志没留。要彻底确认需要保留实例复跑一次旧代码——不值当，因为现版本已经不依赖那条路径。
