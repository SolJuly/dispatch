## 二、能做到什么

### 2.1 一条命令跑完闭环

```bash
python3 tools/p1/jobctl.py new --spec reports/p1/examples/job_h3_t2v.json
python3 tools/p1/run.py <job_id>
```

九步自动走完，每步都有状态记录：

```
CREATED → PROVISIONING → READY → SUBMITTED → RUNNING
        → FETCHING → VERIFYING → PERSISTED → RELEASING → DONE
```

**实测数据**（单次闭环）：

| 模型 | 耗时 | 花费 | 产物 |
|---|---|---|---|
| H3 t2v | 2.9 min | ¥0.14 | 5.17s / 121 帧 / 768×512 |
| Qwen-Image | 1.8 min | ¥0.11 | 1024×1024 |
| LTXV 2B | 1.3 min | ¥0.08 | 2.92s / 73 帧 |
| Wan2.1 i2v | 4.2 min | ¥0.25 | 3.06s / 49 帧 |

### 2.2 五个模型的开箱即用参数

| 模型 | 结构要点 | 稳定参数 | **禁忌** |
|---|---|---|---|
| **H3** | `MiniMaxH3ImageToVideo` + `SigmaShift` | 121 帧 @24fps | 73 帧会崩 |
| **LTXV 2B** | `SamplerCustom` + **`LTXVScheduler`** | 73 帧 @25fps | 97 帧会崩；标准 KSampler 出噪点 |
| **Wan2.1** | `WanImageToVideo` + `CLIPVisionEncode` | 49 帧 @16fps | 社区 NVFP4 4bit 版不可用 |
| **Qwen-Image** | `UNETLoader` + **7B encoder** | 1024² | 3B encoder（2048维）不行 |
| ~~SVD-XT~~ | 4 段链式 | — | **已废弃**：构图自己推近、2.4 倍速 |

最反直觉的一条：**H3 要较高帧数、LTXV 要较低帧数**，需求正好相反，是训练长度决定、调参解决不了。

### 2.3 自动判定好坏

**六项复验**（参与 PASS/FAIL）：decode / geometry / frames / size / black / params
**三条内容告警**（只提示）：窗口最大帧差 / 亮度 σ / 边缘能量

这套是被 LTXV 逼出来的——它两次输出六项全绿但画面是抽象色块，暴露了「格式合格 ≠ 内容可用」。

### 2.4 断点续跑

```bash
python3 tools/p1/run.py <job_id> --resume   # 从断点继续
python3 tools/p1/run.py <job_id> --abort    # 放弃并清理
```

**实机验证**：注入 fetch 失败 → `--resume` 复用实例和 prompt_id，只补做后续步骤，**没重建机、没重提交**。

支持的两种入口：
- `FAILED_*`（失败后，走 `RESUMING` 中转）
- 中间状态（进程被杀留下的 `FETCHING` 等，直接继续）

## 三、留下的坑

按严重程度排序。

### 🔴 重要（会影响判断正确性）

**1. 亮度类指标不可靠，仍然误报**

`verify.py` 里三条告警中的两条（帧差、亮度 σ）本质只反映**平均亮度变化**，不反映画面内容。

实测反例：
- H3 闭环成功样本：帧差 0.092，比 LTXV 噪点的 0.263 还低
- 光线均匀 + 小动作的视频：σ 0.388 / 0.854，正常却被判「曝光异常」

现在用「滑动窗口 + 低阈值」压住了误报，但**指标本身的缺陷还在**，代码里有 TODO。

**正解**：改用 `ffmpeg freezedetect` 算冻结时长占比，或 SSIM。

### 🟡 中等（功能缺失但不影响主流程）

**2. `csctl pull` 目录探测 bug 未修**

`transfer.py:92` 的 `ssh()` 不捕获 `TimeoutExpired`，且 `probe()`/`_classify()` 都在 `pull()` 的 try 之外。满载实例上 ssh 抖动 → 整个 pull 崩溃。

已定位、方案已写（约 10 行），**但没改**（主链文件，等批准）。P1 用 scp 绕过。

**3. Manager 修复是 setup 层，不是镜像层**

每次建机都要等它先卡一下（或靠 patch 兜住）。治本是自制镜像时改 `/start.d/comfyui.sh`。

**4. 定时关机 ≠ 自动销毁**

失败后实例保留 15 分钟到点**关机**，但 Stopped 的机器仍占存储，要 `--abort` 或手动 `terminate` 才彻底释放。

**5. TC-12（Spot 回收）没验**

平台行为不可控。能做的「模拟」语义都不对（自己 terminate ≠ 平台回收），强行写 PASS 反而误导。

### 🟢 轻微（体验问题）

**6. LTXV 只有 2.92 秒**

`length` 只接受 `8n+1`，传 75 被静默折算成 73 帧。要精确 3.000 秒只能改 fps（73 帧 @24.333fps），没做。

**7. 画廊只支持单作业查看**

没有批量导出、没有对比、没有筛选。

**8. 失败时实例保留的提示不够醒目**

只在终端打三行提示，`jobctl show` 里没有明显标记，容易忘。

## 四、做不到什么

这些是**硬限制**，不是没做。

### 4.1 模型能力边界

| 做不到 | 原因 | 证据 |
|---|---|---|
| **H3 出 73 帧** | 训练长度 121，短序列分布外 | 实测崩坏 |
| **LTXV 出 97 帧** | 2B 参数量撑不住长序列时序一致性 | 实测后 1/3 人物崩解 |
| **Wan 用社区量化版** | NVFP4 4bit 精度不够 | 实测过曝 + 噪点 + 崩坏 |
| **精确 3.000 秒（不改 fps）** | 帧数受 `8n+1` 约束 | 传 75 出 73 |
| **SVD 做长镜头** | 4 段链式构图自己推近 | 色漂 12.43 vs 单段 3.22 |

### 4.2 架构限制

| 做不到 | 原因 |
|---|---|
| **并发多任务** | 单任务锁（`flock`），设计如此 |
| **长视频拼接** | 按你的要求延后，没做 |
| **跨实例续跑** | 实例被回收后中间态没法迁移，要重做 |
| **失败自动重试** | 只有手动 `--resume`，没有自动 N 次 |
| **内容质量的真判断** | 三条告警只能提示，最终还得人眼看 |

### 4.3 判断不了的事

| 问题 | 现状 |
|---|---|
| Manager 卡住的真实概率 | 本次 5 轮 0 卡、历史 2/4 卡，样本都不够 |
| 生成的视频「好不好」 | 只能证明「不是废片」（不是黑帧/噪点/静止），不能证明「好看」 |
| 哪个模型适合什么场景 | 只测了同一类 prompt，没做场景矩阵 |

## 五、下一步建议

### 优先级 P0（做完收益最大）

**1. 自制镜像**

现在每次建机 60–90 秒 + setup 30 秒，其中大部分在装 ComfyUI、软链模型、禁 Manager。

自制镜像可以：
- 预置好 `/start.d`（无 Manager）、软链、离线变量
- 建机到可用压到 **1.5 分钟以内**
- 顺带解决 Manager 卡住的根本问题

**预估收益**：每次闭环省 1–1.5 分钟，按 100 次算省 2 小时。

**2. 用 `freezedetect` 替代亮度指标**

```bash
ffmpeg -i x.mp4 -vf "freezedetect=n=0.003:d=0.5" -f null -
```

算冻结时长占比，比帧差准得多。这是唯一能真正判断「画面是否在动」的低成本方法。

### 优先级 P1（补功能）

**3. 修 `csctl pull` 的 ssh 超时**（方案已备，10 行）

**4. 拼接能力**——如果要 3 秒以上的视频，需要：
- 同场景多段生成 + 首帧续接
- 或者换支持长序列的模型（Wan2.2？没测）

**5. 批量任务**——同一 prompt 跑 N 个 seed 挑最好的，或一次跑多个模型对比

### 优先级 P2（打磨）

6. 画廊支持筛选/对比/批量导出
7. `jobctl show` 里醒目标记「实例保留中」
8. TC-12 等真遇到 Spot 回收时补现场

### 不建议做的

- **不要再试图让 H3 出短帧、LTXV 出长帧**——已证伪，是训练长度决定的
- **不要用社区量化版模型**（NVFP4/4bit）——省显存不值得，质量崩得明显
- **不要在亮度类指标上继续调阈值**——方向错了，该换指标
