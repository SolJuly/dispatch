# 定时关机兜底：实测验证

> 2026-10-28 23:38–23:49 · 1 台 5090 · 实扣 **¥0.47**

## 疑问

断点续跑失败时调用 `cs.stop_at(uid, now+15min)` 做兜底。但查实例时 `SchedulerStopTime` 返回 `None`，
看起来像「没设上」，怀疑兜底是假的。

## 结论：兜底真实有效，`None` 是正常现象

### 1. `SchedulerStopTime: None` 的原因

`compshare/cs.py:301` 的注释已经写明：

```python
r = self.json_call("UpdateCompShareStopScheduler", {...})
record_stop_at(i["UHostId"], ts)  # Describe 不返回该字段，本地留档用于展示
```

**平台的 Describe 接口根本不返回这个字段**，所以查到的永远是 `None`。判断是否设上要看：
- API 返回的 `RetCode`（0 = 成功）
- 本地 `.compshare/stop_at.json` 的留档

### 2. 实测：平台真的会按时关机

| 时刻 | 事件 |
|---|---|
| 23:39:32 | 建机 `uhost-1x15cqjtqnov`（5090） |
| 23:40:12 | `stop_at(ts=23:45:42)` → API `RetCode: 0` |
| 23:45:23 | 检查：`State: Running`（还没到点） |
| **23:46:59** | 检查：**`State: Stopped`** ✅ |
| 23:48:00 | 检查：`State: Stopped` |

设定 23:45:42，实际 23:46:59 前完成关机（误差 < 90 秒，平台调度延迟）。

### 3. 为什么之前看到 `None` 会误判

`_keep_instance` 里 `cs.stop_at` 包在 `try/except` 中，异常会被吞成「⚠ 保留实例失败」。
本次日志显示「实例已保留」，说明调用没抛异常——但当时没去查本地留档，只看了 Describe 的
`SchedulerStopTime: None`，于是误以为没设上。

## 修正

`run.py` 的 `_keep_instance` 已加注释，说明该字段恒为 `None`，并附实测数据，
避免后来者重复这个误判。

## 对断点续跑的影响

- 失败后实例保留 15 分钟，到点自动关机 → 最多空烧约 ¥0.95（4090_48G）
- 关机后实例仍在（Stopped），要彻底释放需 terminate
- 兜底有效，但**不是**「自动销毁」——停机的机器仍占存储，长期不管要手动清
