# 断点续跑：幂等性分析与设计

> 设计时间：2026-10-28 23:35 · 单任务场景，不考虑并发
> 目标：中间失败后能从断点继续，不重复建机、不重复提交

---

## 1. 九步幂等性分析

| # | 状态 | run.py 动作 | 幂等 | 重复执行的后果 | 续跑能否跳过 |
|---|---|---|---|---|---|
| 1 | `PROVISIONING` | `cs.create()` 建机 | **❌** | 多花一台机器的钱 | 仅当实例仍存活 |
| 2 | `READY` | push yaml + 禁 Manager + 启动 + 自检 | ✅ | 无害（脚本本身幂等） | 能 |
| 3 | `SUBMITTED` | `POST /prompt` 提交工作流 | **⚠️** | ComfyUI 队列多一个任务，算力白烧 | 能（若 prompt_id 仍有效） |
| 4 | `RUNNING` | 轮询 `/history` | ✅ | 无害 | 能 |
| 5 | `FETCHING` | scp 拉产物 | ✅ | 覆盖写，无害 | 能 |
| 6 | `VERIFYING` | 六项校验 + 三条告警 | ✅ | 纯计算 | 能 |
| 7 | `PERSISTED` | 写 manifest（原子写） | ✅ | 覆盖写 | 能 |
| 8 | `RELEASING` | `cs.terminate()` | **⚠️** | 重复销毁报 8903 / 404 | 不能，只做一次 |
| 9 | `DONE` | 补 release_at、写账本 | ✅ | 覆盖 | 终点 |

### 结论

- **真正不可重复的只有 2 个**：建机（花钱）、销毁（状态不可逆）
- 中间 5 步全部可重跑
- `SUBMITTED` 是"半幂等"——技术上能重跑，但会浪费一次推理

所以续跑的核心是三件事：

1. **复用实例**：记住 `uhost_id`，不重新建机
2. **复用 prompt_id**：已提交过的任务不要重提
3. **顺序重放状态**：状态机要求连续转移，跳过的步骤要"快速走过去"（不做动作）

## 2. 设计

### 2.1 job.json 新增 `steps`

```json
"steps": {
  "provision": {"done": true,  "at": "2026-10-28T23:40:00+08:00",
                "uhost_id": "uhost-xxx", "gpu": "4090_48G", "hourly": 3.8},
  "setup":     {"done": true,  "at": "..."},
  "ready":     {"done": true,  "at": "..."},
  "submit":    {"done": true,  "at": "...", "prompt_id": "abc-123"},
  "wait":      {"done": true,  "at": "...", "files": [["", "out.mp4"]]},
  "fetch":     {"done": true,  "at": "...", "local": ["artifacts/01-out.mp4"]},
  "verify":    {"done": true,  "at": "...", "verdict": "PASS"},
  "persist":   {"done": true,  "at": "..."},
  "release":   {"done": false}
}
```

只存**续跑需要的 ID**（uhost_id / prompt_id / 文件列表），
不存密码——续跑时用 `CS.get(uhost_id)` 重新取。

### 2.2 续跑流程

```
run.py <job_id> --resume
  │
  ├─ 读 job.json，看 state 与 steps
  ├─ 若 state 是 FAILED_*：按断点计算恢复目标
  │    · steps.provision.done 且实例存活 → 从 setup 继续
  │    · steps.submit.done 且 prompt_id 有效 → 从 wait 继续
  │    · 否则从断点继续
  ├─ 顺序重放：对已完成的步骤只走 transition（不执行动作）
  └─ 从第一个未完成的步骤开始正常执行
```

### 2.3 状态机的"恢复边"

现状：`FAILED_*` 是终态，只能 `→ RELEASING → FAILED`。

续跑需要从 `FAILED_RUN` 回到 `RUNNING`。两种做法：

| 做法 | 改动 | 风险 |
|---|---|---|
| A. 直接加边 `FAILED_* → 原状态` | 小 | `FAILED_*` 不再是终态，语义变弱 |
| **B. 加 `RESUMING` 中转态** | 中 | 状态多一个，但语义清晰：失败 → 待续跑 → 原状态 |
| C. 失败时不进 FAILED_*，直接保持原状态 | 小 | 失败无终态记录，违反"失败必须可追溯" |

**选 B**：

```
FAILED_PROVISION / FAILED_RUN / FAILED_FETCH / FAILED_VERIFY
        ↓ (仅 --resume)
    RESUMING
        ↓ (按断点)
 PROVISIONING / READY / SUBMITTED / RUNNING / FETCHING / VERIFYING
```

- 现有守卫（G1 未落盘不许销毁、G2 完成需 PASS）**完全不动**
- `FAILED_*` 仍然不能直接跳回业务状态，必须先经 `RESUMING`
- `RESUMING` 只能从 `FAILED_*` 进，且只能去"断点对应的那一步"

### 2.4 失败时保留实例

续跑的前提是实例还在。所以失败处理要改：

| 现状 | 改为 |
|---|---|
| 失败 → 立即 `RELEASING` 销毁 | 失败 → 进 `FAILED_*`，**实例保留**，设定时关机兜底 |
| — | 用户决定：`--resume` 续跑，或 `--abort` 销毁 |

**风险**：忘了续跑 → 实例空烧。兜底：
- 失败时自动 `stop_at(now + 15min)`（15 分钟自动关机）
- `jobctl show` 显示"实例保留中，可续跑 / 可 abort"

### 2.5 不做的（本轮）

- 跨实例续跑（实例被回收后换机重跑）—— 需要产物/中间态迁移，留后续
- 自动重试（失败后自动 resume N 次）—— 先手动
- 并发锁细化 —— 单任务场景不需要

## 3. 分阶段实施

| 阶段 | 内容 | 验收 |
|---|---|---|
| **P1** | job.json 记录 steps；run.py 每步完成后写入 | 跑一次闭环，job.json 里 steps 全 done=true |
| **P2** | `--resume`：读取 steps、顺序重放、从断点继续；失败保留实例 + 定时关机兜底 | 模拟中途失败，`--resume` 从断点恢复 |
| **P3** | 测试用例：失败注入 → 续跑 → 验证幂等 | `cases.py` 新增 TC-13/14 |

## 4. 风险

| 项 | 评估 |
|---|---|
| 状态机改动 | 新增 1 个状态 + 2 类边，现有守卫不动；`validate` 会校验 events 与 state_seq 一致 |
| 实例空烧 | 失败保留实例 + 15 分钟自动关机兜底 |
| 重复提交 | `steps.submit.prompt_id` 存在且 `/history` 有记录 → 跳过提交 |
| 重复销毁 | `steps.release.done` 一旦 true 不再重试 |
| 向后兼容 | 老 job.json 没有 `steps` 字段 → 视为"无断点"，从头跑（等价现状） |
