# OOM 自动升卡：真机验证报告

日期：2026-11-12
成本：**约 ¥6.3**（四次作业，含两轮升卡）
结论：**链路端到端打通，且抓出 3 个只有在真机上才暴露的 bug —— 全部已修**

证据：`reports/p20/evidence/oom-escalate/{job.json,events.jsonl}`

---

## 一句话

**升卡真的发生了。** 从 24G 的 4090 升到 96G 的 H20，
`GraphicsMemory.Value = 96` 实测确认，ComfyUI 在那台机器上连续跑了 **40 分钟**，
显存占用 **61,737 MiB**、GPU 利用率 100%。

而第一轮真机跑的时候，它**根本没升过卡** —— 三轮全建 24G 机器，
每轮都在同一个点 OOM。这是纯逻辑测试完全看不到的问题。

## 二、真机暴露的三个 bug

### bug 1：`--gpu` 让升卡彻底失效（最严重）

**现场证据**（第一轮，12:11–12:22）：

```
[12:13:51] 已创建 uhost-1xlvk5yw9vdp，等 Running…
[12:14:31] ✗ 推理失败：KSamplerAdvanced: Allocation on device
[12:14:31]   ⤴ 显存不足，准备升卡：显存不足，24G → 32G（5090 ¥3.99/h）
[12:14:33]   ⟳ 从 provision 重跑（5090，32G）
[12:14:34] 计划 4090 ×1 · 镜像 p2-comfy-media-v4 · ≈2.15/h     ← 还是 4090
[12:17:35] ✗ 推理失败：KSamplerAdvanced: Allocation on device
[12:17:37]   ⟳ 从 provision 重跑（4090_48G，48G）
[12:17:39] 计划 4090 ×1 · 镜像 p2-comfy-media-v4 · ≈2.15/h     ← 还是 4090
[12:20:44] ✗ 推理失败：KSamplerAdvanced: Allocation on device
```

`job.json` 里 `floor_vram` 明明写着 48，`oom_escalation.attempts` 也记了两条
`gpu: "4090", vram: 24`，而建出来的机器**三台全是 24G**。

**根因**：

```python
def _gpu_candidates(job, opts):
    if getattr(opts, "gpu", None):
        return [opts.gpu]          # ← 短路返回，下限检查在后面，永远走不到
    ...
    floor = oom_escalate.floor_vram(job)   # ← 死代码
```

而生产路径**几乎总是**带 `--gpu`：

```
tools/p20/p20ctl.py:419   cmd = [..., "--gpu", a.gpu or spec["instance"]["required_gpu"][0], ...]
tools/p2/batchctl.py:215  sp.add_argument("--gpu", default="4090")
```

`p20ctl new --run` 取 `required_gpu[0]` 传进去 —— 对 `sdxl_t2i` 就是 `"4090"`。
所以从 UI/CLI 正常提交的作业，升卡功能**一次都不会生效**。

**测试为什么没抓到**：测试直接构造 `opts.gpu = None` 调这个函数，
生产传的是具体值。这个 bug 只有真机能发现。

**修复**：优先级改成 **显存下限 > `--gpu` > `required_gpu`**。
人工指定但低于下限时，忽略并**大声说出来**（静默是最坏的一种，因为你以为指定生效了）。

### bug 2：抢卡顺延会退回小卡

`step_provision` 里：

```python
cands = _gpu_candidates(job, opts)     # ["4090_48G"]，正确
if gpu not in cands:
    cands = [gpu] + cands              # ← 变成了 ["4090", "4090_48G"]
```

抢卡时的换卡逻辑在 `cands` 里轮转，于是下一轮就退回 24G —— 正是升卡想避免的那张。

**修复**：插回之后再按下限过滤一次；过滤后为空则**显式失败**，
不退回小卡（宁可这一轮建机失败 ¥0，也不要造一台注定 OOM 的机器）。

### bug 3：候选无货时不去阶梯表补更大卡

**现场证据**（12:25）：

```
[12:25:29] 显存下限 48G → 候选 ['4090', '4090_48G'] 收窄为 ['4090_48G']
[12:25:30] ✗ 4090_48G 当前无现货（226604）。
```

当时 **H20 有 2 台（96G，完全满足 ≥48G）**，但 `_pick_gpu` 只在声明列表里找，
不会去阶梯表补。

**修复**：有下限时，从阶梯表补所有满足下限的卡（按价格升序），
逐个查库存，有货就加进候选。只补 ≥ 下限的，不补更小的。

## 三、修复后的真机结果

第三轮（12:26–13:09），日志显示升卡真的生效了：

```
[12:26:16] 显存下限 48G：声明候选都无货，从阶梯补满足下限的卡 ['H20']
[12:26:29] 计划 H20 ×1 · 镜像 p2-comfy-media-v4 · ≈7.50/h
[12:29:28] PROVISIONING -> READY
[12:29:43] SUBMITTED -> RUNNING
```

云端实例实测：

```
uhost-1xlw34007db1  p1-349d92  Running  H20  {'Rate': 5, 'Value': 96}
```

**不是 24G，是 96G。** 这是升卡第一次真正落地。

跑了 40 分钟时的远端状态：

```
61737 MiB, 97871 MiB, 100 %     ← 61.7G 显存占用，GPU 100%
```

同一份工作流在 24G 卡上 40 秒就 OOM。**24G 装不下的东西，96G 装下了。**

最终失败原因是**推理超时（2400s）**，不是 OOM：

```
[13:09:48] RUNNING -> FAILED_RUN | 推理超时（2400s）
```

Wan 14B × 1280×1280 × 10 秒在 H20 上 40 分钟没跑完 —— 这是参数太激进
（是我为了让 24G 必 OOM 特意调的），不是升卡的问题。

## 七点五、第四个 bug：测试读了生产账本

真机验证花了 ¥9.03，超过日上限 ¥8.00 → 花费闸拒绝补位 → **9 条 autostart 测试全红**。
代码一行没改。

根因在 `autostart._ledger_for()`：

```python
cand = Path(jobs_dir).parent / "ledger.jsonl"
return cand if cand.exists() else None      # ← None 会退回真实账本
```

临时目录里没有 `ledger.jsonl` → 返回 `None` → `money_guard.check(None)`
读**真实账本** → 看到"今日已花 ¥9.03" → 闸门拒绝 → 测试失败。

**最难受的是那个函数的 docstring 早就写着**：

> 如果账本还读真实的，那么"今日已花 ¥1.20"会串进测试里，
> 结果取决于当天跑了多少活 —— 那种测试迟早会莫名其妙地红。

注释写对了，但那个 `None` 分支把临时路径换回了真实路径。**警告写在函数头上，
没写进代码结构里，等于没写。**

修复：从不返回 `None`。临时目录一律用临时账本（不存在 = 今天没花 ¥0），
只有生产目录才用真实账本。

这类 bug 的失效方式最难受：**它红的时候你会去查代码，而代码是对的。**

## 八、四个 bug 的共同点

前三个**都不是逻辑错误**，是**接线错误**：

```
bug 1  _gpu_candidates 的优先级顺序（--gpu 短路在前）
bug 2  step_provision 里"把首选 gpu 插回列表"之后没再过一遍下限
bug 3  _pick_gpu 只在声明列表里找，没延伸到阶梯表
bug 4  _ledger_for 的 None 分支把临时账本换回了真实账本
```

第四个是**测试隔离**问题，性质不同但成因相同：一个"看起来无害的兜底分支"
（`return cand if cand.exists() else None`）把正确路径悄悄换成了错误路径。

三个函数的**单测都是绿的**，因为单测喂的是"理想的 opts"，
而生产喂的是 `p20ctl` 自己拼出来的 opts。

这解释了为什么第一版 31 条测试全绿之后还是要真机跑一次：
**测试验证的是"我写的函数对不对"，真机验证的是"这些函数在真实调用链里有没有被用上"。**
两者不是同一件事，而且后者的盲区恰好覆盖了前者的盲区。
